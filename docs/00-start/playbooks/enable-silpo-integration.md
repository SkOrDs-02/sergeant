# Playbook: Enable / Operate Silpo Integration

> **Last touched:** 2026-08-25 by @Skords-01. **Next review:** 2026-11-26.
> **Status:** Active

**Trigger:** вмикаємо `SILPO_ENABLED` у проді вперше · користувачі скаржаться,
що Сільпо «відвалилось» · MCP почав віддавати 429/схема поїхала · треба
вимкнути інтеграцію негайно.

## Owner surface

- Primary surface: Coolify env vars, `apps/server/src/modules/silpo/**`
- Coupled surface: `docs/02-engineering/integrations/env-vars.md` §24,
  [спека](../../90-work/planning/specs/silpo-mcp-integration.md)
- Governing skill: `sergeant-deploy-and-observability` (для інциденту —
  `sergeant-bugfix-and-regression`)

---

## Decision Tree

**Q1: Що сталось?**

- Вмикаю вперше → **ACTION A: перший запуск**
- Усе лежить / 429 / схема поїхала → **Q2**
- Треба вимкнути прямо зараз → **ACTION D: kill switch**

**Q2: Це б'є по всіх користувачах чи по одному?**

- По всіх (спільний `client_id` затротлено/забанено) → **ACTION B: ре-реєстрація DCR**
- По одному (у нього `reauth_required`) → **ACTION C: повторна авторизація користувача**

## ACTION A: перший запуск у проді

**Порядок кроків важливий** — крок 2 без кроку 1 покладе весь API, а не лише
Silpo (`assertStartupEnv` кидає на старті, не деградує).

1. **Перевір, що `PUBLIC_API_BASE_URL` уже стоїть** на Coolify і дорівнює
   публічному HTTPS-URL API. Він обов'язковий при `SILPO_ENABLED=true` —
   без нього контейнер не стартує взагалі.
2. **Згенеруй ключ шифрування токенів:**
   ```bash
   node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
   ```
   → `SILPO_TOKEN_ENC_KEY` (або одразу ring: `SILPO_TOKEN_ENC_KEYS=v1:<hex>`).
   **Втрата ключа = всі зв'язки мертві** (токени не розшифруються), лікується
   лише повторною авторизацією кожного користувача.
3. **Зареєструй OAuth-клієнта з ПРОДОВИМ redirect_uri.** `client_id` зі
   спайку §0 зареєстрований на `localhost` і в проді не спрацює. DCR —
   разовий ops-крок, не рантайм: entry point — `registerDynamicClient()` у
   `apps/server/src/modules/silpo/oauth.ts`; `redirect_uri` має бути рівно
   `${PUBLIC_API_BASE_URL}/api/silpo/callback`. Отриманий `client_id` →
   `SILPO_OAUTH_CLIENT_ID`.
4. **Постав `SILPO_ENABLED=true`** і передеплой. Міграції 125–127 накотяться
   pre-deploy (`node dist-server/migrate.js`).
5. **Димова перевірка на своєму акаунті:** Налаштування → Фінік → «Зв'язати
   Сільпо» → OAuth → повернення зі статусом connected → «Оновити чеки» →
   у транзакції «Сільпо» видно секцію «Чек».
6. **Фоновий синк вмикається сам** — окремої дії не треба. Це in-process
   poller (`modules/silpo/syncScheduler.ts`), який стартує разом із
   сервером і живе рівно доти, доки `SILPO_ENABLED=true`. Перший прохід —
   через 5 хвилин після старту (щоб серія передеплоїв не била Сільпо),
   далі щогодини перевіряє, кого не синкали понад 20 годин.

   > **Не n8n.** Зовнішнього крона тут свідомо немає: n8n у проді на паузі,
   > і ~20 роутів у репо вже висять під воркфлоу, яких ніхто не створив
   > (див. [orphaned-code аудит](../../90-work/audits/2026-08-05-orphaned-code-audit.md)).
   > Патерн узятий з `modules/billing/plataScheduler.ts`.

   Ручний прогін для діагностики лишається:
   `POST /api/internal/silpo/sync-all` під `INTERNAL_API_KEY` (без
   `minAgeHours` бере всіх підряд, ігноруючи поріг віку).

> **Немає per-user гейта.** `SILPO_ENABLED` — глобальний env-прапорець на
> весь деплой; окремого користувацького прапорця в `FLAG_REGISTRY` для
> Silpo немає. Фактичний гейт — те, що зв'язка добровільна: доки людина не
> натисне «Зв'язати Сільпо», для неї нічого не змінюється. Якщо треба
> впустити лише підмножину бета-тестерів — це окрема робота
> (див. [add-feature-flag.md](./add-feature-flag.md)).

## Чому колбек не вимагає сесії (інцидент 2026-08-25)

Перший запуск у проді дав кожному, хто тиснув «Звʼязати Сільпо», сирий
JSON `{"code":"UNAUTHORIZED"}` у вкладці замість екрана налаштувань.

Причина не в протухлій сесії, а в топології доменів:

| Змінна                | Значення                                                        |
| --------------------- | --------------------------------------------------------------- |
| `BETTER_AUTH_URL`     | `https://sergeant.vercel.app` — тут живе кука сесії             |
| `PUBLIC_API_BASE_URL` | `https://api.167-233-98-92.sslip.io` — сюди веде `redirect_uri` |

`apps/web/vercel.json` не проксіює `/api/*` на бекенд (rewrite ловить усе,
КРІМ `/api/` і `/.well-known/`), тож це два різні сайти. Повернення від
Сільпо — top-level навігація на api-домен, де куки сесії немає **ні в кого**.
Роут стояв під router-level `requireSession()`, і той віддавав 401 ще до
хендлера.

Полагоджено тим, що `GET /api/silpo/callback` реєструється ДО
`requireSession()`, а власника бере зі `state` (`silpo_oauth_state`,
міграція 126) — він і був носієм контексту з самого початку. Решта роутів
сесію вимагають як раніше.

**Що це означає для ops:** якщо колись міняється `PUBLIC_API_BASE_URL` або
зʼявляється проксі `/api/*` через фронт — DCR треба перереєструвати
(ACTION B), бо `redirect_uri` вшитий у `client_id`. Сесія на колбеку не
потрібна за жодного з варіантів.

## ACTION B: ре-реєстрація DCR (спільний client_id затротлено/забанено)

Симптом: `429 SILPO_RATE_LIMITED` або 401/403 **одночасно у всіх**
користувачів; у логах `recordExternalHttp("silpo", …)` сплеск помилок,
circuit breaker відкритий (він глобальний, per-client — не per-user).

1. **Спочатку зупини кровотечу:** `SILPO_ENABLED=false` (ACTION D). Далі
   спокійно.
2. Повтори DCR (крок 3 з ACTION A) — отримаєш **новий** `client_id`.
3. Онови `SILPO_OAUTH_CLIENT_ID`, увімкни прапорець назад.
4. **Наслідок для користувачів:** видані старим клієнтом токени більше не
   дійсні — усі побачать `reauth_required` і мають пере-зв'язати акаунт.
   Збережені чеки, спліти й записи комори при цьому **лишаються** (вони в
   нашому PG, не залежать від токена).

Це не інцидент, а задокументований крок: контракту/SLA з Сільпо немає,
`client_id` вважається ефемерним (спека § Ризики).

## ACTION C: один користувач у `reauth_required`

Сервер сам ставить цей статус, коли refresh не допоміг. Дій не треба —
користувач бачить банер і кнопку повторної авторизації на картці
інтеграції. Якщо не допомагає: «Відключити» → «Зв'язати Сільпо» заново
(чеки при цьому не зникають — disconnect прибирає лише токени).

## ACTION D: kill switch

`SILPO_ENABLED=false` на Coolify. Ефект: кожен роут `/api/silpo/*` віддає
`503 SILPO_DISABLED`, каскад пошуку їжі мовчки працює без Silpo, картка в
налаштуваннях показує «Інтеграція ще не увімкнена». **Нічого не
видаляється**, деплой не потрібен — лише рестарт контейнера.

Повне видалення даних — окрема користувацька дія «Видалити всі дані
Сільпо» (`POST /api/silpo/wipe`), не ops-крок.

## Що моніторити після вмикання

| Сигнал                             | Де дивитись                                       | Що означає                                                             |
| ---------------------------------- | ------------------------------------------------- | ---------------------------------------------------------------------- |
| `silpo_schema_drift` / zod-помилки | логи сервера (`logger.warn`)                      | Сільпо мовчки змінили контракт — треба оновити схеми                   |
| сплеск 429                         | `recordExternalHttp("silpo", …)` метрики          | ліміт спільного client_id; див. ACTION B                               |
| breaker відкритий                  | ті самі метрики + `upstream_unavailable` у логах  | MCP лежить; деградація вже автоматична                                 |
| частка чеків без mono-пари         | `silpo.sync.completed` → `unmatched` vs `matched` | калібрування matcher-а; поріг і дії — § нижче                          |
| фоновий синк мовчить               | `silpo.sync_all.completed` раз на добу в логах    | poller не стартував (шукай `silpo_sync_poller_started` у логах старту) |

### Перший тиждень: виміряти «платник ≠ покупець»

Це **єдиний ризик зі спеки, який неможливо було виміряти до продакшену**
(§ Ризики: спайк §0 його не перевірив, бо в dev-базі не було mono-даних).
Карта лояльності Сільпо сімейна: чек виписується на того, хто пред'явив
картку, а транзакція проходить по картці того, хто платив. Якщо це різні
люди, matcher **не має за що зачепитись** — і жодне доопрацювання порогів
цього не полагодить.

Дивись на `unmatched` у рядку `silpo.sync.completed` (пишеться на кожен
sync, ручний і фоновий):

| Частка `unmatched` за тиждень | Читати як                                                                                |
| ----------------------------- | ---------------------------------------------------------------------------------------- |
| < 15%                         | норма — готівка, чужі картки, чеки поза вікном ±1 доба                                   |
| 15–40%                        | matcher варто калібрувати: розширити вікно або послабити збіг суми                       |
| > 40%                         | **системна діра, не баг matcher-а** — родинна карта; це продуктове рішення, не інженерне |

Що робити при > 40%: не крутити пороги (хибних матчів стане більше, а вони
дорожчі за пропущені). Варіанти — ручне привʼязування чека до транзакції з
UI, або чесно звузити обіцянку фічі до «свої покупки своєю карткою».
Рішення за founder-ом.

> **Перший вимір (2026-08-25) спростував гіпотезу.** 34 unmatched-чеки, з
> них **26 просто старіші за завантажену історію банку** (чеки з 2023-08-09,
> mono-транзакції в базі — з 2026-03-26), а сіра зона вікна ±1 доба —
> **0 чеків**. Тобто високий `unmatched` тут НЕ означає ні дірявий matcher,
> ні сімейну карту. **Перш ніж читати частку за таблицею вище — звір
> глибину історії mono.** Розбір: [спека § Калібрування за першим
> тижнем](../../90-work/planning/specs/silpo-mcp-integration.md).

## Діагностика «чек не привʼязався»

Порядок перевірок від найчастішої причини до найрідшої. Перші три
закривають майже все — не починай із порогів matcher-а.

1. **Чи є взагалі банківська транзакція?** Найчастіша причина — оплата
   не тією карткою або готівкою.
   ```sql
   SELECT to_char(t.time,'MM-DD HH24:MI'), t.amount, t.mcc
     FROM mono_transaction t
    WHERE t.user_id = '<user_id>' AND t.time >= date_trunc('month', NOW())
      AND (t.mcc = 5411 OR t.description ILIKE '%сільпо%');
   ```
2. **Чи не відстає синк банку?** `SELECT max(time) FROM mono_transaction
WHERE user_id = '<user_id>';` — чек свіжіший за це значення пари ще
   просто не має.
3. **Чи пару не відхилено вручну?** Кнопка «Це не той чек» пише в
   `silpo_tx_receipt_link_rejections` НАЗАВЖДИ, і matcher її більше не
   поверне — так і має бути.
   ```sql
   SELECT * FROM silpo_tx_receipt_link_rejections WHERE user_id = '<user_id>';
   ```
   Лікується не SQL-ем, а з UI: «Прикріпити чек» у деталях операції знімає
   відхилення разом із привʼязкою.
4. **Чи сходяться суми до копійки?** `sumReg` уже НЕТТО після бонусів
   (див. [спеку § 6](../../90-work/planning/specs/silpo-mcp-integration.md)),
   тож розбіжність означає щось інше — дві покупки однією оплатою,
   часткове повернення.

## Verification

Після ACTION A (перший запуск) — пройди всі пункти на власному акаунті,
**до того як казати бета-тестерам, що фіча є**:

- [ ] Контейнер піднявся (`/health` 200) — тобто `PUBLIC_API_BASE_URL` і
      ключі на місці, `assertStartupEnv` не кинув.
- [ ] «Зв'язати Сільпо» веде на `auth.silpo.ua` і повертає зі статусом
      `connected` (а не на localhost — інакше DCR зроблено зі старим
      `redirect_uri`, див. ACTION A крок 3).
- [ ] «Оновити чеки» витягує чеки; у банківській транзакції «Сільпо»
      з'явилась секція «Чек» з позиціями.
- [ ] «Розбити за чеком» дає спліт, сума частин збігається з сумою
      транзакції до копійки.
- [ ] Комора: «З покупок Сільпо» додає позиції; список покупок показує
      віднімання комори з підписом розрахунку.
- [ ] Кошик: «У кошик Сільпо» → превʼю → підтвердження → позиції реально
      з'явились у кошику на silpo.ua (**єдиний спосіб перевірити запис у
      зовнішню систему — тільки живий акаунт**).
- [ ] «Видалити всі дані Сільпо» прибирає чеки, але лишає підтверджені
      спліти й записи комори.
- [ ] ACTION D перевірено: `SILPO_ENABLED=false` → картка каже «ще не
      увімкнена», решта продукту працює як раніше.
