## Принципи (те, що коштувало часу, коли їх порушували)

1. **Вимірюй, не оцінюй на око.** «Пілюля перекриває таббар» — це не скарга, а число: y=720 проти y=708, hit-test по кожному табу. «Лейбл ріжеться» — це `scrollWidth > clientWidth`. Кожна візуальна знахідка в звіті мусить мати замір, інакше фікс неможливо верифікувати.
2. **jsdom не бачить layout.** Юніт-тести не ловлять перекриття, усічення, скрол-пастки і порядок відмалювання. Для таких речей — жива браузерна перевірка на 390×844, а в тестах — пін на структурний намір (`className` містить `sticky`/`overscroll-contain`) із коментарем, чому пін, а не поведінка.
3. **Тест мусить червоніти без фіксу.** Перед звітом тимчасово зніми фікс і переконайся, що тест падає саме там. На Фізруку другий тест черги міграцій у першій редакції проходив і без фіксу — тобто не перевіряв нічого.
4. **Перевіряй власний діагноз перед фіксом заново.** Між аудитом і фіксом стан коду міг змінитись, а сам діагноз — бути симптомом глибшої причини. L-8 у Фізруку значився як «дрібниця P3: сід не пише дані», а виявився системною регресією на всі чотири модулі (місток LS→SQLite видалили разом із legacy-дренажем).
5. **Рішення власника фіксуються в доці, не в переписці.** Погоджені варіанти — окремою секцією §0.1 зі слідом «що саме ухвалено», інакше через місяць ніхто не доведе, чому зроблено саме так.
6. **Аудит-док — живий.** Кожна хвиля фіксів дописує секцію §0.x «Виконано» з тим, що перевірено наживо, і з розбіжностями між діагнозом і фактичним коренем. Звіт без цього старіє за день.
7. **Не заглушуй лінт заради зеленого.** Додати файл у allowlist — це не фікс. Сирі розміри контролів — задокументований `eslint-disable` із причиною, а не зміна типографіки в PR, який про інше.

## Steps

### 1. Скоуп і контекст (до будь-якого коду)

- Прочитай продуктовий канон модуля (`docs/01-product/model/<module>.md`), спеку і попередні аудити (`docs/90-work/audits/`).
- Зафіксуй скаргу власника **дослівно** — вона стане рамкою дизайн-дослідження («щільно і без структури» → інвентар вертикального стека).
- Склади карту поверхонь: сторінки, фло, оверлеї, стани (порожній / демо / активна сесія / завершена).

### 2. Кодовий аудит — read-only fan-out + адверсарний пас

- Розсип read-only агентів по вимірах: логіка/стани, a11y, дизайн-система, мертвий код, storage/sync. Кожен повертає знахідки з file:line і доказом-цитатою.
- **Адверсарний пас обовʼязковий:** окремий прохід, що намагається СПРОСТУВАТИ кожну знахідку. На Фізруку він убив частину «знахідок» (recovery вже фільтрував порожні сети — розходились лише телеметрія і хінт) і врятував звіт від хибних тверджень.
- Знахідки агентів — не істина. Перевіряй вибірково руками, особливо high-severity.

### 3. Браузерна верифікація наживо

Середовище: дев-сервер + демо-режим (`?demo=1`), viewport **390×844** (найвужчий реальний кейс), `agent-browser` або руками.

- Пройди **кожне** фло до кінця: старт → дія → refresh (перевірка відновлення стану) → завершення. Не зупиняйся на happy path — тисни «Назад» звідусіль, відкривай оверлеї поверх оверлеїв.
- Замір для кожної підозри: `getBoundingClientRect()` (перекриття, видимість), `scrollWidth`/`clientWidth` (усічення), `scrollHeight`/`clientHeight` (скрол-пастки), hit-test кліків крізь оверлеї.
- Скрол-поведінка оверлеїв: `overscroll-behavior`, липкість шапки/дій, чи не віддається жест сторінці під аркушем.
- Консоль має бути чиста; телеметрію читай з `window.__hubAnalytics` ring-buffer (детермінований, на відміну від network).
- Демо-режим — і обʼєкт перевірки, і інструмент: якщо демо порожнє там, де хаб обіцяє дані — це знахідка класу «вітрина бреше» (L-8). А коли демо оживе — воно висвітить дані-сміття, які роками ніде не рендерились (сирі ключі мʼязів у «Почекати»).

### 4. Дизайн-дослідження проблемного екрана

Для екрана, на який скаржаться («щільно», «без структури»):

- **Інвентар вертикального стека:** список елементів згори вниз із висотою в px; скільки одиниць контенту вміщає viewport (Фізрук: 1.2 картки вправи → після редизайну 2).
- **Анатомія вкладеності:** порахуй рівні рамок/панелей усередині картки (6 рівнів — діагноз сам по собі).
- **Порівняй два входи одного факту.** Якщо та сама сутність має два UI (крок травм у фініші проти сторінки «Що болить») — порядок, групування і термінологія мусять збігатися; розбіжність — знахідка severity вище за косметику, бо два входи радять протилежне.
- Пропозиції формулюй як напрямок, не як рішення — рішення ухвалює власник (крок 6).

### 5. Звіт

Файл: `docs/90-work/audits/YYYY-MM-DD-<module>-deep-audit.md`. Структура, що довела себе:

| Секція | Зміст                                                                              |
| ------ | ---------------------------------------------------------------------------------- |
| §0.x   | Виконано по хвилях (дописується після кожної хвилі фіксів)                         |
| §0.1   | Рішення власника (дописується після мокапу)                                        |
| §1     | Методологія і покриття                                                             |
| §2     | **Що працює** (верифіковано наживо) — без цієї секції звіт читається як хейт       |
| §3     | Проблеми логіки: `L-1…L-n`, пріоритет P1–P3, кожна з file:line і репро             |
| §4     | Дизайн-дослідження проблемного екрана                                              |
| §5     | Візуальні проблеми: `V-1…V-n`                                                      |
| §6     | Знахідки кодового аудиту (після адверсарного пасу)                                 |
| §7     | Пріоритезований план: quick wins ≤ пів дня / середні / великі (= рішення власника) |
| §8     | Як відтворити ключові баги                                                         |

Нумерація `L-*`/`V-*` — стабільні ідентифікатори: ними називаються коміти, PR-и і рішення.

### 6. Продуктові розвилки → мокап порівняння

Для кожного рішення, що міняє продуктову поведінку (не багфікс):

- Побудуй HTML-мокап «зараз проти варіантів» **у справжніх токенах модуля** (з `theme.css` / design-tokens), з телефонними рамками 390px, метриками і таблицею порівняння варіантів.
- Дай свою рекомендацію з обґрунтуванням, включно з варіантом, який НЕ радиш, і чому (на Фізруку: «сесійні мʼязи першими» відхилено, бо звʼязку вправа→суглоб у даних немає за побудовою — підказка була б вгадуванням там, де ціна помилки найвища).
- Рішення власника занеси в §0.1 звіту разом із межею, яку рішення не переходить (у Фізрука: recovery-евристика і модель травми — контракти довіри тіла, не чіпаються).

### 7. Хвилі фіксів

- **Quick wins** (≤ пів дня, без продуктових рішень) — одразу, кожен із тестом, що ловить саме той дефект; у коментарі до тесту — ПРИЧИНА його існування, не переказ дій.
- **Середні/великі** — пакетами паралельним агентам із **неперетинними списками файлів** і явними пастками з розвідки. Комітити агентам заборони: рев'ю, повний гейт і коміт — твої.
- **Рев'ю агентів — не формальність.** На Фізруку саме рев'ю зловило: критерій «підхід зроблено» `вага>0 && повтори>0`, який убивав вправи з власною вагою; перемикач типу, що став недосяжним; кнопку «Менше полів», яка нічого не робила. Дивись diff повністю, не звіт.
- Кожна хвиля: повний гейт (`pnpm check`) → браузерна верифікація зачеплених фло → допис §0.x у звіт → окремий PR із замірами «до/після» у Verification.

## Verification

```bash
SERGEANT_HEAVY_OK=1 pnpm format:check && SERGEANT_HEAVY_OK=1 pnpm lint
SERGEANT_HEAVY_OK=1 pnpm check:typecheck-and-test
SERGEANT_HEAVY_OK=1 pnpm build
# + браузерна верифікація на 390×844 із замірами (не «подивився — ок»)
```

- [ ] Повний гейт зелений (`format:check` → `lint` → `check:typecheck-and-test` → `build`); пре-існуючі червоні тести не з твого графа файлів названі в PR явно з доказом непричетності — не замовчані й не «полагоджені» заглушенням.
- [ ] Кожен фікс має тест, що ловить саме той дефект, і тест перевірено на червоність без фіксу.
- [ ] Кожне зачеплене фло пройдено наживо на 390×844; у PR-Verification — таблиця замірів до/після для кожної візуальної знахідки (не «подивився — ок»).
- [ ] Аудит-док оновлено секцією §0.x «Виконано» з розбіжностями між діагнозом і фактичним коренем.
- [ ] Продуктові розвилки мають мокап і зафіксоване в §0.1 рішення власника — або явно позначені як «чекає на рішення».

## Коли НЕ використовувати цей playbook

- Точковий баг із відомим репро → [`fix-failing-ci.md`](./fix-failing-ci.md) або одразу фікс під `sergeant-bugfix-and-regression`.
- Повне QA всіх модулів паралельно → `sergeant-qa-squad`.
- Рев'ю чужого PR → [`run-squad-review.md`](./run-squad-review.md) / review-checklist.
- Чисто дизайн-система без логіки (токени, типографіка) → design-review без аудит-дока.
