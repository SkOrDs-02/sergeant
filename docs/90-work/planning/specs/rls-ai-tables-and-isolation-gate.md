## Проблема

Авторизація в Sergeant тримається виключно на коді сервера: `requireSession()`
кладе користувача в `req.user`, а далі кожен SQL-запит **вручну** дописує
`WHERE user_id = $1`. База не знає, кому належить рядок, і не заперечує, якщо
фільтр забули. Один такий пропуск уже стріляв: людина змогла перевести кошти на
чужий рахунок через AI-інструмент, root cause - відсутній `WHERE` у хендлері
(описано в [ADR-0012](../../../04-governance/adr/0012-rls-as-authz-boundary.md)
§ ADR-12.1 Consequences).

Вектор із часом виріс. AI-шар видає моделі 78 інструментів, і модель впливає на
аргументи виклику. Поки `user_id` береться з сесії, це безпечно; щойно якийсь
майбутній хендлер візьме його з параметра, prompt-injection стає читанням чужих
даних. Захисту в базі під цим немає жодного: `grep -E "ROW LEVEL SECURITY|CREATE
POLICY"` по `apps/server/src/migrations/` дає нуль збігів.

ADR-0012 описує повну цільову модель (RLS на всіх user-scoped таблицях,
окрема DB-роль, `withUserContext` навколо кожного запиту) і залишається у
статусі `Proposed` саме тому, що нічого з цього не реалізовано. Ця спека бере з
неї найменший корисний зріз.

## Мета

Дві незалежні лінії оборони, обидві в цій спеці.

**A. RLS на серверних таблицях AI-шару.** Postgres сам відсікає чужі рядки в
таблицях, до яких дістає AI-шлях. Забутий `WHERE` у цих таблицях перестає бути
витоком.

**Б. Механічний гейт крос-юзер ізоляції.** Параметризований тест проходить
списком усіх user-scoped роутів і перевіряє, що користувач А не отримує дані
користувача Б. Ловить те, чого RLS у цій спеці не покриває.

Це не альтернативи: правила в базі і тести ловлять різні класи помилок. RLS не
знає про роут, який віддає чужі дані з таблиці без RLS; тест не знає про
запит, якого ніхто не написав у тесті.

## Що з'ясовано розвідкою (не переглядати наново)

**Доменні інструменти виконуються на клієнті.** Виконавці живуть у
[`apps/web/src/core/lib/chatActions/`](../../../../apps/web/src/core/lib/chatActions)
і працюють над локальним SQLite, не над Postgres. Файли в
`apps/server/src/modules/chat/toolDefs/` - це лише **декларації** інструментів
для моделі (JSON-схеми), вони не виконують SQL. Тому «таблиці, до яких дістає
AI-шар» - це власні таблиці сервера, а не вся доменна схема.

**Пул ходить через pgBouncer у transaction-mode.** `apps/server/src/db.ts:47`
маршрутизує рантайм-пул на `DATABASE_URL_POOL`, якщо він заданий. У
transaction-pooling з'єднання не закріплене за запитом, тому **контекст можна
ставити виключно через `SET LOCAL` усередині явної транзакції**. Звичайний
`SET` (без `LOCAL`) протече на чужий запит або загубиться - це не стильова
преференція, а вимога коректності.

**Міграції ходять іншим з'єднанням.** Міграційний runner використовує
`MIGRATE_DATABASE_URL` / `DATABASE_URL` (direct connection), не пул. Див.
коментар `apps/server/src/db.ts:30-45`.

**`ai_memories` партиційована** (`025_ai_memories_pgvector.sql:71-97`, 16
партицій `ai_memories_p00..p15`). Політику вмикати на **батьківській** таблиці:
Postgres поширює її на всі партиції; вмикати на кожній партиції окремо не
потрібно і не робити цього.

**Готовий зразок фонового поллера** - `GdprCleanupPoller`
([`apps/server/src/modules/gdpr/cleanupPoller.ts:71`](../../../../apps/server/src/modules/gdpr/cleanupPoller.ts),
запуск у `apps/server/src/index.ts:222`). Згадано тут, бо він читає
user-scoped дані у фоні і підпадає під bypass-режим нижче.

## Design decisions

### A1. Обсяг: п'ять таблиць, не вся схема

RLS вмикається рівно на серверних таблицях, які читає або пише AI-шлях:

| Таблиця                | Де оголошена                                              | Ключ власника  |
| ---------------------- | --------------------------------------------------------- | -------------- |
| `ai_memories`          | `025_ai_memories_pgvector.sql:71` (партиційована)         | `user_id`      |
| `coach_memory`         | міграція 045                                              | `user_id` (PK) |
| `sergeant_nudge_cache` | знайти міграцію grep-ом `sergeant_nudge_cache`            | `user_id` (PK) |
| `ai_usage_daily`       | `002_ai_usage_daily.sql:2`                                | `subject_key`  |
| чат-таблиці            | знайти grep-ом по `chat_` у `apps/server/src/migrations/` | `user_id`      |

Перед написанням міграції **перевір фактичні імена колонок** у кожній таблиці:
таблиця, у якої немає колонки власника, у цю спеку не входить - винеси її в
розділ «Відкриті хвости» замість того, щоб вигадувати ключ.

`ai_usage_daily` - особливий випадок: її ключ це `subject_key TEXT` у формі
`u:<userId>` або `ip:<addr>`, не FK. Політика для неї порівнює
`subject_key = 'u:' || current_setting('app.user_id')`. Рядки з префіксом `ip:`
не належать жодному користувачеві й під користувацьким контекстом не видимі
взагалі - це прийнятно, їх читає лише квота-логіка під bypass.

Решта схеми (`sync_module_data`, `mono_*`, `finyk_*`, `push_*` тощо) у цю спеку
**не входить**. Її стереже лінія Б.

### A2. Роль не міняємо, вмикаємо FORCE

Сервер і міграції продовжують ходити під тим самим користувачем Postgres. Щоб
правила діяли на власника таблиць, кожна таблиця отримує обидва statements:

```sql
ALTER TABLE <t> ENABLE ROW LEVEL SECURITY;
ALTER TABLE <t> FORCE ROW LEVEL SECURITY;
```

Без `FORCE` власник обходить політики повністю, і вся зміна стає no-op. Нової
DB-ролі, нової змінної оточення і нового секрета в Coolify ця спека не заводить.

### A3. Немає контексту - немає рядків (fail-closed)

Політика читає `current_setting('app.user_id', true)`. Якщо параметр не
встановлено, `current_setting` з другим аргументом `true` повертає `NULL`, і
умова політики хибна - запит бачить нуль рядків.

Це свідомо зроблено голосним: забутий helper ламає функцію одразу й помітно,
а не тихо віддає чужі дані. Ціна - усі місця, що працюють поза сесією
користувача, треба знайти **до** деплою, інакше прод впаде.

### A4. Явний bypass для роботи поза сесією

Другий параметр `app.bypass` знімає обмеження для запитів, які легітимно не
мають користувача:

```sql
CREATE POLICY <t>_owner ON <t>
  USING (
    current_setting('app.bypass', true) = 'on'
    OR user_id = current_setting('app.user_id', true)
  )
  WITH CHECK (
    current_setting('app.bypass', true) = 'on'
    OR user_id = current_setting('app.user_id', true)
  );
```

`WITH CHECK` обов'язковий і не є дублюванням `USING`: без нього `INSERT` і
`UPDATE` можуть записати рядок із чужим `user_id`, який після запису стане
невидимим навіть автору. Обидві частини мусять бути в кожній політиці.

Bypass ставиться тільки в трьох місцях, і кожне має бути назване в PR-описі:

1. **Міграційний runner** - ходить іншим з'єднанням; перевір, чи взагалі
   потрібен bypass, бо DDL політикам не підпорядковується. `SET LOCAL` треба
   лише там, де міграція робить DML над цими таблицями (backfill, purge).
2. **Фонові поллери й таймери**, які обробляють рядки багатьох користувачів:
   `GdprCleanupPoller`, ingest-черга ai-memory, reminder-sweep, будь-що з
   `setInterval` у `apps/server/src/index.ts`.
3. **Адмін- і внутрішні роути** `/api/internal/*`.

### A5. Контекст ставиться явним helper-ом, лише в AI-модулях

Новий helper у `apps/server/src/db.ts` (або сусідньому модулі, якщо `db.ts`
впирається в `max-lines: 600` за Hard Rule #18):

```ts
export async function withUserContext<T>(
  userId: string,
  fn: (client: PoolClient) => Promise<T>,
): Promise<T>;

export async function withBypassContext<T>(
  fn: (client: PoolClient) => Promise<T>,
): Promise<T>;
```

Кожен бере з'єднання з пулу, відкриває транзакцію, ставить `SET LOCAL
app.user_id = $1` (відповідно `SET LOCAL app.bypass = 'on'`), виконує `fn`,
комітить, і в `finally` повертає з'єднання. Транзакція обов'язкова: без неї
`SET LOCAL` не має області дії, а `SET` без `LOCAL` заборонений (див. розвідку
про pgBouncer).

`userId` підставляється **параметром**, не конкатенацією рядка. `SET LOCAL` не
приймає плейсхолдери напряму, тому використовуй `SELECT set_config('app.user_id',
$1, true)` - це параметризована форма з тією ж семантикою.

Глобальної обгортки над усіма запитами в `db.ts` ця спека **не робить**:
вебхуки Monobank і LiqPay та метрики не мають сесії, і централізований варіант
вимагав би окремого режиму для них по всьому коду.

Переписуються на helper лише виклики, що торкаються п'яти таблиць з A1:
`apps/server/src/modules/ai-memory/*`, `apps/server/src/modules/chat/coach.ts`,
`apps/server/src/modules/chat/aiQuota.ts`, `apps/server/src/lib/reminders/nudge.ts`,
`apps/server/src/lib/strategicGoals.ts`. Перед правкою перевір список grep-ом -
він міг змінитись.

### A6. Реплік-пул

`apps/server/src/dbReplica.ts` тримає окремий пул для читань з репліки. Якщо
через нього йде хоч один запит до таблиць з A1, helper мусить уміти працювати і
з ним, інакше ці читання повернуть нуль рядків. Перевір grep-ом; якщо жодного
такого запиту немає, зафіксуй це рядком у PR-описі, а код не ускладнюй.

### Б1. Один параметризований тест, список роутів у коді

Гейт живе одним файлом (запропонована назва
`apps/server/src/http/crossUserIsolation.test.ts`) і містить масив описів
user-scoped роутів: метод, шлях, спосіб створити рядок користувачеві Б,
очікування для користувача А.

Тест для кожного запису: створює двох користувачів, кладе дані користувачеві Б,
робить запит від імені А і вимагає, щоб відповідь не містила ідентифікаторів Б
(порожній список, `404` або `403` - усі три прийнятні, `200` з чужим вмістом -
ні).

Обсяг - **усі** user-scoped роути, не лише AI-таблиці. Джерело списку - наявні
реєстри роутів: `apps/server/src/routes/apiV1.test.ts` і
`apps/server/src/contracts/provider.test.ts` уже перелічують роути, звір свій
масив із ними.

### Б2. Список не має права застаріти

Тест перевіряє повноту власного масиву: збирає фактичні роути з Express-роутера
і падає, якщо якийсь user-scoped роут не описаний у масиві. Роут, який свідомо
не має користувацького скоупу (health, auth, вебхуки), заноситься в явний
allowlist із коментарем-причиною.

Без цієї перевірки масив тихо відстає від коду, і гейт вироджується в
декорацію.

### Б3. Один прогін, не два набори

Тести використовують наявний тестовий стенд серверних інтеграційних тестів
(подивись, як це роблять `apps/server/src/modules/me/dataRights.integration.test.ts`
і `stripeWebhook.integration.test.ts`), і запускаються звичайним
`pnpm --filter @sergeant/server test`. Нового CI-джоба ця спека не заводить.

## Порядок робіт

Стадії окремими комітами, бажано окремими PR-ами.

1. **Б повністю.** Гейт крос-юзер ізоляції на поточному коді, без RLS. Він має
   бути зеленим ДО того, як з'явиться RLS: інакше при падінні після ввімкнення
   політик неможливо відрізнити «RLS зламав легітимний доступ» від «тут завжди
   був витік».
2. **A5 helper + переписані виклики**, ще без політик. Поведінка не змінюється
   (`SET LOCAL` без політик ні на що не впливає), тож стадія безпечна і її
   можна злити окремо.
3. **A4 bypass у фонових задачах і внутрішніх роутах.** Теж no-op без політик.
4. **A1-A3 міграція з політиками.** Наступний вільний номер після
   `134_fizruk_item_chosen_variant.sql` - перевір `ls apps/server/src/migrations/`
   на момент роботи. Обов'язковий парний `.down.sql`, який знімає політики й
   вимикає RLS (Hard Rule #4).

Порядок не переставляти: стадія 4 - єдина, що змінює рантайм-поведінку, і на
момент її мержу все інше має бути вже в `main` і зеленим.

## Поза скоупом

- RLS на решті user-scoped таблиць (`sync_module_data`, `mono_*`, доменні
  таблиці модулів). Лишається app-enforced, стережеться лінією Б.
- Окрема DB-роль без BYPASSRLS і `service_role` з ADR-0012 § ADR-12.2.
- Column-level security, маскування PII у SELECT-ах.
- Feature-flag на поступове ввімкнення політик модуль за модулем (ADR-12.3):
  п'ять таблиць - надто мала площа, щоб виправдати прапорець.
- Зміна статусу ADR-0012. Це окремий PR **після** мержу цієї роботи, і він
  переводить не весь ADR, а фіксує, що ADR-12.2 реалізовано частково.
- Клієнтський SQLite. Там дані одного користувача за побудовою.

## Верифікація

Кожен пункт має давати доказ у PR-описі: команда і її результат.

**1. Тести й типи, повний прогін.**

```bash
pnpm check
```

Очікування: зелено. Скорочений `--filter` тут не годиться - контрактні тести
`packages/api-client` і серверні інтеграційні лежать у різних воркспейсах.

**2. Гейт ізоляції ловить регресію (доказ, що він не декоративний).**

Тимчасово прибери `WHERE user_id = $1` з одного роуту, наприклад у
`apps/server/src/modules/ai-memory/listRoute.ts:69`, і запусти:

```bash
pnpm --filter @sergeant/server test crossUserIsolation
```

Очікування: тест **падає** з іменем саме цього роуту. Поверни `WHERE`, прогони
ще раз - зелено. Обидва прогони в PR-опис.

**3. Політики справді ввімкнені на всіх п'яти таблицях.**

Після прогону міграцій на локальній базі (`pnpm dev:db`):

```bash
psql "$DATABASE_URL" -c "SELECT relname, relrowsecurity, relforcerowsecurity FROM pg_class WHERE relname IN ('ai_memories','coach_memory','sergeant_nudge_cache','ai_usage_daily') ORDER BY relname;"
```

Очікування: для кожного рядка `relrowsecurity = t` **і** `relforcerowsecurity = t`.
Якщо друга колонка `f`, політика не діє на власника, і вся зміна безрезультатна.

**4. Fail-closed працює.**

```bash
psql "$DATABASE_URL" -c "SELECT count(*) FROM ai_memories;"
```

Очікування: `0` навіть за наявних рядків у таблиці, бо `psql` не ставить
`app.user_id`. Ненульове значення означає, що `FORCE` не спрацював, або
політика написана fail-open.

**5. Контекст справді розділяє користувачів.**

```bash
psql "$DATABASE_URL" -c "BEGIN; SELECT set_config('app.user_id','<id-A>',true); SELECT count(*) FROM ai_memories; ROLLBACK;"
psql "$DATABASE_URL" -c "BEGIN; SELECT set_config('app.user_id','<id-Б>',true); SELECT count(*) FROM ai_memories; ROLLBACK;"
```

Очікування: два різні числа, кожне збігається з реальною кількістю рядків
відповідного користувача.

**6. Міграція відкочується.**

```bash
pnpm lint:migrations
```

Плюс ручний прогін `.down.sql` на локальній базі: після відкоту крок 3 має
показати `f` в обох колонках, а крок 4 - ненульовий `count`.

**7. Живий прохід застосунком.** Підняти `pnpm dev:server` + `pnpm dev:web`,
залогінитись, відкрити чат, надіслати повідомлення, відкрити сторінку памʼяті
AI. Очікування: відповіді приходять, памʼять показує записи. Це ловить
найімовірнішу помилку стадії 4 - забутий helper на живому шляху, який під
fail-closed дає порожній екран замість помилки.

## Ризики

- **Найімовірніший провал: пропущений виклик поза helper-ом.** Симптом не
  виняток, а порожня відповідь. Тому пункт 7 верифікації обов'язковий і
  ручний: автотести можуть не покривати конкретний шлях.
- **Партиції `ai_memories`.** Якщо політику випадково повісити на партиції
  замість батьківської таблиці, поведінка буде схожою, але нові партиції
  залишаться без захисту. Перевіряй пунктом 3 саме `ai_memories`.
- **pgBouncer.** Якщо `SET LOCAL` опиниться поза транзакцією, контекст
  протече між запитами різних користувачів - це гірше за початковий стан.
