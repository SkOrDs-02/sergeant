## Проблема

Готівкові та «чужокарткові» покупки не потрапляють у finyk автоматично — їх
треба вбивати руками через ManualExpenseSheet. А для карткових покупок
mono-webhook дає лише одну суму «Сільпо −847.50» без розшифровки, що саме
куплено. Чек з магазину — єдиний артефакт, який містить і суму, і позиції,
але сьогодні finyk його ніяк не вміє прийняти. Спека
[silpo-mcp-integration.md](./silpo-mcp-integration.md) закриває це лише для
Сільпо; ця спека — для чеків з **будь-якого** магазину.

Друга половина проблеми — **масове ведення** (Фаза 2 нижче). Одиночний скан
закриває «щойно купив», але не закриває backfill: стос чеків за тиждень,
період без підключеного банку (готівка, чужа картка, банк без
API-інтеграції), історія при онбордингу. Минуле сьогодні закривають лише
mono-webhook + 31-денний backfill і Privat merchant API; для решти банків і
готівки єдиний вхід — ManualExpenseSheet, по одній транзакції за раз.
Артефакти, які в користувача **вже є** — скріншот списку транзакцій у
банк-апці та виписка файлом (CSV/XLS/PDF) — finyk не приймає ніяк.
_(Станом на 2026-08-25 закрито для скрінів, CSV, XLSX і HTML-таблиць під
іменем `.xls`; PDF лишається за гейтом § Фаза 2в.)_

## Мета

Користувач у web/PWA натискає «Сканувати чек», наводить камеру на QR
фіскального чека (або фоткає чек без QR) — і за кілька секунд бачить
чернетку витрати з магазином, сумою, датою і списком позицій. Після
підтвердження: якщо знайдено відповідну mono-транзакцію — чек лінкується до
неї (без дубля), якщо ні — створюється manual expense. Транзакція з чеком
розгортається у список покупок.

Фаза 2 розширює це до масового ведення: користувач вантажить **кілька фото
чеків, скрін екрана банкінгу або файл виписки** — і отримує таблицю
draft-транзакцій з дедуплікацією проти mono/Privat і попередніх імпортів,
масовим редагуванням категорій і одним «Зберегти» на всі.

## Рішення дизайну

Зафіксовані founder-ом на інтервʼю 2026-08-01:

- **QR first, vision fallback — обидва в v1.** Основний шлях: QR фіскального
  чека → офіційний API ДПС → точні структуровані позиції, $0/чек. Fallback
  (нема QR, ДПС лежить/лаг, нефіскальний чек): фото → vision-LLM.
  Відкинуто «тільки vision» (дорожче, точність цін не гарантована) і
  «тільки QR» (базари, закордон, пошкоджені чеки випадають).
- **Vision через OpenRouter + `google/gemini-2.5-flash-lite`.** OpenRouter
  уже вшитий в apps/server (env `OPENROUTER_API_KEY`, per-домен провайдери),
  Flash-Lite — уже дефолт для nutrition/mono; ціна ~$0.0004/чек. Відкинуто
  Anthropic-direct (Haiku ~10× дорожчий, хоч і теж копійки) — але патерн
  валідації зображення береться з `analyze-photo.ts`.
- **Токен ДПС — один, серверний, founder-а.** API публічної частини
  (`/ws/api_public/rro/chkAll`) авторизується персональним токеном з
  Електронного кабінету (вкладка «Токени публічної частини», вхід з КЕП).
  Дані чека публічні, тож користувачам свої кабінети не потрібні. Ліміт
  1000 запитів/добу на токен; кожен чек тягнеться один раз і зберігається
  (природний кеш). Відкинуто per-user токени — зайвий онбординг-барʼєр.
- **Поверхня v1 — web/PWA.** Кнопка «Сканувати чек» поруч із «+ Витрата»
  на сторінці транзакцій finyk. Камера через getUserMedia + zxing
  (переюз патерну `useBarcodeScanner.ts` з nutrition, QR-режим) + file
  upload як альтернатива. Mobile (Expo) — пізніше, патерн капчура вже є в
  `pickImageJpegForNutritionApi.ts`. Відкинуто «mobile first» — акцент
  продукту зараз на web/PWA.
- **Позиції зберігаються + розгортка.** Транзакція з чеком розгортається у
  список покупок. БЕЗ пер-позиційної категоризації/TxSplit у v1 (це етапи
  C/D silpo-спеки). Відкинуто «лише сума+магазин» — парсинг покупок і є
  головна цінність.
- **Дедуп — matcher як у silpo-спеці.** Чек спершу шукає mono-транзакцію
  (сума + дата ±1 доба Kyiv; `mono_transaction.receipt_id` — сильний лінк).
  Знайшов → лінк без нової витрати. Не знайшов → manual expense.
  Unmatched-чек — першокласний стан, не помилка (платник ≠ покупець,
  готівка, інший банк). Matcher **ніколи не видаляє і не зливає** дані.
- **Review-екран обовʼязковий.** Патерн усіх конкурентів (Expensify, Zoho,
  Easy Expense): скан → редагована чернетка → підтвердження. Нічого не
  зберігається без явного «Зберегти» користувача.

## Архітектура

### Флоу v1

```
[Кнопка «Сканувати чек»]
  → камера getUserMedia + zxing (QR-режим) АБО file upload
  ├─ QR прочитано → клієнт парсить URL виду
  │    https://cabinet.tax.gov.ua/cashregs/check?id=..&date=..&time=..&fn=..&sm=..
  │    → POST /api/finyk/receipts/lookup {fn, id, date, time, sm}
  │    → сервер GET https://cabinet.tax.gov.ua/ws/api_public/rro/chkAll
  │         ?id=..&fn=..&date=..&type=1 (оригінальний XML) + token
  │    → парсинг XML: магазин (назва, адреса, ЄДРПОУ), дата/час, сума,
  │      позиції {назва, кількість, ціна, сума}
  ├─ QR нема / не читається / ДПС недоступна → користувачу пропонується фото
  │    → POST /api/finyk/receipts/analyze {image_base64, mime_type}
  │    → валідація magic-bytes (переюз validateImageBase64, 5MB cap)
  │    → OpenRouter chat/completions, model gemini-2.5-flash-lite,
  │      image_url (data URI) + промпт «поверни JSON {store, date, total,
  │      items[]}» (укр. системний промпт, патерн analyze-photo.ts)
  └─ Обидва шляхи → response draft → review-екран (магазин, сума, дата,
       категорія (одна на чек), позиції — усе редаговане)
     → «Зберегти» → POST /api/finyk/receipts
       → matcher: mono-транзакція (сума ±0, дата ±1 доба Kyiv)?
         ├─ так → створити receipt + items + tx_receipt_link (mono)
         └─ ні  → створити receipt + items + manual expense + link (manual)
```

- QR-скан → ДПС-лаг: чек може зʼявитись у реєстрі не миттєво. Відповідь
  404/порожня від chkAll → повідомлення «Чек ще не зʼявився в реєстрі ДПС —
  спробуй за кілька хвилин або сфоткай чек» (обидві опції на екрані).
- vision-результат позначається `source: 'vision'` і на review-екрані
  показується бейдж «розпізнано з фото — перевір суми».

### Модель даних

Узагальнення таблиць silpo-спеки (координація: якщо silpo-етап уже створив
`silpo_receipts` — розширити ту міграцію, НЕ створювати паралельну сімʼю;
якщо ні — ця спека створює спільні таблиці, а silpo пише в них же):

- `receipts` — id, user_id, source (`dps` | `vision` | `silpo`),
  fiscal_num (nullable), store_name, store_tax_id (nullable),
  purchased_at (timestamptz), total_kopiykas (bigint → **coerce до number
  у серіалізаторі**, Hard Rule #1), raw_payload JSONB (XML/JSON з джерела).
  Unique: `(user_id, source, fiscal_num)` де fiscal_num не null —
  повторний скан того самого чека = ідемпотентний no-op.
- `receipt_items` — id, receipt_id FK, position, name, qty (numeric),
  price_kopiykas, sum_kopiykas.
- `finyk_tx_receipt_links` — receipt_id, tx_kind (`mono` | `manual`),
  tx_ref (mono_tx_id або ext_id manual expense), unique на receipt_id.

Міграція — наступний вільний номер у `apps/server/src/migrations/`,
послідовно, без пропусків (Hard Rule #4).

### API-контракт

Три ендпоінти в `apps/server/src/routes/finyk.ts` + модуль
`apps/server/src/modules/finyk/receipts/`:

- `POST /api/finyk/receipts/lookup` — {fn, id, date, time, sm} → draft
  (без запису в БД).
- `POST /api/finyk/receipts/analyze` — {image_base64, mime_type} → draft
  (без запису в БД).
- `POST /api/finyk/receipts` — draft (відредагований) → зберігає receipt +
  items + link/expense, повертає створене.
- `GET /api/finyk/receipts/:id` — чек з позиціями для розгортки транзакції.

Суми через API — **kopiykas як number** (домен-інваріант). Типи
відповідей дзеркаляться у `packages/api-client` + `.contract.test.ts`
(Hard Rule #3, триплет рухається разом).

### Web UI

- `apps/web/src/modules/finyk/components/ReceiptScanSheet.tsx` — сканер
  (zxing QR через переюз/узагальнення `useBarcodeScanner`-патерну; кнопка
  «Завантажити фото»; стани: сканую / lookup / analyze / review / помилка).
- Review-екран: редаговані поля, категорія — дропдаун (рішення founder-а
  2026-07-24: категорії — дропдаун, не чипи), позиції списком.
- Розгортка: у списку транзакцій рядок з привʼязаним чеком отримує
  індикатор і expand до `receipt_items`.
- RQ-ключі — ТІЛЬКИ через `finykKeys` у
  `apps/web/src/shared/lib/api/queryKeys.ts` (Hard Rule #2). Нові ключі:
  `finykKeys.receipt(id)`, інвалідація транзакційних ключів після save.
- Touch targets ≥44px, тексти укр. за style-guide
  (`docs/01-product/copy/style-guide.uk.md`).

### Env

- `DPS_API_TOKEN` (новий) — Coolify env; без нього lookup-шлях відповідає
  503 з повідомленням, vision-шлях працює.
- OpenRouter — наявні `OPENROUTER_API_KEY`; нова пара
  `LLM_RECEIPT_PROVIDER` (default `openrouter`) +
  `OPENROUTER_RECEIPT_MODEL` (default `google/gemini-2.5-flash-lite`),
  за патерном інших доменів у `env.ts`.
- Логи: НЕ логувати image_base64 і сирий XML з ПІБ/адресами понад
  redaction-політику pino (Hard Rule #21).

5. Дедуп: скан чека за карткову покупку з mono-транзакцією в базі →

## Ризики та відкриті питання

- **[ЗАКРИТО 2026-08-18] Доступ до реєстру ДПС — законсервовано на час
  воєнного стану** (рішення founder-а). Токен було згенеровано (публічна
  частина ЕК; діяв би до 18.11.2026; 1000 запитів/добу). Live-смоук:
  формат запиту виправлено за офіційною докою
  `cabinet.tax.gov.ua/help/api-registers.html` (`date` у форматі
  `YYYY-MM-DD HH:mm:ss`, відповідь — JSON-конверт з base64-XML у полі
  `check`), але реєстр відповідає 400 «На період дії воєнного стану
  обмежено доступ до публічних електронних реєстрів» — незалежно від
  токена (без токена і з битим те саме). Founder підтвердив: функція на
  час війни недоступна — гілку законсервовано до відкриття реєстру.
  Код готовий і чекає: `DPS_ACCESS_RESTRICTED`/`DPS_TOKEN_MISSING` → UX
  веде на фото; `DPS_API_TOKEN` в env не ставимо (протермінований токен
  просто перегенерувати, коли реєстр відкриють, і зробити live-смоук
  першим чеком — leaf-теги `dpsXml.ts` досі не бачили живого XML).
  Vision-шлях від цього не залежить і несе бету.
- XML-схема чека РРО vs ПРРО може відрізнятись — закривається фікстурами
  з різних магазинів на кроці smoke-тесту.
- Лаг появи чека в реєстрі ДПС — UX уже передбачає «спробуй пізніше або
  сфоткай»; якщо лаг систематично >хвилин — підняти пріоритет
  vision-шляху в UI.
- Ліміт 1000/добу спільний на всіх користувачів — моніторити після бети;
  мітигація: другий токен, черга, кеш уже є by design.
- zxing і `BarcodeDetector` читають QR добре, але живий чек буває мʼятий —
  якщо скан-UX слабкий, розглянути `jsQR`/збільшення роздільності
  getUserMedia (рішення на click-through, не зараз).
- Приватність: чек містить адресу магазину і назви покупок — покриття
  формулюванням приватності узгодити з відкритим гейтом silpo-спеки
  (finyk §6.4), однією редакцією на обидві фічі.

### Карта джерел транзакцій (де місце Фази 2)

| Джерело             | Канал                                     | Покриття                         | Статус             |
| ------------------- | ----------------------------------------- | -------------------------------- | ------------------ |
| Monobank live       | webhook                                   | з моменту підключення            | працює             |
| Monobank історія    | backfill API (31 день, paced)             | останній місяць                  | працює             |
| PrivatBank          | merchant API `/statements/transactions`   | виписки по токену                | працює             |
| Ручний ввід         | ManualExpenseSheet                        | будь-що, по одній                | працює             |
| Чек (одиночний)     | QR/ДПС + vision                           | будь-який магазин                | **v1 цієї спеки**  |
| **Чеки пачкою**     | кілька фото за раз                        | стос чеків                       | **Фаза 2а**        |
| **Скрін банкінгу**  | скріншот списку транзакцій → vision       | будь-який банк без API           | **Фаза 2а**        |
| **Виписка CSV/XLS** | файл → структурний парсер + column-mapper | будь-який банк, будь-яка глибина | **Фаза 2б**        |
| Виписка PDF         | text-layer → vision fallback              | банки, що дають лише PDF         | гейт (§ питання 3) |

Файлові шляхи Фази 2 — не конкурент API-інтеграціям, а покриття дірок:
банки без інтеграції, глибина понад mono-backfill, готівкові періоди,
користувачі, які не хочуть віддавати банківські токени.

### Флоу Фази 2

> **[ЗМІНЕНО 2026-08-18, бета-фідбек №2]** Точки входу розведені за
> змістом, а не за кількістю файлів: **чеки (одне ЧИ кілька фото)** живуть
> у «Сканувати чек» (`ReceiptScanSheet`, пікер `multiple`: 1 файл →
> одиничний review, 2+ → «Чеки пачкою»), а «Додати документи»
> (`BulkImportSheet`) лишився банківським докам — скрін банкінгу + CSV.
> Схема нижче — історичний дизайн однієї спільної точки входу.
>
> **[ДОДАНО 2026-08-18, бета-фідбек №3]** Глибина пачки: «Редагувати» на
> рядку відкриває повний review-екран чека (позиції включно, той самий
> `ReceiptReviewForm`); порожній драфт («схоже, не чек») — бейдж +
> авто-виключення зі збереження, авто-повернення після заповнення полів.
>
> **[ДОДАНО 2026-08-18, бета-фідбек №4 — «сітка 2» дедуп-превʼю]** Тір-2
> ключ хешує опис і не ловить повторний СКРІН: vision читає описи
> недетерміновано, два прогони на тому самому зображенні дають різні хеші
> (реальний кейс тестерки — той самий скрін двічі поспіль задвоїв рядки).
> Тому прев'ю (`statement/preview` і `screenshot/analyze`) тепер звіряє
> кожен рядок з уже збереженими `finyk_manual_expenses` за трійкою
> дата+сума+напрям, ігноруючи опис (`duplicateDetect.ts`,
> count-обмеження на однакові покупки в один день), і ставить м'яку мітку
> `duplicateLikely` — бейдж «схоже, вже є» + знята галочка у bulk-review,
> рішення за людиною. Mono-матч лишається на commit (tier 1), як і був.
>
> **[ДОДАНО 2026-08-18, бета-фідбек №5 — видиме очікування]** «Додати
> документи» не мали стадії очікування взагалі: аркуш стояв на кнопках
> вибору файлу всі 5–20 секунд стиснення + vision, і тестерка читала це
> як завислий екран («є пауза і не зрозуміло це триває процес чи фрозен
> скрін»). Тепер обидва аркуші мають спільний `ScanStatus` (спінер +
> назва фази + пояснення затримки після 7 секунд), а стадія `processing`
> вмикається синхронно з вибором файлу — до першого `await`, бо саме
> стиснення фото і було невидимою частиною паузи. Фази називають реальні
> кроки («Готую фото…» → «Розпізнаю транзакції…»/«Розпізнаю чек…» →
> «Шукаю чек у ДПС…»); фейкового прогрес-бару свідомо нема — ні vision,
> ні ДПС відсотка виконання не віддають. Зміна тексту тут не косметика:
> `Spinner` крутиться під `motion-safe:`, тож під `prefers-reduced-motion`
> рухомий текст — єдиний доказ, що процес живий.

```
[«Додати документи» (та сама точка входу, що «Сканувати чек»)]
  → dropzone: до N зображень (фото чеків / скріни) або 1 файл виписки
  → класифікація: MIME/розширення ділить «зображення vs файл виписки»;
    тип зображення (чек vs скрін банкінгу) повертає сам vision-промпт
    першим полем відповіді {doc_type} — окремого класифікатора немає
  ├─ зображення-чек:
  │    клієнт спершу пробує zxing-decode QR прямо з фото → є QR →
  │    v1 lookup-шлях (ДПС, $0); нема/не читається → v1 analyze-шлях
  │    (vision). Кожен чек = свій draft із позиціями.
  ├─ зображення-скрін банкінгу:
  │    → vision → {doc_type: 'bank_screenshot', bank?, transactions[
  │      {date, time?, amount_kopiykas, direction, description}]}
  │    → 1..N draft-рядків БЕЗ позицій
  └─ CSV/XLS:
       → детект кодування/роздільника (спільний шар ініціативи 0022)
       → автопрофіль відомого банку (mono-CSV, Privat24-XLS) АБО ручний
         column-mapper «де дата / сума / опис» з preview перших рядків
  → усі шляхи → bulk-review: одна таблиця draft-рядків
  → per row: matcher v1 (mono/Privat) + дедуп (нижче) → статус рядка
  → «Зберегти вибране» → create/link → підсумок {нових, лінків, пропущено}
```

### Рішення дизайну Фази 2

- **Один конвеєр з ініціативою 0022, а не паралельний.** Ініціатива
  [0022-import-from-external-trackers](../../initiatives/0022-import-from-external-trackers.md)
  вже планує спільний upload-шар (multipart, ZIP, детект кодування і
  роздільника, журнал `import_batches`) і Фазу 3 «фінанси через
  column-mapper». Ця спека **конкретизує фінансову гілку** 0022
  (банківські виписки/скріни + звʼязка з чеками і mono-дедупом) і переюзає
  спільний шар — вона НЕ створює другий імпорт-конвеєр. Хто перший дійде
  до імплементації, той закладає спільний шар; другий у нього вʼїжджає
  (той самий принцип, що з таблицями silpo у v1).
- **Batch-чеки = N × v1, без нової чекової механіки.** Кожне фото проходить
  наявний lookup/analyze-шлях; нового — лише черга обробки (паралелізм ≤2,
  реком.), ліміт зображень на батч (реком. 10; 5MB/файл — наявний
  validateImageBase64-патерн) і зведення draft-ів у bulk-review. Для
  batch-QR ДПС-ліміт 1000/добу спільний — додається per-user добовий cap
  на lookup (реком. 50) і черга.
- **Скрін банкінгу — це транзакції без позицій, НЕ чек.** Результат
  vision — рядки {дата, сума, напрямок, опис/мерчант}; `receipt_items` не
  створюються. Промпт зобовʼязаний: ігнорувати рядки балансу («Баланс
  після», «Доступно»), розрізняти надходження/витрату (знак, колір,
  стрілка), повертати `confidence` на рядок; суми — kopiykas. На review —
  той самий v1-бейдж «розпізнано з фото — перевір суми».
- **Виписки: спершу структурні формати (CSV/XLS), PDF — за гейтом.** mono
  віддає CSV, Privat24 — XLSX/CSV; це покриває найбільші банки «дешевим»
  шляхом ($0, без LLM). PDF-виписки (Ощад, частина закордонних) — дорожчий
  і хиткіший шлях: text-layer, а якщо його нема (скан) — vision
  посторінково; вмикається окремим рішенням після живих CSV/XLS
  (§ питання 3).
- **Автопрофілі + column-mapper.** Для відомих форматів (mono-CSV,
  Privat24-XLS) — вшиті мапи колонок, користувач нічого не мапить.
  _Обидва профілі звірені з живими файлами (mono 2026-08-18, Privat24
  2026-08-25); реконструкція колонок Privat24 виявилась хибною і
  виправлена за фактом — деталі в 0022 § Відкриті рішення._
  Невідомий формат → ручний mapper (0022 Фаза 3) з preview перших 5
  рядків. Обовʼязково покрити: дати `DD.MM.YYYY` і ISO, двоколонкові
  дебет/кредит-виписки (mapper має роль «колонка витрат»), суми з комою
  та пробілами-роздільниками тисяч.
- **Дедуп — триярусний, статус видно per row.** (1) _Проти
  банк-API-даних:_ matcher v1 (сума + дата ±1 доба Kyiv) проти mono/Privat
  транзакцій — рядок виписки того ж банку/періоду стає лінком, не дублем.
  (2) _Між імпортами:_ детермінований id рядка від семантичного row-key
  (рішення founder-а 2026-08-04 у 0022 § Відкриті рішення №2:
  `source + session_identity (день+рахунок) + normalized_values +
occurrence_index`) — повторний upload того самого файлу чи періоду =
  upsert-no-op, а два однакові платежі в один день лишаються двома
  рядками. (3) _Чеки:_ наявний unique `(user_id, source, fiscal_num)`.
  Bulk-review показує статус рядка: «нова» / «= mono-транзакція → лінк» /
  «вже імпортовано → пропущено»; два останні зняті з вибору за
  замовчуванням.
- **Ідемпотентність через наявний sync-механізм, без нової таблиці
  рядків.** finyk local-first: manual-рядки живуть як per-row blob
  (`id` + `data_json`, LWW) і їдуть через `applyFinykPerRowBlob`.
  Імпортований рядок = manual expense з детермінованим
  `id = imp1:<sha256(row-key)>` → create робиться `ON CONFLICT`-no-op, а
  клієнт підтягує нові рядки тим самим sync-pull шляхом, яким v1
  доставляє чекові manual expenses. Окремої таблиці «рядків виписки» не
  зʼявляється.
- **Журнал батчів + undo.** `import_batches` (0022): `source`, `file_hash`
  (журнальний атрибут, не ключ дедуплікації), лічильники, `status` +
  **`created_row_ids JSONB`** — список створених id. «Скасувати імпорт» =
  tombstone усіх рядків батчу наявною delete-механікою sync. Без цього
  списку батч не відкотити, тому він обовʼязковий.
- **Надходження імпортуються, але зняті з вибору за замовчуванням
  (реком.).** Виписка/скрін містить і надходження — finyk має «Ручне
  надходження», тож `direction` зберігаємо. Але перекази між власними
  рахунками — головне джерело шуму масового імпорту, тому income-рядки в
  bulk-review за замовчуванням ✗ і вмикаються чекбоксом. Ратифіковано
  founder-ом 2026-08-18 (§ питання 2) разом із follow-up-ом: рядки з
  `transferLikely`-розміткою (перекази на власну банку) так само зняті з
  вибору за замовчуванням.
- **Оригінали файлів не зберігаємо (реком.).** Як у v1 (фото чека не
  зберігається — лише parsed `raw_payload`): скрін/виписка парситься, у БД
  лишаються тільки поля рядків; IBAN, номери карток і баланси відкидаються
  на парсингу і не потрапляють ні в БД, ні в логи (Hard Rule #21). Це
  водночас privacy-властивість і відповідь на «чи потрібне сховище
  файлів» — не потрібне.
- **Мультивалютні рядки у Фазі 2 пропускаються.** UAH-рядки імпортуються;
  не-UAH — статус «пропущено: валюта» з лічильником у підсумку. Важливо,
  що́ тут «не-UAH рядок»: це рядок, чия сума ведеться у валюті рахунку, —
  Privat24-CSV рахунку в EUR/USD чи рядок скріна з €/$ біля суми. Валютна
  покупка з ГРИВНЕВОЇ картки (Netflix у EUR, підписка в USD) — НЕ такий
  рядок: банк сам конвертує, mono-CSV несе суму в колонці «Сума в валюті
  картки (UAH)», і саме її бере парсер — така операція входить в імпорт у
  гривневому еквіваленті (перевірено реальною mono-випискою 2026-08-18:
  255/255 рядків, 0 пропущених, валютні підписки увійшли в грн). Валютна
  нормалізація — відкрите рішення №4 ініціативи 0022; тут його не
  дублюємо і не випереджаємо.

### API-контракт Фази 2

Сусідній модуль `apps/server/src/modules/finyk/import/` (або спільний
`modules/import/` — вирішується при імплементації разом з 0022, § межі
вище):

- `POST /api/finyk/import/images` — multipart, 1..N зображень → масив
  draft-ів (чеки з позиціями і скрін-рядки впереміш), без запису в БД.
  Одиночний v1 `receipts/analyze` (base64) лишається як є.
- `POST /api/finyk/import/statement/preview` — multipart, 1 файл CSV/XLS
  (+ опційний mapping) → `{profile | needs_mapping, rows[],
skipped[{reason}]}`, без запису в БД.
- `POST /api/finyk/import/commit` — вибрані/відредаговані draft-рядки →
  триярусний дедуп + matcher → створення (receipts / manual expenses /
  лінки) → `{batch_id, created, linked, skipped}`.
- `GET /api/finyk/import/batches/:id` — статус/підсумок батчу.
- `DELETE /api/finyk/import/batches/:id` — undo батчу (tombstone рядків).

Суми скрізь — kopiykas як number (Hard Rule #1); типи дзеркаляться у
`packages/api-client` + `.contract.test.ts` (Hard Rule #3). RQ-ключі —
тільки через централізовану фабрику (Hard Rule #2); чи це
`finykKeys.import*`, чи спільний з 0022 `importKeys` — вирішити при
імплементації, в одному місці.

### Bulk-review UI

- Точка входу v1 (`ReceiptScanSheet`) виростає у «Додати документи» або
  отримує сусідній `BulkImportSheet` (рішення на імплементації): dropzone →
  прогрес по файлах → таблиця рядків.
- Таблиця: чекбокс (дефолт: нові ✓; дублі, лінки та income ✗), дата, опис,
  сума, категорія (дропдаун per row — рішення founder-а 2026-07-24:
  категорії — дропдаун) + масове «категорія для вибраних», статус-бейдж.
  Чеки в таблиці розгортаються в позиції (v1-патерн).
- Зламаний рядок не блокує решту: статус «не розпізнано», виключений з
  вибору, батч зберігається без нього.
- Touch targets ≥44px; тексти укр. за
  [style-guide](../../../01-product/copy/style-guide.uk.md).

### Вартість Фази 2 (довідково)

CSV/XLS — $0. Скрін банкінгу ≈ той самий порядок, що чек-vision

batch-QR — див. рішення про per-user cap вище.

### Черговість поставки

1. **Фаза 2а — зображення пачкою:** batch-чеки + скріни банкінгу.

3. **Фаза 2в — PDF-виписки:** лише після зняття гейта (§ питання 3).

### Верифікація Фази 2 (обовʼязково)

1. `pnpm check` зелений; unit: парсер профілів на фікстурах реальних
   виписок (mono CSV, Privat24 XLS, один «невідомий» CSV через mapper);
   контракт-тест схеми vision-відповіді для скрінів; детермінізм row-key
   (той самий період з двох різних файлів → той самий набір id).
2. Дедуп e2e: (а) виписка періоду, що перетинається з mono-даними → лінки
   і пропуски, 0 дублів у списку транзакцій; (б) повторний upload того
   самого файлу → 0 нових рядків; (в) два однакові платежі в один день →
   2 рядки, не 1.
3. Click-through: 10 фото чеків одним батчем → таблиця → масова категорія →
   зберегти → всі у списку транзакцій; скрін mono-екрана → рядки без
   рядка-балансу; undo батчу прибирає всі його рядки.
4. Privacy-перевірка: у БД і логах немає IBAN/PAN/балансів із фікстурної
   виписки (grep дампу і логів).
5. UI — скриншот bulk-review у PR.

### Ризики Фази 2

- **Vision плутає баланс із сумою на скрінах** — рядок «Баланс: 12 345,67»
  стає транзакцією. Мітигація: промпт явно виключає баланс, фікстурні
  скріни 2–3 банків у контракт-тесті, `confidence` + бейдж перевірки.
- **Надто грубий row-key склеює легітимні однакові платежі** («дві кави по
  85 грн в один день»). Мітигація: `occurrence_index` у ключі (рішення 0022) + обовʼязковий тест-кейс (в) у верифікації.
- **Формати виписок дрейфують** — банки міняють колонки без попередження.
  Мітигація: автопрофілі версіонуються, фікстури ловлять дрейф, fallback
  завжди є (ручний mapper).
- **Великі виписки** (роки історії, 10k+ рядків) кладуть памʼять.
  Мітигація: стрімінговий парсинг, ліміт розміру, батч-запис чанками
  (патерн mono-backfill).
- **Приватність файлів.** Виписка — найчутливіший документ у продукті
  (ПІБ, IBAN, повна історія витрат). Мітигація: оригінали не зберігаємо,
  parsed-поля мінімізовані, privacy-формулювання — та сама одна редакція,
  що закриває гейт silpo/чеків (finyk §6.4), розширена на виписки і
  скріни.
- **Шум масового імпорту.** Без дедупу (1)–(3) імпорт виписки створив би
  сотні дублів проти mono-даних. Тому дедуп — блокуючий acceptance, не
  nice-to-have.

### Відхилення від тексту спеки (свідомі, з причин)

1. **Ключ ідемпотентності чека — без `source`**: `UNIQUE(user_id,
fiscal_num)` крос-джерельний (ревʼю: dps-скан і майбутня silpo-історія
   того самого чека мають злитись, а не дублюватись).
2. **Vision-retry дедуп**: спека не визначала — додано `clientScanId`
   (uuid від клієнта, живе в `raw_payload`, партіальний UNIQUE +
   SAVEPOINT-обробка гонки; послідовний retry і конкурентний double-tap
   обидва no-op).
3. **Вхід у UI — глобальний FAB-фан (3 дії)**, не сторінко-локальна кнопка біля
   «+ Витрата»: та сама одна точка входу, але з будь-якої сторінки finyk.
4. **Файлова структура web** — `components/receiptScan/` і
   `components/bulkImport/` за конвенцією модуля, не плаский файл.
5. **QR-сканер** — окремий `useReceiptQrScanner` (та сама архітектура
   BarcodeDetector→zxing, що nutrition), НЕ перевикористання
   nutrition-хука: межа модулів + той хук 1D-only.
6. **Кап commit-у** — 1000 рядків (не 5000): узгоджено з реальним
   верхнім розміром виписок і вартістю per-row транзакційного циклу.
7. **Форма import-API** (§ API-контракт Фази 2 обіцяв інше): замість
   multipart `POST /api/finyk/import/images` (1..N зображень) — JSON
   base64 `POST /api/finyk/import/screenshot/analyze` (1 зображення;
   пачка = клієнтський цикл, як у batch-чеків), а
   `statement/preview` — JSON `csv_text`, спершу **CSV-only** (XLS/XLSX і
   PDF відкладені, § Фаза 2б/2в). Причина: дзеркалить перевірений
   v1-шлях `receipts/analyze` (та сама валідація зображень,
   `BODY_SIZE_POLICY`, жодного multipart-парсера в кодовій базі).
   Міграційних наслідків немає — ендпоінти нові; якщо колись
   зʼявиться multipart-варіант, це буде додатковий маршрут, не
   заміна.

   **Доповнено 2026-08-25 (Фаза 2б, PR «other-bank transactions»):** те
   саме тіло тепер приймає АБО `csv_text`, АБО `file_base64` +
   `file_name` — сам файл, як він є. Multipart так і не зʼявився:
   base64-поле дало ту саму можливість без нового парсера в кодовій базі
   (той самий аргумент, що вище). Формат визначається magic-байтами, не
   розширенням:
   - `PK\x03\x04` → XLSX (власний ридер: `zipReader.ts` на
     `node:zlib` + `xlsxGrid.ts` на OOXML — без нової залежності, за
     тим самим принципом, що `csvParser.ts` і `receipts/dpsXml.ts`);
   - `<table>` у тексті → HTML-таблиця, яку банк віддає під іменем
     `.xls` (`htmlTableGrid.ts`);
   - інакше — текст, декодований UTF-8 → windows-1251 fallback;
   - OLE2 (`.xls` Excel 97) і `%PDF` → 400 з дією для користувача, а не
     нуль рядків.
     **Категорія рядка (2026-08-25).** Відповідь несе опційний
     `categoryHint` — id чипа пікера finyk, який сервер вивів із трьох
     шарів: власна колонка категорії банку → MCC → ключові слова опису
     (`import/categoryHint.ts`; два останні шари переюзають каталог
     `@sergeant/finyk-domain`, яким уже категоризується mono-вебхук).
     Поле ВІДСУТНЄ, коли жоден шар не спрацював — це «доказів немає», а
     не «Інше»: клієнт тоді підставляє власний дефолт, і UI може
     відрізнити здогадку від дефолту. Той самий резолвер працює і на
     шляху скріна (там доступний лише третій шар).

     Плюс дві речі, без яких таблична виписка не працює взагалі:
     пошук рядка-заголовка під преамбулою («Виписка за період…») і зняття
     друкованих підказок профілю (`DD.MM.YYYY`, кома-десятковий) для сіток
     із ТИПІЗОВАНИХ клітинок — там значення вже канонічні.
