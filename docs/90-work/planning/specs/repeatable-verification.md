# SPEC: повторювані комплекти верифікації

> **Last validated:** 2026-09-05 by Codex. **Next review:** 2026-12-05.
> **Status:** Active

## Проблема

Методики, акаунти, результати та історія виправлень змішані у великих одноразових аудитах. Нова сесія повторює розвідку; результати різних прогонів важко порівняти.

## Мета

Шість повторюваних комплектів, сталі сценарії та знахідки, JSON-облік спроб, докази, коротка передача між сесіями та CLI без нових залежностей. Приймання: живий наскрізний пілот і повтор, а також перевірка повноти бібліотеки.

## Рішення дизайну

- Власник, інтервʼю 2026-09-05: web-first, усі виміри; native пізніше. Комплекти плюс легкий CLI, без універсального раннера.
- Власник: постійні синтетичні та одноразові акаунти; основний стенд локальний/тестовий, production smoke окремо.
- Власник: єдиний реєстр відкритих знахідок активних аудитів; старі прогони залишаються джерелами історії.
- Власник: приймання через пілот і повтор. Пілот: витрата → незалежна сума → другий пристрій → запит ШІ → візуал/a11y/антислоп.
- Погоджений план: методики живуть у `docs/02-engineering/testing/verification/`, прогони у `docs/90-work/audits/verification/`. Сценарій визначений один раз; комплекти та модулі є тегами.
- Чинний продуктовий аудит: `storageState` не є новим пристроєм; AI-бюджет до $5 на фазу, mock/live розділені; критерії антислопу беруться з чинної стратегії.

## Поверхня змін

Owner: `sergeant-tech-debt` (scripts), `sergeant-spec` (цей контракт). Продуктові API, DB і runtime не змінюються.

### Формат бібліотеки

`catalog.json`: `{schemaVersion:1, suites:[{id,title}], scenarios:[...]}`. Картка: `id`, `revision` (ціле >0), `title`, `suite`, `modules` (масив), `modes` (smoke/full/pilot), `profiles` (масив), `source`, `preconditions`, `steps` (масив конкретних дій), `expected` (масив), `evidence` (масив), `cleanup`, `pitfalls`. Усі текстові поля непорожні. Інвентар маршрутів та матриця покриття живуть поряд; явні прогалини не є pass.

### Формат прогону

`runs/<id>/run.json`: schemaVersion, id, status (`open|closed`), createdAt, closedAt (після закриття), kind (`live|demo`), metadata, scenarios (повні знімки вибраних карток), attempts (append-only).

metadata: executor, commit, dirty, deployment, environment, baseUrl, browser, viewport, timezone, flags, seedRevision, accounts (аліаси, без секретів), ai (mode, model, configuration, budgetUsd), baseline (ID або null). Знімок каталогу та metadata утворюють контекст порівняння. `--metadata <json-file>` обовʼязковий для init; CLI додає git commit/dirty, якщо відсутні.

Спроба: id, scenarioId, at, status (`pass|fail|blocked|not-run|not-applicable`), actual, reason, evidence (масив `{path,sha256,type}`), metrics (обʼєкт), findingIds (масив). Кожен pass/fail потребує доступного локального доказу з SHA256; CLI може обчислити checksum при record. Інші статуси потребують причини. Шляхи доказів відносні до репозиторію або абсолютні; секретні артефакти поза git. Втрачені/змінені докази роблять validate червоним, а звіт показує це явно. Повторна спроба не замінює попередню.

`findings.json`: schemaVersion, findings (масив). Запис: id, legacyId, title, severity, source (repo-relative шлях), sourceAnchor (опційно), status (`open|fixed-pending-verification|verified|accepted|duplicate`), history (масив), verification (для verified: runId, attemptId), owner (опційно). Імпорт зберігає походження й не заявляє свіжого відтворення. `verified` можливий лише за реальною pass-спробою live-прогону, що посилається на finding ID; PR не є доказом. Старі знахідки без однозначного актуального стану залишаються open із приміткою про тріаж.

### CLI

`pnpm verification <command>` — `scripts/verification/cli.mjs`, Node built-ins, без shell-виконання команд із метаданих. `--root` дозволяє ізольовані тестові fixtures. Відносні шляхи джерел рахуються від root; run ID має бути безпечним сегментом шляху, заборонити traversal та перезапис існуючого прогону.

- `list [--suite ID] [--module ID] [--mode smoke|full|pilot]`: перелік сценаріїв; фільтри перетинаються. `full` включає всю бібліотеку. Невідомий фільтр/порожня вибірка — помилка.
- `init --id ID --metadata FILE [фільтри]`: snapshot вибірки, порожні attempts, шаблон `handoff.md`. Ніколи не запускає тести/створення акаунтів.
- `record --run ID --input FILE`: валідує спробу й додає її атомарно, не змінює closed-прогін. Час та ID генеруються, якщо відсутні; дублікати заборонені.
- `validate [--run ID]`: перевіряє каталог, реєстр, посилання, метадані, знімки, спроби та докази; без run перевіряє всі прогони. Неповний open-прогін структурно валідний, але не успішний.
- `report --run ID`: Markdown у stdout: покриття за останніми спробами, усі спроби, findings, решта роботи, доступність доказів. Не зберігає другий ручний трекер.
- `compare --before ID --after ID`: Markdown у stdout; лише зіставні scenario ID/revision, розходження контексту явні; нові/вилучені/не виконані окремо. Різні live/demo не можуть означати поліпшення; зміни числових metrics показуються без вигаданих порогів. Повторно відкриті = pass→fail для того самого сценарію зі спільним finding ID.
- `close --run ID`: структурна валідація, атомарна фіксація closed; outcome `passed` лише коли усі останні спроби pass або обґрунтовані not-applicable; інакше `incomplete` (є blocked/not-run/відсутні) або `failed`. Закриття не приховує пропуски.

JSON — джерело результатів; Markdown — сценарна методика та контекст. Нові generated Markdown починаються AUTO-GENERATED. CI/lint має запускати структурну валідацію бібліотеки та тести CLI; локальні секретні докази не вимагати у CI (явний режим перевірки лише бібліотеки).

## Поза скоупом v1

Native, автоматичний запуск suite-команд, планувальник, автоматичні продуктові фікси, весь аудит продукту та ретроспективна нормалізація всіх історичних результатів. Пілот не доводить виконання всієї матриці. Немає доступу до стенду/ключа — записати blocked із доказом, не замінювати live демонстрацією.

## Верифікація

1. `node --test scripts/verification/*.test.mjs`: duplicate IDs, невідомий scenario, pass без доказу, checksum mismatch, невідомий finding, append-only repeats, closed immutability, traversal, непорівнянність, metric delta, неповний close, фальшиве verified, round trip усіх CLI-команд.
2. `pnpm verification validate --catalog-only`: усі картки й джерела існують, покриття шести комплектів; exit 0. Повний validate локально додатково перевіряє прогони й докази.
3. `pnpm lint:specs`, форматування змінених файлів, документаційні посилання та належні lint-гейти.
4. Живий пілот на синтетичному акаунті з витратою 12345 копійок: очікуване збільшення витрат 12345, один запис після reload і pull на другому пристрої; AI відображає фактичні дані; desktop/coarse viewport без обрізання, фокус доступний, три висновки антислопу з доказами. Запис кожного кроку окремою карткою, не агрегованим pass.
5. Відновити початкові умови на іншому одноразовому акаунті з тією самою seedRevision, повторити й compare. Витрати AI ≤$5 на фазу. Немає живого стенду — пілот лишається явним блокером приймання.

## Ризики та відкриті питання

Продуктові рішення погоджені. Операційні залежності: живий тестовий стенд, секрети в середовищі та підтверджений стан профілів. Старі звіти містять суперечливі статуси; імпорт переносить контекст, а не оголошує баг чинним. Реальні доступи й недоступні докази фіксуються у handoff кожного прогону.
