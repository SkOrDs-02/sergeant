## Контекст

Strava — найбільший трекер кардіо-активностей (біг, вело, плавання, 200+
типів; годинники Garmin/Apple Watch/Polar синкають туди самі). У червні
2026 Strava запустила [офіційний MCP-конектор](https://press.strava.com/articles/strava-launches-mcp-connector)
— структурний повтор історії Сільпо: платформа офіційно відкрила
персональні дані користувача для AI-клієнтів. Паралельно живе класичний
[Strava API v3](https://developers.strava.com/docs/getting-started/):
OAuth 2.0, `/athlete/activities`, **webhooks** (activity create/update/
delete + deauthorization) — тобто push-модель mono-патерну, не полінг.

Це друга інтеграція за плейбуком Сільпо (спека —
[`silpo-mcp-integration.md`](./silpo-mcp-integration.md), патерн-донор:
спайк §0 → Connect-інфра → незалежні треки). Ландшафт кандидатів і чому
Strava перша в черзі MCP-хвилі —
[research 2026-08-25](../../research/2026-08-25-mcp-and-integrations-landscape.md).

## Проблема

1. **Фізрук — єдиний модуль без авто-входу даних.** Finyk має
   mono-webhook, nutrition — чеки ДПС/Сільпо і комору; кардіо і кроки —
   лише руками. «Фінанси самі» працює, «тренування самі» — ні.
2. **Кардіо не представлене в моделі.** Канон фізрука прямо каже:
   силові — перша реалізація, «модель даних доведеться розширювати на
   біг, кардіо, йогу» ([fizruk.md](../../../01-product/model/fizruk.md)).
   Люди, які бігають/катаються, сьогодні не мають що записати у фізрук.
3. **Зв'язки голодують.** «Тренування↔білок/витрати» — ядро продукту
   (product-overview §1), але кореляції бачать лише те, що людина ввела
   руками; кардіо-активності повз продукт.

## Мета

Користувач зі Strava-акаунтом зв'язує його з Sergeant один раз; далі
кожна активність (записана в апці Strava чи годинником) **сама**
з'являється у фізруку як кардіо-тренування — з типом, тривалістю,
дистанцією — живить стрік і детерміновані digest-кореляції, і не
створює дублікатів із ручними записами. Все без нового ручного вводу.

## Перед-спайк (кабінетний, 2026-08-25)

Що вже відомо без живого акаунта:

- **API v3 живий і безкоштовно реєструється** на `strava.com/settings/api`
  (Client ID + Secret, callback domain). Дефолтні ліміти —
  **200 запитів/15 хв, 2 000/день на застосунок** (заголовки
  `X-RateLimit-*`; вищі ліміти — за запитом).
- **Webhooks є**: activity create/update/delete + **deauthorization**
  (останній — готовий тригер для wipe-флоу). Полінг не потрібен.
- **`/athlete/activities`** віддає summary: тип/sport_type, дистанція,
  час, elevation; `start_date_local` + timezone — лягає на
  ADR-0078 (день-ключ за локальним часом активності).
- **Найбільший ризик — юридичний, і він гірший, ніж здавалось.**
  Листопад 2024: [API Agreement заборонив](https://press.strava.com/articles/updates-to-stravas-api-agreement)
  показ даних будь-кому, крім самого атлета (нам ОК — показуємо лише
  власнику), і використання даних в AI-моделях. **Червень 2026:
  заборону розширено** — не можна використовувати Strava-дані «в
  операціях будь-якого AI Application», з явним переліком:
  **retrieval-augmented generation, ingestion у context window**
  ([розбір](https://www.getvertical.ai/blog/chatgpt-strava-integration/),
  [обговорення комплаєнсу](https://communityhub.strava.com/developers-api-7/compliance-and-ai-use-13628)).
  Для продукту, чий hub-coach шар кладе дані користувача в LLM-контекст,
  це пряме обмеження архітектури — див. § Рішення дизайну.
- **Strava агресивно ріже API-екосистему** (плата для розробників,
  ретаєринг ендпоінтів: Club-ендпоінти зникають 2026-09-01, Explore
  Segments — лише Extended Access Tier). Платформний ризик вищий за
  Сільпо: у Сільпо правил не було взагалі, у Strava вони є і жорсткішають.
- **Офіційний MCP** — read-only, для підписників Strava, позиціонований
  як канал «атлет ↔ його AI-клієнт». Чи легальний/технічно доступний він
  для **server-side** third-party продукту — невідомо; це живе питання
  спайку, і його умови можуть відрізнятись від API Agreement.

## Знахідка: межа LLM-контексту не одна (перевірено 2026-08-27)

Драфт припускав, що «межа збирання LLM-контексту фільтрує `origin: strava`
безумовно» — тобто одне місце з одним тестом. Звірка з кодом цього **не
підтверджує**: місць щонайменше три, і вони в різних середовищах виконання.

1. **Чат-тули фізрука виконуються на клієнті.**
   [`handleQueryFizrukAction`](../../../../apps/web/src/core/lib/chatActions/queryFizrukActions.ts)
   відпрацьовує `query_workouts` / `exercise_progress` / `training_stats`
   у браузері проти локальних даних; на сервер їде вже сформований
   результат. Сирі записи з полем `origin` живуть саме тут — отже фільтр
   мусив би бути клієнтським.
2. **Серверний чокпойнт існує, але бачить уже текст.**
   [`prepareToolResults.ts`](../../../../apps/server/src/modules/chat/prepareToolResults.ts)
   — справжня межа периметра (маска → усічення → огорожа, з `AI-DANGER`
   про незмінність порядку), але структури з `origin` в ній уже немає.
3. **Дайджест і коуч збирають контекст окремо**, на сервері
   (`weekly-digest.ts`, `chat/coach.ts`).

Для звичайної фічі це дрібниця. Тут — ні: фільтр є **договірною умовою
існування інтеграції**, і одна пропущена гілка означає порушення API
Agreement, а не косметичний баг. Гарантія, яку не можна забути
застосувати (структурна ізоляція — окрема сутність, якої AI-шлях не
читає взагалі), відрізняється від гарантії, яку треба памʼятати
застосувати в трьох місцях.

Рішення по цьому — після спайка (рішення №3): при no-go воно не
знадобиться.

## Рішення дизайну (провізійні — до спайку §0)

- **Канал: API v3 + webhooks, не MCP.** Webhook-модель — точний
  mono-патерн (push, upsert, ідемпотентність), полінгу і TTL-кешів
  Сільпо не треба. MCP-гілка перевіряється на спайку як альтернатива,
  але v1 проєктується під API v3. Відкинуто: полінг за розкладом —
  webhooks його скасовують.
- **Strava-дані ніколи не потрапляють у LLM-контекст.** Червнева
  редакція API Agreement забороняє ingestion у context window — отже:
  кожен імпортований запис несе `origin: "strava"`, і межа збирання
  LLM-контексту (HubChat tool-results, coach-інсайти, LLM-частина
  digest) **фільтрує їх безумовно**. Детерміновані обчислення
  (`insightsEngine`, `digestCorrelations`, стрік) — код, не модель:
  їм можна. Це не мітигація «про запас», а умова існування інтеграції.
  **Механізм гарантії — відкрите рішення** (№3): фільтр у трьох місцях
  проти структурної ізоляції, див. § «Знахідка: межа LLM-контексту не
  одна». Обирається після спайка. Якщо спайк §0 покаже, що навіть
  детерміновані обчислення трактуються як порушення — **no-go всієї
  інтеграції**, кардіо-джерелом стає HealthKit/Health Connect (без
  договірних обмежень).
- **Кардіо — окрема сутність, не розширення `fizruk_workouts`.**
  ✅ **Ратифіковано founder-ом 2026-08-27** (рішення №2) — і незалежно
  від того, чим закінчиться спайк: та сама сутність потрібна
  HealthKit/Health Connect. Силова модель (groups/sets JSONB) не пасує
  кардіо; канон застерігає від припущення, що модель фінальна, але не
  вимагає одної таблиці. Форма: `fizruk_activities` (id = id активності
  в джерелі для імпортованих, `origin strava|manual`, sport_type,
  started_at_local + timezone, moving_sec, distance_m, elevation_m,
  avg_hr?, `raw JSONB`). Відкинуто: пхати кардіо у
  `fizruk_workouts.groupsJson` — ламає силовий редактор і стрік-логіку.
  **Міграція їде в тому самому PR, що й перший імпортер**, не раніше.
- **Стрік і «повноцінне тренування».** Канон: «повноцінне тренування ≠
  легка активність». Імпортована активність рахується у стрік за
  порогом (пропозиція v1: `moving_sec ≥ 20 хв` АБО тип із allowlist;
  прогулянка 10 хв — ні). Поріг — константа, рішення founder-а на
  треку C.
- **Дедуп із ручними записами** — першокласний стан, як unmatched у
  Сільпо: якщо в межах ±2 год від імпортованої активності є ручне
  тренування, не створюємо друге мовчки — показуємо пропозицію
  «це те саме?» (link/ignore). WeightTraining зі Strava за
  замовчуванням НЕ імпортується (силові ведуться у нас, багатше).
- **Токени — дзеркало Сільпо/mono.** `strava_connection` (AES-256-GCM +
  key ring, `token_key_version`), single-flight refresh обов'язково з
  першого дня: Strava **ротує refresh_token при кожному обміні** — та
  сама гонка, яку Silpo-раунд-4 ловив у проді, тут відома наперед.
  OAuth-state — у PG (`strava_oauth_state` за зразком міграції 126),
  не в памʼяті процесу.
- **Снапшот у власний PG; deauth-webhook → позначка + wipe-патерн
  Сільпо**: «Відключити Strava» видаляє лише токени; окрема дія
  «Видалити всі дані Strava» — активності. Спайк §0 звіряє, чи API
  Agreement вимагає видалення даних при deauthorization (у Strava,
  на відміну від Сільпо, це може бути прописано).
- **Ізоляція збою:** kill switch `STRAVA_ENABLED`, деградація до
  staleness-банера, `recordExternalHttp("strava", …)`, breaker;
  ліміт 2 000/день — на застосунок, тобто спільна доля всієї бази
  (SPOF-патерн спільного client_id Сільпо) — глобальний бюджет +
  webhook-first мінімізують витрату.
- **Free/Pro:** імпорт власних даних = Free (аналогія «банк-sync
  безкоштовний назавжди»). Проактивні/AI-надбудови тут неможливі
  за визначенням (AI-заборона), тож Pro-питання не виникає.

## Спайк §0 (≤1 день, живий акаунт founder-а — до будь-якого коду в main)

Передумова: у founder-а є Strava-акаунт із хоч кількома активностями;
якщо історії немає — записати 2–3 тестові (прогулянка з телефоном
достатня) перед спайком.

1. **Реєстрація застосунку** на `strava.com/settings/api`: чи є у 2026
   плата / який tier для нашого обсягу; фактичні ліміти в
   `X-RateLimit-*`. **Go/no-go: вартість.**
2. **OAuth + `/athlete/activities`**: глибина історії; точні поля
   (sport_type, start_date_local, timezone, moving_time, distance,
   average_heartrate, calories?); скільки активностей за один виклик;
   як виглядає WeightTraining/Walk/Run у сирому JSON (фікстури для
   zod-схем і snapshot-тесту — як у Сільпо).
3. **Webhook**: створити підписку, записати тестову активність,
   виміряти затримку події; перевірити подію deauthorization.
   **Go/no-go по треку B** (без webhook — полінг, цінність падає).
4. **Юридичний прохід поточної редакції API Agreement**: дослівне
   формулювання AI-заборони — чи сумісна вона з «Strava-дані поза
   LLM-контекстом, детерміновані обчислення дозволені»; вимоги до
   зберігання/видалення при deauth; display-обмеження (лише власнику —
   у нас так). **Головний go/no-go всієї інтеграції.** Фіксувати
   цитатами у спеці, як зроблено з офертою Сільпо.
5. **MCP-гілка**: endpoint/умови офіційного MCP; чи доступний
   server-side third-party клієнту; чи його terms дозволяють більше
   (це sanctioned-AI-канал Strava). Якщо так — переоцінити рішення
   «API v3 перший».
6. **Ліміти per-app vs per-athlete** — на скільки активних користувачів
   вистачає 2 000/день при webhook-first моделі (оцінити: 1 подія =
   1 fetch активності).

- Узагальнення «фітнес-адаптера» — лише при другому живому джерелі
  (правило другого рітейлера з Сільпо-спеки).

## Верифікація (обовʼязково)

1. `pnpm check` зелений; contract-тести strava-схем; snapshot-тест
   фікстур API; migration-тест + rollback-sanity.
2. Click-through: Налаштування → «Зв'язати Strava» → OAuth → connected →
   backfill підтягує історію → записана в Strava тестова активність
   з'являється у фізруку без дій користувача (webhook) → стрік
   оновлюється за порогом.
3. Негативні шляхи: 401 → refresh → повторний 401 → `reauth_required` +
   банер; 429 → backoff без падіння; deauth-webhook → статус
   disconnected; wipe видаляє активності, ручні тренування лишаються.
4. **Тест LLM-межі:** запит у HubChat, що тягне тренування, не містить
   жодного рядка з `origin: strava` у tool-results (юніт на фільтр +
   інтеграційний на збирання контексту).
5. Дедуп: імпортована активність поверх ручного запису тієї ж години →
   пропозиція звʼязки, не другий запис.

## Ризики та відкриті питання

- **AI-заборона API Agreement (головний).** Навіть із фільтром LLM-межі
  лишається сіра зона «indirect operation of AI Application» — закриває
  спайк §0 п.4; якщо no-go — кардіо-джерелом стає HealthKit/Health
  Connect, ця спека закривається зі статусом Withdrawn.
- **Політика Strava жорсткішає щопівроку** (плата, ретаєринг, tiers) —
  мітигації ті самі, що в Сільпо: снапшот у PG, kill switch, тонкий
  адаптер; плюс не будувати на Strava нічого, що не переживе її втрату.
- ~~**Кардіо-моделі у фізруку немає**~~ — форму `fizruk_activities`
  ратифіковано 2026-08-27 (рішення №2). Лишається відкритим лише
  **стрік-поріг** («повноцінне тренування ≠ легка активність») — рішення
  founder-а на треку C.
- **Персона — підтверджений ризик, не гіпотеза.** Founder має акаунт,
  але активностей не веде (рішення №4). Отже дефекти не спливуть на
  власному використанні, як було із Сільпо, і цінність перевіряється
  лише на тестовій групі — тобто після бети. Вага треку відносно
  HealthKit/Health Connect падає; треки B–D не планувати до
  підтвердженого попиту.
- **Ліміт 2 000/день на застосунок** — спільна доля бази; webhook-first
  тримає витрату ~лінійною від кількості нових активностей, але backfill
  великих історій треба чергувати (послідовний обхід, як silpo-poller).
- **Дрейф контракту** — snapshot-тест фікстур + zod-деградація до
  staleness (патерн Сільпо).
