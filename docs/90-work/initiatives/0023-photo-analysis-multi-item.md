## TL;DR

Фото-аналіз повертає **одну** страву на кадр: `dishName` + одні `macros` на все, що є на тарілці. Коли модель помиляється в одній позиції з трьох, виправити її неможливо — треба або приймати неправильну суму, або віднімати калорії руками. Тестова група вперлася в це першою ж серйозною спробою. Розв'язок — повернути `items[]` із власними КБЖВ на позицію і дати видаляти/додавати позицію точково, без повторного прогону моделі.

## Чому зараз

- **Це перша скарга з бети, яка про механіку, а не про косметику.** Тестерка сама відкинула своє складніше рішення й сформулювала дешеве: розбивка + ручна правка однієї позиції.
- **Модель уже вміє сегментувати тарілку.** `analyze-photo` повертає `ingredients: [{name, notes}]` — назви складників там уже є. Бракує КБЖВ на позицію і UI, який трактує їх як окремі сутності. Це доростання наявної структури, а не новий конвеєр.
- **Уточнення не заміняє виправлення.** `refine-photo` — це повторний прогін по всьому кадру: він може змінити й ті дві страви, що вже вгадані. Точкове видалення позиції детерміноване, реролл — імовірнісний. Поки немає першого, друге видає себе за нього.
- **Категорія вже конвергувала.** Апка, яку тестерка показала як приклад, розбиває вечерю на три рядки з окремим `×` на кожному. Для фото-логування це вже не диференціатор, а очікування за замовчуванням.

## Скоуп

**In:**

1. **Контракт `items[]`** — `NutritionPhotoResult` віддає масив позицій, кожна зі своїми `name`, `macros`, `gramsApprox`, `confidence`. Триплет Hard Rule #3 (серіалізатор `normalizePhotoResult` ↔ типи `api-client` ↔ contract-тест) рухається одним PR.
2. **Per-item confidence** — модель уже віддає `confidence` на весь результат; на рівні позиції він робить «третя сумнівна» видимим до того, як людина сама помітить.
3. **UI списку позицій** у `PhotoAnalyzeCard` / meal-sheet: видалити позицію, додати свою, правити грами — без повторного звернення до моделі.
4. **Зворотна сумісність** — старий однопозиційний шлях лишається валідним входом (одна позиція = список довжини 1), щоб клієнти в польоті не зламались.

**Out:**

- **Голосовий / текстовий опис страви замість фото** — окремий канал вводу, не механізм виправлення. Свідомо не в цій ініціативі (оцінка тестерки: «годна штука, але то не для MVP» — і вона має рацію саме тому, що це інший вхід).
- **Сегментація по пікселях / bbox на фото** — модель віддає назви, не координати; малювати рамки поверх кадру тут не потрібно.
- **Переписування журналу** під N рядків на прийом їжі — денний журнал уже вміє кілька позицій; ця ініціатива доводить до нього результат аналізу, а не змінює його схему.

## План змін

### Фаза 0 — Канал «сказати своїми словами» — **зроблено**

Дешевий проміжний крок, який не потребував зміни контракту: `refine-photo` уже приймає `qna` як довільні пари (до 8, по 500 символів), тож вільне зауваження їде туди під підписом `PHOTO_NOTE_QUESTION`.

- `apps/web/src/modules/nutrition/hooks/usePhotoAnalysis.ts` — стан `note`, пара в `qna` **першою** (сервер ріже до 8), скидання на новий кадр.
- `apps/web/src/modules/nutrition/components/PhotoAnalyzeCard.tsx` — поле «Що не так? Опиши своїми словами» + чесний підпис про те, що перерахунок оновлює весь результат.
- Блок уточнень **більше не гейтиться** на `questions.length > 0`: коли модель упевнена, вона не питає нічого — саме в тому випадку, заради якого канал і потрібен.

**Чого Фаза 0 не робить:** не виправляє одну позицію з трьох. Вона дає людині сказати, що не так, і дає нам **безкоштовний датасет** із того, що саме люди пишуть — вхід для рішень Фази 1.

### Фаза 1 — Контракт `items[]` (P0 для ініціативи)

- **Сервер:** промпт `analyze-photo` / `refine-photo` просить масив позицій із КБЖВ і впевненістю на кожну; `normalizePhotoResult` ([`apps/server/src/lib/nutritionResponse.ts`](../../../apps/server/src/lib/nutritionResponse.ts)) гарантує форму й на порожньому/кривому виводі моделі.
- **Контракт:** `NutritionPhotoResult.items: NutritionPhotoItem[]` у `packages/api-client` + contract-тест, який пінить триплет.
- **Зворотна сумісність:** сумарні `macros` лишаються полем верхнього рівня (сума позицій) — старі клієнти не ламаються.
- **Оцінювальний стенд:** `pnpm --filter @sergeant/server eval:vision` має рахувати якість посегментно, інакше регресію розбивки не видно.

### Фаза 2 — UI списку позицій

- `PhotoAnalyzeCard` рендерить позиції рядками: назва, КБЖВ, грами, `×`.
- Позиція з низькою впевненістю позначена візуально — виправлення саме себе наводить на ціль.
- «Додати позицію вручну» перевикористовує наявний пошук продукту з meal-sheet, а не новий екран.

### Фаза 3 — Перенесення в журнал

- Збереження пише N рядків замість одного злитого — денний журнал і `estimatedKcalShare` рахують по позиціях.
- Перевірка: сума позицій == те, що бачила людина на картці.

## Відкриті рішення

1. **Скільки позицій максимум?** Промпт має мати стелю (пропозиція: 8) — інакше салат перетворюється на список з 15 інгредієнтів, і UI стає гіршим за поточний.
2. **Інгредієнт vs позиція.** «Рис з овочами» — це одна позиція чи дві? Пропозиція: позиція = те, що людина назве стравою; `ingredients` лишається описом усередині позиції.
3. **Ціна токенів.** Посегментний вивід довший; треба зміряти на `eval:vision` перед розкаткою (`max_tokens: 650` зараз може не вистачити).

## Ризики

| Ризик                                                                | Мітигація                                                                                          |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Модель дробить страву надто дрібно — UI гірший за поточний           | стеля позицій у промпті + правило «позиція = страва, не інгредієнт»; зміряти на стенді до розкатки |
| Сума позицій ≠ підсумок, який бачила людина                          | серіалізатор рахує підсумок **із позицій**, а не бере окреме число моделі                          |
| Довший вивід упирається в `max_tokens` і JSON рветься посеред масиву | підняти ліміт у тому ж PR + наявний фолбек нормалізатора на кривий вивід                           |
| Зростання вартості одного аналізу                                    | заміряти на `eval:vision` до розкатки; Premium-гейт `ai-photo-analysis` уже стоїть                 |

## Критерії DONE

- [ ] `NutritionPhotoResult.items[]` у контракті + contract-тест (Hard Rule #3) зелений.
- [ ] Видалення хибної позиції і додавання своєї — без повторного прогону моделі.
- [ ] Позиція з низькою впевненістю візуально відрізняється від решти.
- [ ] Журнал отримує N рядків; сума збігається з карткою.
- [ ] `pnpm --filter @sergeant/server eval:vision` рахує посегментну якість і має baseline до/після.
- [ ] Тестова група підтверджує сценарій «видалити булочку, додати сирник».
