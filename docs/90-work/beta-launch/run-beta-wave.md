## Чому саме такий порядок

Три залежності, які диктують послідовність:

1. **Стеля витрат ставиться першою.** `ANTHROPIC_BUDGET_HARD_DEGRADE_ALL` — єдине, що фізично обмежує рахунок за AI. Soft/hard-пороги без нього лише пишуть алерт і нічого не зупиняють. Вмикати після того, як люди зайшли, — означає лишити вікно без стелі.
2. **Розсилка йде до видачі Pro.** Pro видається по email, а email з'являється лише після реєстрації. До розсилки видавати нема кому.
3. **Група бети створюється до розсилки.** Порожній `TELEGRAM_BETA_INVITE_LINK` не валить скрипт — він тихо шле лист **без** посилання на групу. Тобто «доступ відкрито» без доступу.

## Фаза 0 — підготовка (один раз перед першою хвилею)

### 0.1 Стеля витрат на AI

У Coolify, у сервісі API:

```
ANTHROPIC_BUDGET_HARD_DEGRADE_ALL=true
```

Коли денний спенд Anthropic пробиває `ANTHROPIC_BUDGET_HARD_USD` (дефолт `5`), усі не-founder користувачі падають на дешеву модель замість того, щоб виставити рахунок далі. Без цього прапорця стелі немає.

Там же перевір:

- `STRIPE_ENABLED` — має лишатись `false`. Назва історична (Stripe виведено з експлуатації), але саме ця змінна вимикає **серверний** paywall.
- `AI_QUOTA_FOUNDER_IDS` — **тільки твій** Better-Auth ID. Founder обходить і квоту, і аварійний breaker; тестерам це не видають.

### 0.1а Відкрити Pro всім одразу (замість поіменної видачі)

```
BILLING_ALL_PRO=true
```

Знімає обидва гейти разом: `getUserPlan()` віддає синтетичний Pro (сервер), `/api/billing/status` — той самий Pro клієнтові, тож `usePlan()` перестає малювати пейволи. Рядки в `subscriptions` не заводяться, [Фаза 2](#фаза-2--видача-pro) стає непотрібною.

Що прапорець дає насправді — рівно одне. З трьох «Pro-фіч» у `effectiveLimits.ts` дві (`cloudSyncDevices`, `monoAutoSync`) ніде не enforced і живуть лише в тексті сторінки тарифів. Реально відрізняється тільки `aiRequestsPerDay`: Free — 5/добу, Pro — **без ліміту**.

> **AI-DANGER: разом із персональною стелею зникає єдине per-user гальмо витрат.** Лишається тільки глобальний денний бюджет (`ANTHROPIC_BUDGET_HARD_DEGRADE_ALL` із 0.1), а він, спрацювавши, роняє на дешеву модель **одразу всіх** — тобто один захоплений тестер псує досвід решті. На закриту групу за інвайтом це прийнятний розмін; на відкритий доступ — ні. Знімати прапорець разом із рештою бета-інфраструктури (`AI-LEGACY: expires 2026-10-31`).

Одруківка в значенні не проходить мовчки: Zod-схема приймає лише `true`/`false`/`1`/`0` і валить старт сервера на будь-чому іншому. Це навмисно — тихий фолбек на Free означав би, що тестери сидять на 5 запитах, і ніхто про це не дізнається.

### 0.2 Група бети в Telegram

Створи групу, візьми invite-лінк, поклади його у своє локальне оточення як `TELEGRAM_BETA_INVITE_LINK`.

### 0.3 Окремий Vercel-проєкт для застосунку бети

**Окремий проєкт, а не окремий домен.** Причина — у фазі 4: видалення проєкту забирає і кастомний домен, і генерований `<project>.vercel.app`, і всі deployment-URL-и разом. Відкручений домен лишає `<project>.vercel.app` публічним, і на Hobby захистити його неможливо (див. [Vercel docs](https://vercel.com/docs/deployment-protection): production domain лишається публічним).

Налаштування проєкту:

| Поле                                 | Значення                                                                            |
| ------------------------------------ | ----------------------------------------------------------------------------------- |
| Root Directory                       | `apps/web`                                                                          |
| Include files outside Root Directory | **увімкнути** (інакше pnpm-воркспейс не збереться)                                  |
| Build / Install / Output             | лишити порожніми — їх задає [`apps/web/vercel.json`](../../../apps/web/vercel.json) |

Змінні оточення — розділ [«Змінні для бета-проєкту»](#змінні-для-бета-проєкту) нижче.

### 0.4 Ручний гейт деплою

За замовчуванням **обидві** поверхні викочуються самі на мерж у `main`, тобто робота під час бети доїде до тестерів без твого відома:

| Поверхня                   | Тригер                                                                                                                                                  |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Фронт (Vercel-проєкт бети) | будь-який пуш у `main`                                                                                                                                  |
| Бекенд (Coolify)           | пуш у `main`, що чіпає `apps/server/**`, `packages/shared`, `db-schema`, `finyk-domain`, лок-файл → GH Actions → образ → вебхук → деплой **+ міграції** |

Два дроти, обидва знімаються оборотно:

**Фронт.** `Settings → Git → Production Branch` → зміни `main` на `beta`. Створи гілку `beta` від поточного стану — вона й стане тим, що бачать тестери. Пуші в `main` проєкт більше не чіпають; свідомий фікс — мерж `main` → `beta`.

**Бекенд.** Прибери секрет `COOLIFY_DEPLOY_WEBHOOK` у Settings → Secrets репозиторію. У [`deploy-api.yml`](../../../.github/workflows/deploy-api.yml) для цього є заготовлений вимикач: крок стоїть під `continue-on-error: true` і при порожньому секреті виходить із кодом `0`. Тобто CI лишається зеленим, **образ усе одно збирається й лягає в ghcr.io** — розробка не сповільнюється, просто ніхто не викочує, поки ти не натиснеш Deploy у Coolify.

> **Значення секрета перед видаленням копіювати НЕ треба — і не вийде.** Actions-секрети write-only: зашифровані at rest, розшифровуються лише в раннер під час прогону, тож GitHub не покаже їх навіть власнику репо (пропонує рівно «Update» або «Remove»). Тут до 2026-08-10 стояла інструкція «скопіювавши значення собі» — невиконанна; знято за фактом зіткнення з нею.
>
> Джерело істини — Coolify, і значення збирається звідти заново:
>
> - **`COOLIFY_DEPLOY_WEBHOOK`** — повний GET-URL виду `https://<coolify-host>/api/v1/deploy?uuid=<uuid-ресурсу>`. Готовий URL лежить на сторінці ресурсу в розділі **Webhooks**; сам `uuid` видно і в адресному рядку сторінки ресурсу.
> - **`COOLIFY_DEPLOY_TOKEN`** — Bearer із розділу API-токенів Coolify. Показується один раз при створенні: якщо загубився, не шукай — згенеруй новий, онови секрет, старий відклич.
>
> Повернення гейта після бети = скопіювати webhook-URL із Coolify і завести секрет із тим самим іменем.

> **Ручний Deploy бере `:latest`, тобто вершину `main` на мить натискання** — не той коміт, який ти переглянув. Якщо між перевіркою і кнопкою в `main` щось доїхало, воно поїде разом, і гейт захистить лише від _випадкового_ деплою, а не від несподіваного вмісту. Воркфлоу тегує образ ще й по SHA (`ghcr.io/<owner>/sergeant-api:<sha>`), тож коли потрібен саме перевірений коміт — заміни тег у налаштуваннях ресурсу Coolify з `latest` на конкретний SHA.
>
> Міграції ручний деплой не оминає: вони не в цьому воркфлоу, а в pre-deploy кроці Coolify (`node dist-server/migrate.js`), тож виконаються перед стартом контейнера як завжди.

> **Гейт, а не заморозка.** Міграції додаються приблизно **одна на два дні** (080 → 090 за 19 днів). Повна заморозка на два тижні накопичить ~7 міграцій, які виконаються однією пачкою на базі, де вже лежать дані тестерів — рівно той big-bang, якого заморозка мала уникнути. Two-phase DROP (Hard Rule #4) розрахований на те, що фази роз'їжджаються по різних деплоях. Тому деплой раз на 2–3 дні, коли сам перевірив, а не «ніколи до кінця бети».

### 0.5 Де перевіряти, поки гейт закритий

| Що змінюєш                       | Де перевіряти                                                                                               |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Верстка, навігація, стан         | локально, або PR-превʼю Vercel / другий (не-бета) проєкт                                                    |
| Ендпоінт, серіалізатор, міграція | повний локальний стек — [`run-locally-after-merge.md`](../../00-start/playbooks/run-locally-after-merge.md) |
| Бот, вебхуки, платежі            | локальний стек + `cloudflared tunnel --url http://localhost:3000`                                           |

Окреме dev-середовище на тому ж VPS **не заводити**: спільний інстанс Postgres означає спільні `shared_buffers`, `max_connections`, 2 vCPU і спільну долю в OOM. Це ізоляція даних, але не ізоляція збоїв — тобто не те, заради чого її заводять. Локальний docker-Postgres дає справжню ізоляцію за нуль ресурсів.

## Фаза 1 — розсилка інвайтів

Запускається з ноута. Потрібні три змінні: `DATABASE_URL` (публічний URL прод-бази — той самий, що для міграцій), `TELEGRAM_WAITLIST_BOT_TOKEN`, `TELEGRAM_BETA_INVITE_LINK`.

### 1.1 Подивитись, що піде і скільком

```bash
node scripts/telegram/broadcast-waitlist.mjs --dry-run
```

Друкує кількість адресатів і повний текст листа. Нічого не шле. **Читай текст очима** — після відправки редагувати нічого.

### 1.2 Перша хвиля

```bash
node scripts/telegram/broadcast-waitlist.mjs
```

Стеля — **30 адресатів за прогін, це дефолт**: голий запуск більше не розсилає всій черзі. Лист у Telegram неможливо відкликати, тож безпечний дефолт тут важливіший за зручність.

`--limit` існує не для економії. Як зреагують живі люди, суха перевірка не покаже: перші 30 скажуть, чи зрозумілий лист і чи витримує група потік. Далі `--limit 50`, далі решта — або `--limit 0`, щоб дослати всю чергу без стелі.

Некоректне значення (`--limit 3O` з літерою) валить скрипт з поясненням, а не тихо знімає стелю.

### Як він поводиться

Черга — це `notified_at IS NULL AND opted_out_at IS NULL`. Після **кожного** успішного повідомлення скрипт одразу ставить `notified_at`, окремим запитом. Тому перерваний прогін (заснув ноут, обірвався інтернет) безпечно перезапустити: вже запрошені у вибірку не потраплять.

| Відповідь Telegram    | Дія                                               |
| --------------------- | ------------------------------------------------- |
| успіх                 | `notified_at = NOW()`                             |
| `403` заблокував бота | `opted_out_at = NOW()` — це відписка, а не збій   |
| `429`                 | чекає рівно `retry_after`, пробує **один** раз    |
| інше                  | нічого не ставить, наступний прогін спробує знову |

Темп — 50 мс між повідомленнями (~20/с) при стелі Telegram ~30/с.

### Свій текст

```bash
node scripts/telegram/broadcast-waitlist.mjs --dry-run --text "Привіт! Відкрив доступ..."
```

## Фаза 2 — видача Pro

Без Pro тестери не побачать частину того, що треба протестувати: аналіз фото їжі, AI-memory, мультивалютність, експорт у PDF, автосинк Monobank.

Гейт стоїть **двічі** — на сервері (`requirePlan`) і на клієнті (`useFeatureGate` → `usePlan`). Клієнтський спрацьовує першим і навіть не шле запит, тому `STRIPE_ENABLED=false` його не знімає.

> **Уся ця фаза необов'язкова, якщо в Фазі 0.1 увімкнено `BILLING_ALL_PRO`.** Прапорець знімає обидва гейти одразу: `getUserPlan()` віддає синтетичний Pro (сервер), а `/api/billing/status` — той самий Pro клієнтові, тобто `usePlan()` теж перестає малювати пейволи. Рядки в `subscriptions` при цьому не заводяться взагалі.
>
> Коли все-таки лишити скрипт: він видає **поіменно** і термін **сам згасає** через `current_period_end`. Прапорець не робить ні того, ні іншого — він відкриває всіх, поки ти його не знімеш.

> **Симптом, коли цю фазу пропустили (спіймано 2026-08-10).** Тестер пише «нейронка перевантажена» або «ліміт вичерпано»: не генерується меню на тиждень, чат відмовляє. Це **не** аварія на боці Anthropic/OpenRouter — це наш власний 429 з `assertAiQuota`. Free має `aiRequestsPerDay: 5` (`billing/effectiveLimits.ts`), і одна генерація меню плюс кілька повідомлень вичерпують добу за хвилини.
>
> Причина завжди одна: людина не Pro. `getUserPlan()` віддає Pro рівно за трьома умовами — ID у `AI_QUOTA_FOUNDER_IDS`, `BILLING_ALL_PRO=true` **в env сервера**, або живий рядок у `subscriptions`. Мерж коду з прапорцем сам собою не видає нічого: `BILLING_ALL_PRO` — змінна оточення в Coolify, і поки її не задано, значення `false` (Zod-схема дефолтить саме так, щоб не вгадувати на білінговому прапорці).
>
> Перевірка на дві команди:
>
> ```bash
> psql -U postgres -d postgres -c 'SELECT user_id, plan, status, provider, current_period_end FROM subscriptions ORDER BY 1;'
> psql -U postgres -d postgres -c "SELECT subject_key, bucket, endpoint, request_count FROM ai_usage_daily WHERE usage_day = CURRENT_DATE ORDER BY request_count DESC LIMIT 20;"
> ```
>
> Читати разом, а не поодинці. Немає живого рядка для цього `user_id` **і** `request_count` уперся рівно в 5 — діагноз підтверджено, лікується цією фазою або прапорцем із Фази 0.1 (різниця між ними — абзацом вище).
>
> Дві пастки в читанні. Перша: рядок може бути, але **простроченим** — `getUserPlan()` бере лише `current_period_end IS NULL OR > NOW()`, тож видача на 14 діб мовчки згасає всередині хвилі, і симптом повертається без жодної зміни в коді. Друга: видача **не скидає** `ai_usage_daily`, тож після неї лічильник так і стоїть на 5 — це вже не стеля, просто історія доби. Пʼятірка сама по собі не доводить, що людина заблокована **зараз**; доводить лише пʼятірка ПЛЮС відсутність живої підписки.
>
> Якщо підписка жива, а 429 усе одно приходить — це не план. Далі за списком: пер-ендпоінтний `rateLimitExpress` (свої вікна на кожному маршруті), USD-стеля транскрипції (`modules/transcribe/usdCap.ts`, окремий лічильник у доларах, не в запитах), глобальний денний бюджет Anthropic.

Потрібна одна змінна: `DATABASE_URL`.

### 2.1 Побачити, хто зареєструвався

```bash
node scripts/billing/grant-beta-pro.mjs --list
```

Пошта, поточний план, дата реєстрації. Нічого не змінює. Тут ти зіставляєш акаунт із людиною з вейтліста — автоматично це не зв'язати, бо в бота є `chat_id`, а не пошта.

### 2.2 Перевірити

```bash
node scripts/billing/grant-beta-pro.mjs --emails a@b.com,c@d.com --dry-run
```

`--dry-run` тут **виконує всі справжні записи в транзакції й відкочує її**, а не друкує план. Тому суха перевірка ловить помилку в SQL до того, як та щось зачепить.

### 2.2а Видати по даті, без зіставлення пошт

Якщо зіставляти акаунти з людьми з вейтліста не хочеться — не треба:

```bash
node scripts/billing/grant-beta-pro.mjs --since 2026-08-09 --dry-run
node scripts/billing/grant-beta-pro.mjs --since 2026-08-09 --days 14
```

Бере **всіх, хто зареєструвався з цієї дати** (київська північ, `"user"."createdAt" >= дата`) і далі йде тим самим шляхом, що й `--emails`. Логіка проста: посилання на бету є лише в запрошених, тож «усі, хто зареєструвався з дати розсилки» — це рівно вони.

Ціна відома і прийнята: випадковий перехожий, який роздобув URL і зареєструвався у вікні, теж отримає Pro. На два тижні закритої хвилі це дешевше за збір пошт у спільному чаті — і без чужих персональних даних там.

Дата — це дата **розсилки**, не сьогоднішня. Формат жорсткий, `YYYY-MM-DD`; інше скрипт відхилить.

### 2.3 Видати поіменно

```bash
node scripts/billing/grant-beta-pro.mjs --emails a@b.com,c@d.com --days 14
```

Тестери побачать Pro після перезавантаження сторінки. Багато адрес — склади список у файл (по одній на рядок, `#` — коментар) і передай `--emails-file beta.txt`.

### Що зроблено навмисно

- **`--days` закриває бету саму.** Через N днів Pro відпадає без твоєї участі — забути відкликати доступ це нормальна людська справа.
- **Повторний запуск безпечний.** Дублів не буде, просто оновиться термін.
- **Справжню оплачену підписку скрипт скасувати не може.** Він працює лише з записами `provider = 'manual'` — тими, які сам і створив.
- **`status = 'trialing'`, не `'active'`** — щоб бета-доступи не змішались із реальними платниками в метриках, коли ті з'являться.

## Фаза 3 — під час бети

Стан вейтліста — командою `/stats` у боті (працює тільки з твого `chat_id`, заданого в `TELEGRAM_WAITLIST_ADMIN_CHAT_ID`):

```
Вейтліст: 24

Чекають:      4
Запрошені:    18
Відписались:  2

Канали:
  hero — 19
  footer — 5
```

`Чекають` — це черга наступної хвилі. Коли впаде до нуля, всі запрошені.

Витрати дивись у Coolify-логах за алертами `anthropic_budget_*`. Soft-поріг (`$3/день`) — сигнал, що темп вищий за очікуваний; hard (`$5/день`) — момент, коли всі падають на дешеву модель.

### 3.1 Цикл свідомої викатки

Гейт із фази 0.4 не спиняє розробку — він робить викатку рішенням. Мержиш у `main` як завжди; змінюється лише те, що між `main` і тестерами тепер стоїш ти.

**Вебхук повертати не треба.** Секрет — це лише автоматичний тригер. Сам деплой робить Coolify власною кнопкою Deploy, тягнучи образ із `ghcr.io`. Прибираєш секрет один раз на початку хвилі й повертаєш один раз у фазі згортання; між цим він не потрібен. Coolify налаштований на тег `:latest`, тому Deploy означає «викоти те, що зараз найновіше на `main`». Конкретний старіший коміт — це зміна тега сервісу на `:<sha>`, тобто вже сценарій відкату.

**Порядок: бекенд, перевірка, фронт.**

```bash
# 1. Що саме поїде
git log beta..main --oneline

# 2. Є міграція серед змін? Прочитати очима — вона виконається на базі з даними тестерів
git diff beta..main --name-only -- apps/server/src/migrations

# 3. Бекенд: кнопка Deploy у Coolify.
#    Pre-deploy виконує `node dist-server/migrate.js`, далі стартує новий контейнер.

# 4. Переконатися, що поїхало саме те
curl -sI https://<api-host>/health | grep -i x-server-build-id
git rev-parse main    # має збігтися

# 5. Тільки після цього фронт.
#    УВАГА: це НЕ мерж. Оновлення бети — форс-пуш, і перед ним варто
#    зафіксувати точку відкату. Перевірено прогоном 2026-08-09 (знахідка B3).
#
#    Історична примітка: у прогоні 2026-08-09 `beta` і `main` НЕ мали
#    спільного предка (історію main колись переписали, `git merge-base`
#    порожній), тож `git merge main` падав з `refusing to merge unrelated
#    histories`. Після викатки 2026-08-10 `beta` — прямий предок `main`,
#    і той самий пуш пройшов fast-forward. Форс лишається канонічним:
#    він працює в обох випадках, а розбирати, який зараз, — зайве.
git fetch origin
git tag beta-rollback-$(date +%Y%m%d) origin/beta && git push origin --tags
git push --force origin main:beta
```

Крок 4 не формальність: `X-Server-Build-Id` несе `GIT_SHA`, вшитий у образ на збірці — це єдиний ідентифікатор релізу, бо Coolify тягне готовий образ і власного SHA не додає (див. [`buildIdHeader.ts`](../../../apps/server/src/http/buildIdHeader.ts)). Якщо заголовок показує старий SHA, Coolify віддав закешований образ, і котити фронт ще рано.

Чому бекенд перший: сервер має розуміти новий формат **до** того, як інтерфейс почне його надсилати. У зворотному порядку виникає вікно, де UI просить те, чого сервер ще не знає, — а тестери в цей момент усередині. Порядок обертається лише коли зміна щось **прибирає**: спершу деплой, що перестає писати в колонку, потім міграція, що її дропає (двофазний DROP, Hard Rule #4).

Не деплоїти в п'ятницю ввечері та в день старту місії, коли активність найвища.

### 3.2 Разові деплої фронту

Три способи для різних ситуацій.

**Форс-пуш у `beta`** — звичайний шлях, описаний вище (саме форс, не мерж — див. крок 5). Vercel бачить пуш у production-гілку й **збирає заново**, застосовуючи змінні проєкту бети зі скоупу **Production**. Це єдиний шлях, який гарантує правильні `BACKEND_URL`, `VITE_POSTHOG_KEY` і `VITE_SENTRY_ENVIRONMENT`.

> **Пастка пропущеного білда (знахідка 2026-08-10).** `apps/web/vercel.json` має `ignoreCommand` з `turbo-ignore`, і той бере базу порівняння з `VERCEL_GIT_PREVIOUS_SHA`, а без неї — з `--fallback=HEAD^1`, тобто **з одного коміта назад**. Для `main`, куди коміти падають по одному, це працює. Для `beta`, яка отримує їх пачкою, — ні: досить, щоб ОСТАННІЙ коміт у пачці був серверний (як `654bc12`, merge `BILLING_ALL_PRO`), і `turbo-ignore` вирішує, що `@sergeant/web` не змінювався. Білд пропускається мовчки, разом з усіма фронтовими фіксами пачки; у Deployments це виглядає як деплой зі статусом «Skipped». Тому в `ignoreCommand` тепер стоїть ранній вихід: на гілці `beta` білд іде **завжди**, `turbo-ignore` питають лише на решті гілок. Якщо колись побачиш пропущений білд на беті знову — перевір саме цей рядок, а разова розблокувалка — `⋯ → Redeploy` у Deployments (при ручному редеплої `VERCEL_GIT_PREVIOUS_SHA` вже виставлений і різниця рахується чесно).

**Промоут готового білда.** Vercel будує прев'ю для всіх гілок, тож коміт майже напевно вже має зібраний деплой. Його можна підняти в production без перезбірки — швидше, і котиться рівно той артефакт, який ти дивився:

```bash
vercel ls beta
vercel promote <url-деплою>
```

> **Пастка промоуту (знахідка B5, прогін 2026-08-09).** Промоут **не перезбирає** деплой — він лише переносить домени. А прев'ю-деплой зібрано зі змінними скоупу **Preview**, і `VITE_*` вкомпільовуються саме на збірці (див. § [«Що означає префікс `VITE_`»](#що-означає-префікс-vite_)). Тобто промоутнутий прев'ю-білд поїде в бету з чужим `VITE_SENTRY_ENVIRONMENT` і, ймовірно, без `VITE_POSTHOG_KEY` — рівно та розірвана воронка, від якої застерігає розділ «Змінні для бета-проєкту». Промоуть лише деплої, зібрані **в проєкті бети** зі скоупу Production; в усіх інших випадках — форс-пуш у гілку. Промоут деплою з іншого Vercel-проєкту неможливий узагалі: деплої належать проєкту.

**Миттєвий відкат.** Найважливіша команда з трьох:

```bash
vercel rollback <url-попереднього-деплою>
```

Прогнати її один раз **до** старту хвилі, на порожньому місці — знадобиться вона в найгірший момент, і тоді не буде часу читати довідку.

**Чого не робити:** `vercel --prod` із локальної теки. Ця команда деплоїть робоче дерево, а не закомічений стан — після неї те, що бачать тестери, перестає відповідати будь-якому коміту.

### 3.3 Асиметрія відкатів

Фронт відкочується за секунди однією командою. Бекенд — ні.

Відкат бекенда означає задеплоїти старіший тег образу, а міграції при цьому **не відкочуються самі**: файли `.down.sql` існують, але автоматично їх ніхто не застосовує — це ручна операція на живій базі з даними тестерів.

Практичний наслідок: до фронту можна ставитись сміливо, до бекенда — обережно. Саме тому крок «прочитати міграцію перед деплоєм» у циклі вище не декоративний.

## Фаза 4 — згорнути бету

Порядок важливий: спершу забрати доступ у даних, потім прибрати поверхні.

### 4.1 Відкликати Pro

```bash
node scripts/billing/grant-beta-pro.mjs --emails-file beta.txt --revoke --dry-run
node scripts/billing/grant-beta-pro.mjs --emails-file beta.txt --revoke
```

Записи не видаляються — статус стає `canceled`. Це історія того, що доступ був виданий і коли забраний.

### 4.2 Видалити Vercel-проєкт бети

Саме **проєкт**, не домен. Разом із ним помирають і кастомний домен, і `<project>.vercel.app`, і всі deployment-URL-и.

### 4.3 Змінити домен бекенда в Coolify

Vercel-проєкт закриває UI, але бекенд має власний публічний хостнейм, і він буде в Network-панелі у кожного тестера. Зміна домену сервісу вбиває старий хостнейм. (Раніше тут стояв аргумент «`POST /api/chat` не вимагає сесії — анонім має 3 повідомлення на добу з IP». Це вже неправда: усі AI-роути за `requireSession()` — [ADR-0086](../../04-governance/adr/0086-no-anonymous-ai-sign-in-required.md). Але хостнейм лишається публічною поверхнею для сесійних роутів колишніх тестерів, тож крок чинний.)

### 4.4 Не переюзовувати хостнейм бети

Local-first сховище скоупиться по origin. Підняти щось на тому ж хостнеймі через півроку — воскресити в тих самих людей беточні бази з несумісною схемою.

### Чого це не закриває

Тестер, який **встановив PWA**, збереже робочу офлайн-копію: оболонка в precache Service Worker-а, дані в браузері. Без AI, без синку, без оновлень — але запуститься. Відкликати це дистанційно неможливо, бо відкликання вимагало б мережі, без якої offline-first дизайн навмисно обходиться.

## Змінні для бета-проєкту

У Vercel → Settings → Environment Variables проєкту бети. Задавати для **Production**.

| Змінна                    | Обов'язкова | Де взяти                                                                                                                                                                                                                                                                                                                 |
| ------------------------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `BACKEND_URL`             | **так**     | Origin бекенда з Coolify (без шляху). Вмикає edge-проксі, і запити стають same-origin                                                                                                                                                                                                                                    |
| `VITE_POSTHOG_KEY`        | ні          | PostHog → Project Settings → Project API Key. **Той самий, що на лендінгу** — інакше воронка «клік у боті → реєстрація» розірветься на два незведені потоки                                                                                                                                                              |
| `VITE_POSTHOG_HOST`       | ні          | Дефолт `https://eu.i.posthog.com`; задавати лише якщо інстанс не EU                                                                                                                                                                                                                                                      |
| `VITE_SENTRY_DSN`         | ні          | sentry.io → Project Settings → Client Keys (DSN). Це DSN **браузера** — не той `SENTRY_DSN`, що стоїть у Coolify для сервера (див. нижче)                                                                                                                                                                                |
| `VITE_SENTRY_ENVIRONMENT` | ні          | `beta` — щоб помилки тестерів не змішались із прод-помилками                                                                                                                                                                                                                                                             |
| `VITE_APP_ENV`            | **так**     | `beta` — спільний перемикач середовища для PostHog (`environment` супер-property, `apps/web/src/core/observability/posthog.ts`) і фолбек для Sentry, якщо `VITE_SENTRY_ENVIRONMENT` не заданий (`sentry.ts`). Без нього PostHog-події бети йдуть з `environment: "production"` — невідмінні від справжнього прод-трафіку |

### Чого задавати НЕ треба

| Змінна                  | Чому                                                                                                                                                                                          |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `VITE_API_BASE_URL`     | Задаси — застосунок піде на бекенд напряму, в обхід проксі, і домен бети доведеться додавати в `ALLOWED_ORIGINS` на сервері. Лишити порожньою: тоді шляхи відносні й CORS не задіяний узагалі |
| `SITE_URL`              | Vercel підставляє `VERCEL_PROJECT_PRODUCTION_URL` сам                                                                                                                                         |
| `VITE_INTERNAL_API_KEY` | **Ніколи в прод-білді.** Це dev-only ключ; у бандлі він став би публічним (Hard Rule #20)                                                                                                     |

#### Що означає префікс `VITE_`

Vite — збирач фронтенду. Він бачить **лише** ті змінні, що починаються з `VITE_`, і **вкомпільовує їхні значення прямо в JS-бандл**, який їде в браузер. Звідси два наслідки:

- зміна `VITE_*` у Vercel UI **не діє, поки не перебілдиш** — це не рантайм-конфіг;
- усе, що з `VITE_`, стає **публічним**. Ніколи не клади туди секрет.

Тому одна й та сама річ має дві різні змінні на двох поверхнях:

| Поверхня                  | Змінна            | Де живе                           |
| ------------------------- | ----------------- | --------------------------------- |
| Сервер (Node на Coolify)  | `SENTRY_DSN`      | env сервера, читається в рантаймі |
| Браузер (бандл на Vercel) | `VITE_SENTRY_DSN` | вкомпільовується в JS             |

**Значення може бути те саме**, якщо хочеш бачити помилки сервера й браузера в одному Sentry-проєкті. Але краще завести два проєкти: у них різні стектрейси, різні алерти, і фронтові помилки тестерів не топитимуть серверні. DSN — не секрет за дизайном (він write-only, для того й придуманий, щоб лежати у браузерному коді), тож у бандлі йому нормально.

Те саме стосується `VITE_POSTHOG_KEY`: це публічний ключ проєкту, а не приватний API-ключ.

#### Що саме класти в `BACKEND_URL`

Це **публічний** URL API — той самий хост Coolify, який віддає `/api/*`. Не внутрішня адреса: middleware виконується на edge-мережі Vercel, тож ходить ззовні через інтернет.

- **Тільки origin**, без шляху. Значення проходить через `backendUrl.origin` ([`apps/web/middleware.ts`](../../../apps/web/middleware.ts)), тому `https://api-хост/api` мовчки втратить `/api`. Правильно — `https://api-хост`.
- **Тільки `https://`** (виняток — `localhost`). Інша схема робить middleware no-op, щоб проксі не даунґрейднувся на незашифрований канал.
- **Без префікса `VITE_`** — принципово: `VITE_*` потрапляють у клієнтський бандл, а `BACKEND_URL` читається на сервері й лишається там.

Значення те саме, що пішло б у `VITE_API_BASE_URL`. Різниця в тому, хто ходить на бекенд: тут — edge Vercel (запити same-origin, CORS не задіяний), там — браузер напряму, і домен бети довелося б додавати в `ALLOWED_ORIGINS`.

### Змінні для скриптів (локально, не у Vercel)

| Змінна                        | Для чого       | Де взяти                                                              |
| ----------------------------- | -------------- | --------------------------------------------------------------------- |
| `DATABASE_URL`                | обидва скрипти | Публічний URL прод-бази — той самий, що використовується для міграцій |
| `TELEGRAM_WAITLIST_BOT_TOKEN` | розсилка       | BotFather                                                             |
| `TELEGRAM_BETA_INVITE_LINK`   | розсилка       | Invite-лінк групи бети                                                |

Це секрети. Не комітити, не вставляти в чати, не друкувати в логах.
