## Рішення щодо способу впорядкування

На запит користувача дозволено фундаментальне редагування наявних ADR:

1. Не створювати corrective/superseding ADR лише для виправлення помилкового
   опису.
2. Переписувати існуючий ADR на поточний канон, коли тема ще є живим рішенням.
3. Історичні ADR не видаляти: зберегти номер, дату та історичний контекст,
   але прибрати хибну претензію на актуальний runtime-контракт.
4. Не маскувати незавершені міграції як прийняті рішення.
5. Після кожного тематичного блоку оновлювати індекс ADR, канонічну
   документацію та запускати структурні/лінкові перевірки.

## Виконання

1. Повністю класифіковано всі 90 нумерованих ADR; пропуски `0029`, `0040` і
   `0056` лишаються історичними, нових номерів для «виправлень» не створено.
2. Відредаговано 35 ADR-файлів: AI/model/cache/quota, authz/PII,
   OpenAPI/sync/jobs/n8n, billing/cash, product-ledger/day-key та agent/tooling
   рішення. Живі ADR тепер відрізняють executable contract від target або
   operations pending; історичні не прикидаються поточним runtime.
3. `README.md` ADR синхронізовано з переписаними статусами й короткими
   резюме; TEMPLATE вимагає `Last validated` і `Next review`.
4. Узгоджено канонічні Hub/AI-memory і nutrition документи, а також відновлено
   повну документаційну навігацію після upstream deletion старих work-доків:
   посилання ведуть на immutable GitHub permalink, а generated daily artifacts
   регенеровано штатно.

### Свідомо не вигадані відповіді

ADR не перетворюють target на факт: RLS, reverse trial/annual checkout,
production provider activation, cash ledger delivery, goal-period calendar
anchor, reminder clock policy та backfill-marker UI лишені явними
product/operations decisions. Пропозиції без чинної реалізації (`0003`,
`0018`) і документи, що взагалі не є архітектурними рішеннями (`0054`, `0063`),
правильно перекласифіковано або позначено історичними, а не отримали штучний
runtime contract.

5. Перевірити ADR graph, внутрішні посилання, generated docs, freshness та
   hard-rules registry. Для docs-only зміни full application build не є
   релевантним сигналом.

## Межі аудиту

Цей документ є робочим аудитом, а не новим архітектурним рішенням продукту.
Він не затверджує автоматично RLS, нові payment semantics, увімкнення AI
memory, pantry/goal cutover або cleanup legacy tables/routes — ці питання
мають бути або підтверджені поточним кодом, або винесені як явно відкриті
рішення.
