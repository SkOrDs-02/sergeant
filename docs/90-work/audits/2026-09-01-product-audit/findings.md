## Як писати знахідку

- **ID** — `<вимір>-<номер>`: `LOG` логіка · `FUN` функціональність · `UX` ·
  `VIS` візуал · `SLOP` анти-слоп · `TXT` текст · `JRN` шлях юзера · `AI` ·
  `CALC` розрахунки · `A11Y` · `PERF` · `SYNC` · `SEC` · `CI` (червоні гейти
  на `main`, знайдені автоматичним базисом). Номер наскрізний у
  межах виміру. ID стабільний: ним називаються коміти й PR.
- **Severity:** `blocker` (втрата даних, білий екран, неможливо завершити
  основний шлях, гроші порахувані неправильно) · `major` (функція не працює
  або бреше, обхід є) · `minor` (працює, але з тертям) · `polish`
  (косметика, копі).
- **Стан:** `описано` → `підтверджено` (відтворено вдруге або іншим акаунтом)
  → `у роботі #PR` → `виправлено #PR` (верифіковано наживо) → `закрито`.
  Окремо: `знято` (помилка виміру, з поясненням) і `рішення власника`
  (продуктова розвилка, чекає вибору).
- **Доказ обовʼязковий:** маршрут, акаунт, кроки, очікуване / реальне,
  консоль або мережа, скріншот (де є), `file:line` кореня, якщо відомий.
  Знахідка без відтворюваних кроків — це спостереження (§ нижче), не баг.
- Не дублювати відкриті знахідки попередніх аудитів — посилатись на них
  (§ «Успадковані відкриті»).

### LOG-1 — чат-tool `habit_stats` рахує стрік жорстко [major]

**Поверхня:** `apps/web/src/core/lib/chatActions/routineActions.ts:538-560`.
**Реальність:** цикл по `getKyivDayKey(now - i*DAY_MS)`, `currentStreak = 0`
на кожному дні без відмітки; ні `pauseIntervals`, ні `skips`, ні

`routine-domain` не імпортується взагалі. UI (`useRoutineDerivedData.ts`)
рахує за гнучкою моделлю канону §4 — тобто «скільки в мене стрік?» у чаті

**Чому major, не blocker:** втрати даних немає, відповідь — читання. Але це
той самий B-3 з product-knowledge-overview, який вважався закритим після
переходу UI на `flexStreak.ts`: коментар у `flexStreak.ts:6-8` чесно каже,
що старий `streakForHabit` живе, «доки всі споживачі не перемкнені» — і
споживач у чаті не перемкнений.
**Фікс:** `habit_stats` → `flexibleStreakBreakdown` + `habitCompletionRate`
з тим самим day-anchor, що в UI; тест «чат = UI» на звичці з паузою.
**Стан:** підтверджено (адверсарний пас по коду), кроки в браузері — Ф4.

### SYNC-3 — ре-пуш ручних витрат Фініка по колу [blocker]

**Що видно:** `sync_op_log` для Q3 (60 витрат, 30 відміток, 9 продуктів,
1 звичка) — **3 385 ops**, з них `finyk_manual_expenses insert` — **3 237**;
на кожен id витрати ~80 ops із 80 різними `client_ts` від 3 пристроїв.
Сідер (`ec2b…`) дав рівно 60; два пристрої, що лише **читали** (свіп після
логіну `7b32…` — 1 885, AI-драйвер `c6ed…` — 1 440), пушили безперервно:
360–720 ops на 5 хв = 72/хв на пристрій, тобто рівно стеля `api:v2:sync`.
Пуші припинились о 19:56:38 — коли закрились браузери. Решта таблиць
(routine, nutrition) — по одному op на запис, циклу немає.
**Наслідки:** бейдж «Синхронізація · 60 в черзі» не спорожнює ніколи; 429
на push/pull (звідси SYNC-1 alert і SYNC-2 «черга росте»); LWW-мітки ручних
витрат переписуються щохвилини (будь-яка справжня правка з іншого пристрою
програє чи виграє випадково); трафік і батарея; op-log росте лінійно з часом
на кожному відкритому пристрої.
**Ймовірний механізм:** pull → `applyPullOp`/`refreshCachesAfterPull` для
`finyk_manual_expenses` (обидва в allowlist) оновлюють LS/warm-кеш модуля →
dual-write екстрактор бачить «новий» запис → `triggerManualExpenseSqliteMirror`
(`sqliteWriter/index.ts:363-373`, blob-upsert з `JSON.stringify(expense)`)
→ `enqueueOutboxUpsert` → push з новим `client_ts` → сервер приймає як
новішу версію → інші пристрої (і цей самий на наступному pull) отримують op
знову. Тобто pull-apply не позначений як «не мій запис», і blob-upsert не
порівнює вміст перед тим, як класти в outbox.
**Фікс:** (1) у finyk-адаптері pull-apply писати SQLite напряму, без
dual-write-екстрактора (як routine/nutrition); (2) blob-upsert — no-op, якщо
`data_json` не змінився; (3) тест «pull 60 рядків → outbox порожній».
**Стан:** підтверджено на трьох пристроях; репро без сідера — Q2/Q6 у Ф3.

**Масштаб по `sync_op_log` (2026-09-01, після всіх прогонів):**
`finyk_manual_expenses insert` — Q3: 3 357 ops на 60 витрат з 3 пристроїв;
Q8: 283 applied + **12 rejected `lww_conflict`** на 10 витрат з одного
пристрою; Q2: 85 на 10 з 2 пристроїв; Q4: 16 на 4. Жодна інша таблиця так не
поводиться (комора Q3 — 45 ops на 45 рядків). `lww_conflict` на власних
повторних push-ах — доказ, що клієнт шле той самий рядок зі старішим
`client_ts`, ніж уже застосований. Побічний ефект — голодування черги:
у Q2 три з пʼяти продуктів комори (яйця, яблука, олія) так і не дійшли до
сервера до закриття вкладки сідера (op-лог має лише молоко ×2 і гречку).

### SYNC-2 — ліміт синку 60/хв досяжний одним пристроєм; черга росте мовчки [major]

**Що видно:** `seed-light` для Q2 (реальний UI, один контекст, ~70 с):

(`routes/sync.ts:38`); клієнтський writer не має обробки 429/`Retry-After`

для автентифікованого користувача або рахувати push і pull окремо.
**Стан:** підтверджено трейсом; повторити на Q6 (два пристрої) у Ф3.

**Кроки:** Q5 (Pro) або Q3, `/chat`: «Скільки я витратив за цей тиждень?» /

OpenRouter = `[thinking, redacted_thinking, tool_use{caller,id,input,name,type}]`.
`ToolUseBlockSchema` (`packages/shared/src/schemas/api.ts:308-315`) —
`.strict()`, поле `caller` невідоме → блок відкинуто;

thinking Anthropic вимагає повертати їх незмінними (окремий ризик).
**Фікс:** на клієнті — не викидати блок через невідоме поле, а

**Стан:** підтверджено; блокує Ф4 (память, деструктивні confirm, undo
