- Obs-005: **ЧАСТКОВО СПРОСТОВАНО 2026-08-05 (нижче).** Первісне формулювання: «синк даних модулів на новий пристрій працює (тренування A, звичка A відновились)». - Obs-006: Обмеження стенда — Browser pane емулює 375×812, але `pointer: coarse` = false, тож 44px touch-target safety-net (діє лише під coarse) інструментально НЕ верифіковано. - Obs-007 · **підтверджено кодом і пробою API (2026-08-05)**: «Pro відкриває … CloudSync між пристроями» — неправда на рівні реалізації. Синк не гейтиться по тарифу ніде (див. Вихідна нотатка: Продуктова неузгодженість обіцянок синку: сторінка входу — «Все працює локально. Акаунт потрібен лише для синхронізації між пристроями»; Налаштування → Тариф — «Pro відкриває … CloudSync між пристроями»; факт — синк модульних даних працює на Free. Три різні історії — вирішити канонічно.
- Obs-009 · **виправлення Obs-005, потребує окремої перевірки**: твердження «синк на новий пристрій працює» не було доведене. У тому тесті дані А були **локальними від початку** (тренування зроблено анонімно в тому ж браузер-профілі, потім зареєстровано акаунт) — сервер там не опитувався. Спроба чистого тесту 2026-08-05 (стерти локальне сховище → повторний вхід) показала: після входу **не летить жодного `/api/v1/me` чи sync-pull**, тож канонічний SQLite лишається порожній і всі чотири картки хаба показують обіцянку. **З'ясовано 2026-08-05 (код + пряма проба API):**

1. **Це НЕ Pro-гейт.** Гейта по тарифу немає ніде: роут `apps/server/src/routes/sync.ts:35-54` вішає лише `setModule` + `rateLimitExpress` + `requireSession()`; ні в `syncV2Pull`, ні в клієнтських `bootSyncEngineReader`/`createSyncEngineReaderRuntime` жодної перевірки плану. **Пряма проба:** сесія Free-акаунта `qa-a-empty` → `GET /api/v2/sync/pull?since=0` → **HTTP 200 з повним op-log** (тренування, items тощо). Тобто сервер і синк для Free працюють повністю.
2. **Чому в моєму тесті не було pull-у** — не через синк: зламаний персистер (Obs-010) не змонтував RQ-клієнт → `me` не фетчився → `status !== "authenticated"` → `AnonymousDataMigrationProvider` віддавав ранню гілку, а `bootSyncEngineReader()` живе **тільки** в `.then()` цього гейта. Весь authed-boot ланцюг висить на `status === "authenticated"`.
3. **Наслідок для F-007:** сервер віддає дані, тож «новий пристрій» упирається не в бекенд. Перевірити на чистому профілі лишається, але **презумпція тепер — синк робочий**.

**Знайдено попутно — ✅ ВИПРАВЛЕНО 2026-08-05** (обидві діри мали спільний корінь: sync-runtime жив у success-гілці переносу анонімних даних). Фікс: `bootSyncForUser()` у `AnonymousDataMigrationProvider` піднімає **обидва** runtime у `.finally()` — тобто на успіху, на провалі й на «нема чого переносити», — попередньо перемкнувши SQLite-партицію на юзера. +3 регресійні тести.

- **Reader стартує лише з `.then()` міграції** (`AnonymousDataMigrationProvider.tsx:120-133`). Якщо `migrateAnonymousDataToProfile` **впаде**, `bootSyncEngineReader()` не викликається взагалі, а кнопка «Відкласти» (`defer`) лише ховає блокуючий екран і reader теж не піднімає. Сесія тихо працює **без жодного pull-у** до успішного retry.
- **Writer має рівно один продакшн call-site** — `anonymousDataMigration.ts:310`, і він **після** раннього `return` для `snapshot.length === 0` (рядки 263-266). Тобто вхід на пристрої без анонімних даних не піднімає writer, що дренить op-log outbox; `notifyOutboxEnqueued` при непіднятому runtime — свідомий no-op. Дані все одно доїжджають на сервер (мій прийом їжі доїхав, `nutrition_meals` 2→3) — вочевидь через dual-write REST-каналом, тож це може бути by design. Але пару «reader без writer» варто підтвердити свідомо.
