# Браузерна QA `apps/web` перед закритою бетою

> **Last touched:** 2026-09-03 by @claude. **Next review:** 2027-10-16.
> **Status:** Active

Мета: пройти `apps/web` очима анонімного користувача й перевірити push-контур
перед закритою бетою. Знайдені проблеми задокументовані; полагоджені лише
очевидні дрібниці (текст і відсутні стани), архітектурні — описані.

## Умови прогону

| Гілка          | `claude/web-qa-browser-check-51396e` (worktree від `c29915c5b`)            |

**Обмеження середовища, які треба тримати в голові при читанні звіту.**
Dev-сервер не віддає COOP/COEP, тому SQLite-WASM працює не на OPFS, а на
`kvvfs` поверх `localStorage` (у консолі — явне повідомлення про це). Панель
браузера не композитила кадри, тому піксельні кліки не доходили; взаємодія
йшла через DOM-виклики. Скріншотів немає з тієї ж причини.

## Блокери

### 1. Дані Рутини ніколи не синхронізуються з сервером

`routineUid("hab")` ([`packages/routine-domain/src/storage.ts:37`](../../../packages/routine-domain/src/storage.ts)) видає
id виду `hab_4a1e6194-4528-4357-bfde-765750a15a87`. Колонка
`routine_habits.id` у Postgres має тип `uuid NOT NULL`, тому вже перший
`SELECT ... WHERE id = $1` падає з `22P02` і операція повертається як
`apply_failed`.

Доказ — два ідентичні op-и в одному `POST /api/v2/sync/push`, різниця лише в id:

```json
{
  "accepted": 1,
  "results": [
    {
      "idempotency_key": "qa_vwe7yv29wkh",
      "status": "rejected",
      "reason": "apply_failed"
    },
    { "idempotency_key": "qa_3qz8ayr9h1x", "status": "applied" }
  ]
}
```

Перший — `hab_<uuid>`, другий — голий `<uuid>`.

Це **не** дефект переносу анонімних даних: той самий id іде у звичайний
push із [`adapter.ts:333`](../../../apps/web/src/modules/routine/lib/sqliteWriter/adapter.ts), тобто
жодна звичка жодного залогіненого користувача ніколи не доїжджає до
сервера. Локально все виглядає справним — помилка осідає рядком у
`sync_op_outbox` і нікуди не спливає.

Уражені **всі чотири таблиці Рутини**, не лише звички. `routineUid` викликається
з трьома префіксами ([`reducers.ts`](../../../packages/routine-domain/src/reducers.ts)):
`tag_` (рядок 51), `cat_` (72), `hab_` (102). `routine_entries` має проблему у
важчій формі: id будується як `buildCompletionRowId(habitId, dateKey)` →
`hab_…|2026-08-01|…`, що не є uuid і поготів. Прогін `POST /api/v2/sync/push`
по кожній таблиці:

| op                                             | результат      |
| ---------------------------------------------- | -------------- |
| `routine_tags` з `tag_<uuid>`                  | `apply_failed` |
| `routine_tags` з голим `<uuid>` (контроль)     | `applied`      |
| `routine_categories` з `cat_<uuid>`            | `apply_failed` |
| `routine_entries` з `hab_<uuid>\|<дата>\|done` | `apply_failed` |
| `routine_habits` з `hab_<uuid>`                | `apply_failed` |
| `routine_habits` з голим `<uuid>` (контроль)   | `applied`      |

Фінік цим не уражений — витрата, створена в тому ж прогоні, синхронізувалась
без проблем. Інші модулі точково не перевіряв; `nutrition_meals` має
legacy-фолбек `meal_mig_…` ([`nutritionLog.ts:44`](../../../packages/nutrition-domain/src/nutritionLog.ts)),
який варто перевірити тим самим методом.

Наслідок для бети: «Рутина» не має резервної копії взагалі — ні звички, ні теги,
ні категорії, ні відмітки виконання. Зміна пристрою губить усе, і користувач про
це не дізнається.

Варіанти рішення — див. розбір нижче в § «Варіанти вирішення».

### 2. Провал переносу анонімних даних блокує весь застосунок

[`AnonymousDataMigrationProvider`](../../../apps/web/src/core/durability/AnonymousDataMigrationProvider.tsx)
рендерить `children` лише у стані `ready`. У стані `failed` користувач бачить
повноекранне

> Не вдалося завершити перенесення. Дані на цьому пристрої не видалено й вони
> ще не захищені синхронізацією. **[Повторити]**

і більше нічого. Ні «продовжити без переносу», ні виходу. Перевірено, що
блокуються навіть публічні маршрути: `/legal/privacy` у цьому стані показує
той самий екран.

Відтворення (реальний прогін цієї сесії): анонімно створити витрату й звичку
→ зареєструватись із того ж браузера. Через блокер №1 звичка отримує
`apply_failed`, `assertServerAcknowledged` кидає
`Anonymous migration is not server-confirmed`, і застосунок замикається. Кнопка
«Повторити» веде в той самий цикл, бо причина детермінована.

Дані при цьому не втрачаються — вихідні рядки навмисно не видаляються до
підтвердження сервером. Тобто це блокування доступу, а не втрата даних, але
для беті-користувача різниця невелика: застосунок мертвий після реєстрації.

Дві незалежні речі варті виправлення навіть після фіксу №1: гейт має мати
шлях «продовжити, перенесу пізніше», і він не повинен накривати маршрути,
яким перенос не потрібен (юридичні сторінки щонайменше).

## Виправлено в цій гілці

Правки навмисно вузькі: тексти й відсутні стани, без зміни роутингу,
залежностей чи архітектури.

**3. 401 без сесії читався як «Mono відхилив токен».**
`POST /api/v1/mono/connect` віддає 401 у двох різних випадках: наш власний
session-gate (`{"error":"Потрібна автентифікація"}`) і реальне відхилення
токена банком (`{"code":"MONO_TOKEN_INVALID"}`). Клієнт розрізняв їх ніяк і
показував анонімові «Mono відхилив токен. Перевір, чи скопіював правильний» —
тобто відправляв людину з бездоганним токеном перегенеровувати справний токен.
Тепер гілки розділені по `code`, для session-401 є окрема копія. Додано тест
на кожну гілку.

**5. Екран переносу використовував неіснуючі токени.**
`bg-background`, `text-foreground`, `bg-card`, `text-muted-foreground` не
зареєстровані в `packages/design-tokens/tailwind-preset.js` (там `bg`, `text`,
`panel`, `line`, `muted`). Екран рендерився без фону й з успадкованим кольором
тексту. Замінено на реальні токени, `text-sm` → `.text-style-body` (Hard Rule
#16). Ті самі неіснуючі класи трапляються в
[`StrategyPage.tsx`](../../../apps/web/src/pages/strategy/StrategyPage.tsx) —
не чіпав, інша поверхня.

**6. Кнопка «Дозволити» при `permission = denied`.**
Умова була `!== "granted" && !== "unsupported"`, тобто кнопка показувалась і в
заблокованому стані — поруч із підказкою «відкрий налаштування браузера».
`Notification.requestPermission()` у цьому стані резолвиться миттєво тим самим
`denied`, не показуючи промпт, тож кнопка не могла спрацювати ніколи. Тепер
кнопка лише для `default`, для `denied` — конкретніша інструкція.

**7. Тогл пушів зникав мовчки.**
`PushNotificationToggle` повертав `null`, коли Web Push недоступний. Саме це
бачить користувач iPhone у вкладці Safari — фіча просто відсутня, без натяку,
що вона зʼявиться після «На початковий екран». Тепер рядок лишається і пояснює:
для iOS/iPadOS — інструкція про початковий екран, для решти — що браузер не
підтримує пуші й що нагадування всередині застосунку працюють без них.

Верифікація: `pnpm --filter @sergeant/web typecheck` — чисто;
`vitest run` по зачеплених файлах — 6/6 + 9/9 + решта зелені;
`playwright -c playwright.pwa-regression.config.ts` — результат ідентичний
базовому (перевірено через `git stash`), тобто правки нейтральні.

**8. ~~`@critical` тест `pwa-regression` червоний на обох проєктах.~~ — Закрито 2026-09-03.**
Корінь був у припущенні тесту, не в коді. `ModuleHeader` навмисно рендерить
назву модуля як `<p data-testid="module-header-title">`, а не заголовок: хром
оболонки стоїть у DOM ПЕРЕД сторінковим `<h1>` і роллю `heading` інвертував

Тест же чекав `getByRole("heading", { name: "Фінік" })` — ролі, якої там не

_Оригінальна знахідка:_ `module headers keep their canonical names after

`getByRole("heading", { name: "Фінік" })` після переходу на legacy-діплінк

цим змінам. Другий тест, `completing module selection survives a hard PWA-style
reload`, один раз упав на `mobile-safari` і двічі пройшов — схоже на флейк за
таймінгом. Корінь падіння `module headers` не ізолював: це або таймінг
редіректу `?module=` → `/finyk` разом із ліниво вантаженим чанком на 5-секундному
`expect`, або втрачена роль `heading`. Варте окремого тріажу до бети — червоний
`@critical` контур перед релізом читається погано незалежно від причини.

([`requireAnthropicKey.ts`](../../../apps/server/src/http/requireAnthropicKey.ts)):
вони віддають 503 з нейтральним `error` і маркером у `body.code`. Прокидати
`code` окремо не довелось: обидва викликачі (`useChatSend`, `useInlineAiRail`)
уже передавали `body.code` третім аргументом; мертвою гілку робила лише умова.
Тепер `friendlyApiError` звіряється по `code === "ANTHROPIC_KEY_MISSING"`
незалежно від статусу й тексту. Тест у
[`hubChatUtils.test.ts`](../../../apps/web/src/core/lib/hubChatUtils.test.ts)
годує реальну форму відповіді сервера (червоний до фіксу) і перевіряє, що
503 без коду далі віддає серверний текст.

_Оригінальна знахідка:_ `friendlyApiError` у [`hubChatUtils.ts:67`](../../../apps/web/src/core/lib/hubChatUtils.ts)
перевіряє `status === 500`, а сервер віддає **503**. Крім того, до мапера
доїжджає лише `body.error` (`serverMessage`), а маркер лежить у `body.code`
(`ANTHROPIC_KEY_MISSING`), тож регексп не має за що зачепитись у жодному разі.
Правка вимагає прокинути `code` через шар помилок — це не текстовий фікс, тому
не робив. Наслідок сьогодні: розробник із незаповненим ключем бачить
користувацьке «AI-помічник тимчасово недоступний» і шукає проблему не там.

## Що працює як задумано

**Анонімний доступ.** Гейта немає ніде: онбординг проходиться, усі чотири
модулі відкриваються, записи створюються. Перевірено створення витрати (137 ₴,
Фінік) і звички (Рутина) без акаунта. Перший екран взагалі не auth — це
`/welcome` з вибором модулів, а `AuthPage` з «Поки що пропустити» видно лише
тим, хто свідомо тисне «У мене вже є акаунт».

**AI-асистент аноніму не блокується — і це навмисно.**
`POST /api/v1/chat` резолвить сесію як `sessionUser ?? null` і працює далі
([`chat.ts:278`](../../../apps/server/src/modules/chat/chat.ts)), тож
повідомлення «потрібен акаунт» тут було б неправдою. Локально відповідь — 503
через відсутній ключ. Єдиний 401 на цьому шляху — `GET /chat/usage` (лічильник
квоти), і він падає тихо, не ламаючи чат.

**Дозвіл на пуші не просять на вході.** `Notification.requestPermission()`
викликається рівно у двох місцях, обидва — обробники дії користувача
(`NotificationsSection`, `usePushNotifications.subscribe`). Жодного виклику на
буті. Антипатерн відсутній.

**Серверний бік підписки.** `POST /api/v1/push/register` кладе рядок у
`push_subscriptions` (не в `push_devices` — там native FCM/APNs токени),
`unregister` проставляє `deleted_at`. Перевірено напряму через API + psql.

**Запасний варіант для нагадувань.** Крім web-push існує локальний контур:
`useModuleReminder` у сторінці та окремий цикл у Service Worker, який показує
нотифікації через `registration.showNotification`. Тобто нагадування не
залежать від сервера. Застереження: обидва шляхи все одно вимагають
`Notification.permission === "granted"`, тому у вкладці Safari на iOS не
працюють так само, як і пуші. І копія «навіть коли застосунок закрито»
спирається на пробудження SW, яке браузер не гарантує — перевірити це в
поточному середовищі я не міг.

> **Резолюція (2026-08-02).** Застереження вище виявилось точним, і навіть
> м'якшим за реальність: цикл у Service Worker не «не гарантований», а
> непрацездатний у принципі. Браузер вбиває неактивний SW за ~30 секунд, а
> стан звичок жив у його памʼяті й приходив туди `postMessage`-ом з відкритої
> сторінки — після перезапуску перевірка виходила на першому ж рядку. Цикл
> прибрано разом із його файлом у `apps/web/src/sw/`; нагадування тепер
> шле сервер (`apps/server/src/lib/reminders/`), тож вони таки залежать від
> нього — і саме тому працюють при закритому застосунку. Деталі:
> [`notifications.md`](../../02-engineering/architecture/notifications.md),
> commit `347dcf0` _«нагадування шле сервер, а не таймер у сервіс-воркері»_.
> Абзац вище лишається як опис стану на дату аудиту.

## Не перевірено

- **Повний цикл пушів у Chrome desktop** (запит дозволу → підписка → отримання
  тестового пуша → відписка) через UI. Профіль браузера мав `denied`, змінити
  дозвіл із коду неможливо. Серверний бік покрито окремо (див. вище), клієнтський
  ланцюжок `subscribeToWebPush` → `pushRegister` — ні.
- **Реальний iPhone.** Логіку гілкування перевірено за кодом і тестами, поведінку
  на пристрої — ні. Симуляція user-agent не відтворює відсутність `PushManager`
  у вкладці Safari, тому окремого прогону не робив, щоб не видавати за перевірку
  те, що нею не є.
- **Успішна відповідь AI** — потрібен `ANTHROPIC_API_KEY`.

## Що виправлено по блокерах (2026-08-01)

Власник обрав варіант **A** для блокера №1 і **A + C** для блокера №2 з
розбору нижче. Обидва реалізовані в цій же гілці.

### Блокер №1 — міграція 094

[`094_routine_pk_text.sql`](../../../apps/server/src/migrations/094_routine_pk_text.sql)
переводить `id` у `routine_habits` / `routine_tags` / `routine_categories` /
`routine_entries` з `uuid` у `text`; drizzle-модель
(`packages/db-schema/src/pg/routine.ts`) і снапшот-тест підтягнуто слідом.
Down-міграція навмисно падає, якщо в таблицях уже є клієнтські id — тихо
викинути дані користувача при відкаті гірше, ніж впасти.

Перевірено на живій БД тим самим `POST /api/v2/sync/push`, яким баг знайдено:

| op                                             | до             | після     |
| ---------------------------------------------- | -------------- | --------- |
| `routine_habits` з `hab_<uuid>`                | `apply_failed` | `applied` |
| `routine_tags` з `tag_<uuid>`                  | `apply_failed` | `applied` |
| `routine_categories` з `cat_<uuid>`            | `apply_failed` | `applied` |
| `routine_entries` з `hab_<uuid>\|<дата>\|done` | `apply_failed` | `applied` |

`GET /api/v2/sync/pull` віддає ці рядки з незміненими id (потрібен заголовок
`X-Origin-Device-Id`, який клієнт завжди шле). Побічно перевірено UTF-8:
кирилиця проходить round-trip без втрат.

### Той самий баг у Харчуванні — міграція 095

Перевірка «а де ще?» знайшла той самий клас у коморі й раціоні. Уражені
чотири таблиці, не дві, як фіксував тех-борг: `nutrition_pantries` (`home`,
`p_<ms>_<idx>`), `nutrition_pantry_items` (`<pantryId>::<idx>::<name>`),
`nutrition_meals` (`meal_mig_…`), `nutrition_recipes` (`rcp_ai_<hash>`). Усі
чотири давали `apply_failed`; після
[`095_nutrition_pk_text.sql`](../../../apps/server/src/migrations/095_nutrition_pk_text.sql)
— усі `applied`. Разом із PK переведено `pantry_id` і
`nutrition_prefs.active_pantry_id`, FK знято й повернуто в одній транзакції.

Фінік і Фізрук цим не уражені — їхні клієнти генерують голі UUID (перевірено
кодом і живим push-ем витрати).

### Блокер №2 — вихід із гейта + виняток для публічних сторінок

`AnonymousDataMigrationProvider`:

- на провалі поруч із «Повторити» зʼявилась «Продовжити, перенесу пізніше»;
  рішення зберігається (`hub_anon_migration_deferred_v1:<userId>`), тож
  наступний старт не замикає застосунок знову;
- замість повного екрана лишається тонка попереджувальна смуга «Дані ще не
  перенесено в профіль» із дією «Спробувати зараз» — щоб про незавершений
  перенос не забули;
- `/legal/privacy`, `/legal/terms`, `/legal/cookies`, `/legal/offer` і
  `/status` більше не блокуються ніколи; перенос там триває у фоні.

Покрито тестами: відкладення, памʼять про відкладення між монтуваннями, і
доступність юридичного маршруту при незавершеному переносі.

**Доповнення 2026-08-05.** Гейт більше не показує «Переносимо дані в профіль…»
на кожному старті. Панель зʼявляється, лише коли розвідка справді знайшла
анонімні рядки (`onTransferStart` з `migrateAnonymousDataToProfile`), провалилась
або затягнулась понад 500 мс; на найчастішому шляху «переносити нема чого» видно
звичайне порожнє полотно буту. Рендер `children` при цьому лишається
заблокованим, бо під час розвідки активна SQLite-партиція перемкнута на
анонімну. Причина правки: гейт монтується на КОЖНОМУ старті авторизованої сесії,
а перед ним ще й йдуть автоматичні перезавантаження з `chunkReload` — і
користувач бачив тривожний текст про перенесення даних там, де жодного
перенесення не було.

**Верифікація фіксів:** `pnpm --filter @sergeant/web typecheck` і
`@sergeant/server typecheck` — чисто; 43/43 тести по зачеплених зонах;
`db-schema` — 552/555 (три падіння передують гілці: `feedback_entries` у
drift-тесті та снапшот telegram-waitlist, перевірено на чистій базі);
`pnpm lint:migrations` — зелено; eslint і prettier по всьому діфу — чисто.

## Варіанти вирішення

### Блокер №1 — конфлікт формату id

| Варіант                                                                 | Плюси                                                                                                          | Мінуси                                                                                                                                                                                                       |
| ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **A. Колонки Рутини `uuid` → `text`**                                   | Одна міграція, нуль змін у клієнті, наявні локальні дані їдуть як є. Знімає й `routine_entries` без винаходів. | Втрата валідації типом на рівні БД. Розходження з рештою таблиць, де `uuid` лишається.                                                                                                                       |
| **B. Клієнт переходить на голі uuid**                                   | Схема лишається строгою й однорідною.                                                                          | Потрібна локальна міграція id у SQLite усіх наявних пристроїв із перезшиванням посилань (`habit_id` у відмітках, `tag_ids`, `category_id`). `routine_entries` це не рятує — його id навмисно детермінований. |
| **C. Сервер нормалізує id на вході** (зрізає префікс / UUIDv5 із рядка) | Клієнта не чіпаємо, локальні дані не мігруємо.                                                                 | Прихована трансформація в шарі синку: id на клієнті й на сервері різні, дебаг ускладнюється. Потребує зворотного мапінгу на pull.                                                                            |

Про `routine_entries` окремо: його id — `<habitId>|<дата>|<стан>`, тобто
навмисно детермінований ключ дедуплікації. Перевести його на випадковий uuid
не можна, не зламавши дедуп; лишається або `text`-колонка (варіант A), або
детермінований UUIDv5 від того самого рядка (частковий варіант B).

Рекомендація: **A** — найкоротший шлях до працездатної бети без міграції даних
на пристроях користувачів. Повернення до строгих `uuid` (варіант B) можна
зробити окремою ініціативою, коли буде час на міграцію id.

Що б не обрали, до фіксу варто додати захист від повторення: `apply_failed`
сьогодні осідає тихо, тому баг і прожив непоміченим. Мінімум — лічильник
відхилених op-ів у логах/алертах; краще — smoke-тест на кожну таблицю з
реальним клієнтським форматом id (той самий прогін, яким це знайдено).

### Блокер №2 — гейт переносу

Задум гейта правильний: не видаляти вихідні рядки, поки сервер не підтвердив
запис. Проблема лише в тому, що «перенос не завершився» прирівняно до
«застосунком користуватися не можна».

| Варіант                                                              | Плюси                                                                 | Мінуси                                                                        |
| -------------------------------------------------------------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| **A. Додати «Продовжити, перенесу пізніше»**                         | Мінімальна правка. Користувач не замкнений, дані на місці.            | Потрібен видимий індикатор «перенос не завершено», інакше про нього забудуть. |
| **B. Не блокувати взагалі — банер замість повноекранного стану**     | Найм'якший UX, застосунок завжди доступний.                           | Ризик, що користувач роками ходить із неперенесеними даними й не помічає.     |
| **C. Звузити гейт до маршрутів, яким перенос потрібен**              | `/legal/*` і решта публічного лишаються доступними за будь-яких умов. | Не розвʼязує головного: модулі все одно заблоковані.                          |
| **D. Часткова толерантність: переносити, що вдалося, решту в чергу** | Найчесніше щодо даних.                                                | Найбільше роботи; потрібен окремий стан «частково перенесено».                |

Рекомендація: **A + C** разом. Дешево, знімає замикання, і публічні сторінки
перестають залежати від стану синку.
