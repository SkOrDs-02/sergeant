# Відстеження свіжості документації

> **Last touched:** 2026-10-01 by @claude (дашборд свіжості більше не комітиться, рішення власника; раніше того ж дня — `docs-daily-brief.yml` лише вручну, § «Чому `docs/today.md` виключено»). **Next review:** 2026-12-16.
> **Status:** Active

Ця система гарантує, що критична документація лишається актуальною — у документах вшиваються freshness-заголовки, а `docs-freshness.yml` (щопонеділка і вручну, [ADR-0102](../adr/0102-github-actions-ci-and-autodeploy.md)) відкриває GitHub-issue для протермінованих файлів. **Список відстежуваних файлів автоматично виводиться з самого репо** — нічого додавати в JSON-allowlist не треба.

---

## Як це працює

1. **Freshness-заголовок** — у кожному відстежуваному документі біля початку (перші 15 рядків) є blockquote канонічного формату:

   ```markdown
   > **Last touched:** 2026-04-27 by @Skords-01. **Next review:** 2026-07-26.
   ```

2. **Auto-discovery** — `scripts/docs/freshness-config.mjs` через `git ls-files '*.md'` сканує кожен `.md`, шукає канонічний заголовок та автоматично додає файл до списку відстежуваних із `defaultCadenceDays = 90`. Виключення (templates, ADR, code-adjacent README) — у `excludeGlobs` із розумних дефолтів.

3. **Конфіг** — `scripts/docs/freshness-config.json` містить лише **відхилення від дефолтів**:
   - `cadenceOverrides` — інший cadence для конкретних файлів (60 днів для runbook, 180 для аудитів);
   - `explicitInclude` — файли без заголовка, які треба тримати у списку (рідкість);
   - `explicitExclude` — файли, які навмисно вимкнено;
   - `excludeGlobs` — додаткові glob-патерни поверх дефолту.

   ```json
   {
     "cadenceOverrides": {
       "docs/operations/observability/runbook.md": 60,
       "docs/work/specs/audits/archive/ux-audit-2025.md": 365
     }
   }
   ```

4. **Workflow** — `.github/workflows/docs-freshness.yml` запускає `scripts/docs/check-freshness.mjs` щопонеділка і вручну через `workflow_dispatch` (на PR не біжить з 2026-09-30, [ADR-0102](../adr/0102-github-actions-ci-and-autodeploy.md)). Для кожного файлу з простроченим **Next review** скрипт відкриває GitHub-issue з лейблами `documentation` і `freshness-overdue`. Той самий прогін збирає HTML-дашборд і вивантажує його артефактом `docs-freshness-dashboard` (див. [§ Дашборд](#дашборд)).

5. **Coverage-gate** — `node scripts/docs/check-freshness.mjs --check-coverage` фейлиться, якщо в репо знайдено `.md` без freshness-заголовка, який при цьому не виключено через `excludeGlobs` / `explicitExclude`. Запускається в pre-merge CI, щоб новий док не пройшов без header-а.

6. **Cadence-gate** — `node scripts/docs/check-freshness.mjs --check-cadence` фейлиться, якщо бодай в одного відстежуваного дока **Next review** уже в минулому. Живе в **окремій джобі** `Docs freshness cadence` (`.github/workflows/docs-automation.yml`) і навмисно **не** входить у `pnpm lint`. Причина — не косметика: каденс червоніє від плину часу, без жодної зміни в коді, а всередині `pnpm lint` він валив джобу `check` **до** typecheck, test, build і бандл-гейта `size-limit`, тобто глушив найцінніші перевірки; всередині джоби `markdown-links` — глушив перевірку дашборда. Це рівно той антипатерн, який AGENTS.md § Performance budgets формулює як «гейт, що стоїть у кроках після потенційно червоного кроку, не є гейтом». Окрема джоба лишає каденсу всю блокувальну силу, але забирає здатність приховувати чужі результати. Локально перед PR: `pnpm docs:check-freshness-cadence`.

7. **Ідемпотентність** — скрипт вшиває коментар-маркер (`<!-- doc-freshness:<path> -->`) у тіло issue. Перед створенням нової issue він шукає вже відкриту з таким маркером і пропускає, якщо знайшов.

## Закриття issue

Скрипт закриває freshness-issue **сам** — і це друга половина механізму, якої до 2026-08-23 не існувало.

Кожен issue несе marker `<!-- doc-freshness:<шлях> -->`. Наприкінці кожного не-`pull_request` прогону скрипт бере всі відкриті issue з лейблом `freshness-overdue` і закриває ті, чий шлях у цьому прогоні **не** визнано простроченим — тобто заголовок оновили, файл видалили/заархівували, або шлях виключили з трекінгу. Issue без marker-а не чіпаються: їх міг завести живий автор.

**Чому це знадобилось.** Доти скрипт умів лише відкривати. Односторонній храповик: оновив заголовок — issue висить; видалив док — issue висить і вказує в нікуди. Так у беклозі накопичилось дев'ять відкритих freshness-issue, з яких вісім (#127, #255, #295, #296, #299–#302) посилались на файли, яких у репо вже немає, а дев'ятий (#305) стосувався авто-генерованого `today.md`. Жоден із них не ніс сигналу, але всі дев'ять читались як робота.

**Чому тільки поза `pull_request`.** PR, який оновлює заголовок, закрив би issue ще до мержу — і якби PR відкотили, issue лишився б закритим при простроченому доці. `docs-freshness.yml` викликає скрипт тільки на `github.event_name != 'pull_request'`; не послаблюй цю умову.

**Запис вимагає `GITHUB_REPOSITORY`.** Історичний дефолт slug-а в скрипті (`Skords-01/Sergeant`) не збігається з поточним remote, тож будь-яка операція запису тепер падає з явною помилкою замість того, щоб вгадувати репо. В Actions змінна виставлена завжди.

## Підтримувані формати заголовка

| Формат             | Приклад                                                                   | Нотатки                                                                                                                                                                                |
| ------------------ | ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Канонічний         | `> **Last touched:** 2026-04-27 by @user. **Next review:** 2026-07-26.`   | Бажаний. Auto-discovery враховує лише цей формат.                                                                                                                                      |
| Legacy (label)     | `> **Last validated:** 2026-04-27 by @user. **Next review:** 2026-07-26.` | Той самий формат зі старим лейблом. Read-sites його приймають, а `scripts/docs/bump-last-validated.mjs` перезаписує на `Last touched:` при першому ж дотику (лінива міграція корпусу). |
| Legacy (pre-PR-11) | `> Last reviewed: 2026-04-27. Reviewer: @user`                            | Стиль AGENTS.md до PR-11.A. Розпізнається парсером, але **не** включається auto-discovery — мігруйте.                                                                                  |

Коли знайдено legacy-заголовок (через `explicitInclude` або старий `freshness-allowlist.json`), скрипт обчислює дату наступного рев'ю як `lastValidated + cadenceDays`.

## Як додати документ у freshness-список

> Зазвичай нічого не треба робити з конфігом — просто додайте заголовок. Дату й handle оновить **auto-bump pre-commit hook** (`scripts/docs/bump-last-validated.mjs`).

1. Додайте freshness-заголовок до документа (одразу після title):

   ```markdown
   # Мій документ

   > **Last touched:** YYYY-MM-DD by @yourhandle. **Next review:** YYYY-MM-DD.
   > **Status:** Active
   ```

   Дата наступного рев'ю — `today + 90` (стандартний cadence).

2. Якщо документ потребує іншого cadence-у — додайте запис у `scripts/docs/freshness-config.json` → `cadenceOverrides`:

   ```json
   "cadenceOverrides": {
     "docs/my-runbook.md": 60
   }
   ```

3. Якщо файл — це не код-агностичний governance-док (наприклад, це auto-generated SDK-doc), додайте його шлях у `excludeGlobs` чи `explicitExclude`.

4. Запустіть локально, щоб переконатися, що файл потрапив у tracking:

   ```bash
   pnpm docs:freshness-dashboard
   open docs/governance/governance/freshness-dashboard.html   # gitignored, не комітити
   ```

## Каденція

### Чому вона різна

Пласкі 90 днів на весь корпус — це арифметично нездійсненна обіцянка. На 2026-08-13 у гейті **416 документів**; при 90-денному циклі це ~190 переглядів на квартал, тобто **~6 документів щодня, без вихідних і назавжди**. Такий борг не гаситься — він накопичується, гейт червоніє масово, а масове червоне лікується масовою пересувкою дат. Пересувка ж нічого не переглядає, лише переносить стіну на три місяці вперед і робить її більшою.

Тому каденція тепер залежить від того, **що це за документ**, а не однакова для всіх:

| Каденція | Для чого                                                                                                                               | Де налаштовано                                                                                      |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 60 днів  | **Процедури, за якими діють під тиском**: incident-runbook, hotfix, ротація секретів, debug-chat, pre-merge migration checklist        | поіменні шляхи в `cadenceOverrides` — свідомо вузький список                                        |
| 90 днів  | **Живі правила й архітектура**: governance, `docs/engineering/architecture/**`, `docs/product/modules/**`, агентські доки              | `defaultCadenceDays` + точкові glob-и                                                               |
| 180 днів | **Повільна довідка**: дизайн-система, інженерні описи, per-rule тіла правил (їх синхронність і так гейтить `lint:hard-rules-registry`) | glob-и `docs/design/**`, `docs/engineering/**`, `docs/governance/governance/rules/**`               |
| 365 днів | **Записи про момент**: аудити, security-огляди, плани, постмортеми, what's-new, спайки. Їх не «оновлюють» — їх замінюють новими        | glob-и `docs/governance/security/**`, `docs/work/specs/audits/**`, `docs/work/specs/planning/**`, … |

`cadenceOverrides` приймає і **точні шляхи, і glob-и**. Пріоритет: точний шлях → **найдовший** glob, що збігся → `defaultCadenceDays`. Тобто `docs/engineering/notes/**` перебиває `docs/engineering/**`, і окремий документ завжди перебиває обидва.

### Чому дати рознесені

Календар сам собою не збиває документи в купу — це робить **штампування**. Пакетна правка (перейменування, прогін генератора, масовий бамп) записує однакову дату в десятки файлів, і рівно через одну каденцію вони протухають **одного дня**. Заміряно 2026-08-13: 195 документів дивились на одну дату, а попередня когорта з 47 була так само проштампована в травні.

Тому `nextReviewFor()` додає до каденції детермінований зсув `reviewJitterDays()` — 0…⅓ каденції, порахований із шляху документа (FNV-1a). Властивості:

- **тільки додає** — жоден документ не переглядається раніше, ніж обіцяє його каденція;
- **стабільний** — той самий шлях завжди дає той самий зсув, тож повторний перерахунок нічого не змінює;
- **розбиває когорту в чергу** — після переходу максимум становить 8 документів на день замість 195.

Одне джерело правди для всіх трьох споживачів (бампер, гейт, перерахунок) — `nextReviewFor()` у `freshness-config.mjs`. Якщо котрийсь із них порахує дату сам, вони розійдуться.

### Статус знімає з календаря

Документ зі статусом `Archived`, `Superseded`, `Done`, `Deprecated` чи `Closed` (`TERMINAL_STATUSES`) до гейта не потрапляє взагалі. Календар питає «це ще правда?» — а для завершеного чи замороженого документа відповідь не має користі: постмортем, виконаний план чи заархівований спайк описують момент, який уже не зміниться.

Очевидний важіль тут визнаний свідомо: одне слово в заголовку прибирає файл із гейта. Це обмежено тим, що словник статусів валідує `check-lifecycle-markers.mjs`, статус видно в дифі, а документ, помічений завершеним і при цьому не завершений, — це брехня про сам документ, якої календар усе одно не ловить.

### Як змінити каденцію документа

Поправте `scripts/docs/freshness-config.json` → `cadenceOverrides`. Дати перегляду далі
проставляє pre-commit-хук `scripts/docs/bump-last-validated.mjs` при наступному дотику
до файлу.

Пакетного re-stamp більше немає: `scripts/docs/restamp-next-review.mjs` <!-- removed --> прибрано
2026-09-19 як ручний скрипт, який після появи хука не запускали жодного разу. Межа,
яку він тримав, лишається чинною і для хука: `Last touched` і автора переписувати не
можна - пересунути їх без реального перегляду означає записати в документ факт, якого
не було.

## Свідомо виключено

Дефолтний `excludeGlobs` (`scripts/docs/freshness-config.mjs` → `DEFAULT_CONFIG`) виключає:

- `docs/governance/adr/**` — Architecture Decision Records іммутабельні (див. нижче).
- `**/_TEMPLATE*.md`, `**/TEMPLATE*.md`, `docs/start/instructions/INDEX.md` — шаблони / згенеровані індекси.
- `apps/**/README.md`, `packages/**/README.md`, `ops/**/README.md` — code-adjacent доки, які живуть із кодом.
- `apps/server/src/ai-prompts/**` — промпти, які версіюються разом зі своїми консумерами.
- `.github/**`, `.agents/**`, `.claude/**` — UI-templates і агентські skill-набори, що приходять зверху.
- `CHANGELOG.md`, `THIRD_PARTY_LICENSES.md` — генеровані / суто історичні.

Плюс поіменні виключення в `scripts/docs/freshness-config.json` → `excludeGlobs`, серед них три артефакти **одного генератора** (`pnpm docs:gen-daily`): `docs/open-work.md`, `docs/STATUS.md` і — з 2026-08-23 — `docs/today.md`.

### Чому `docs/today.md` виключено (2026-08-23)

`today.md` штампує сам генератор, ставлячи `Next review` рівно **+7 днів**. Доти, доки `docs-daily-brief.yml` крутився за розкладом, це працювало. Розклад прибрали 2026-07-09 (`dca267eeb`, економія Actions-хвилин для solo-maintainer-а), лишивши тільки `workflow_dispatch` — і файл почав протухати через тиждень після кожного ручного прогону. Через дев'ять днів, 2026-07-18, freshness-чекер завів issue #305. **Розклад повернуто 2026-09-16** (рішення власника) — уже не заради `today.md`, а тому що ті самі артефакти звіряють два PR-гейти в `docs-automation.yml`, і без щоденної регенерації вони червоніють на `main` після кожної пачки злиттів. **2026-10-01 розклад знято вдруге** (рішення власника): бот-PR через `GITHUB_TOKEN` не запускає обовʼязкових чеків, тож кожен тижневий прогін лишав PR, який доводилось землити руками. Воркфлоу лишився з `workflow_dispatch`. Розбіжність цих артефактів ловить pre-commit (`pre-commit-derived-artifacts.mjs` у кожному коміті з `.md`) і називає команду регенерації.

Виправляти це «оновленням заголовка» безглуздо: у людини там нема чого валідувати, а наступний прогін генератора все одно перепише файл. Тому `today.md` поїхав туди ж, де вже лежали його два брати з того самого пайплайну.

### Architecture Decision Records (`docs/governance/adr/**`)

ADR-и **навмисно виключені**. ADR фіксує контекст, альтернативи та обґрунтування рішення **на момент його прийняття** — це історичний запис, а не «живий» документ. Коли базове рішення змінюється:

1. Напишіть новий ADR, який описує нове рішення з актуальним контекстом.
2. Виставте `Status: Accepted` на новому ADR і `Status: Superseded by ADR-NNNN` на старому.
3. Додайте рядок `Supersedes: ADR-MMMM` у заголовок нового ADR.

Це стандартний патерн із [оригінальної пропозиції Майкла Найгарда](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions) та спільноти [adr.github.io](https://adr.github.io/).

Якщо ADR коли-небудь потребує операційних метаданих, які треба перевалідовувати за cadence-ом (наприклад, таблиця квот, прайс-лист), винесіть ці дані в окремий док під `docs/engineering/integrations/`, `docs/work/specs/launch/` або `docs/operations/observability/` і додайте **його** заголовок — а сам ADR не чіпайте.

## Дашборд

`pnpm docs:freshness-dashboard` (`scripts/docs/generate-freshness-dashboard.mjs`) рендерить HTML-таблицю всіх відстежуваних доків: статус, `Last touched`, `Next review`, днів до прострочки, власник, каденція. Це **звіт, а не гейт** і не джерело даних: trust badge, `today.md` і гейти свіжості рахують усе прямо з шапок доків.

Де взяти:

- локально: `pnpm docs:freshness-dashboard` пише `docs/governance/governance/freshness-dashboard.html` (файл у `.gitignore`);
- з CI: артефакт `docs-freshness-dashboard` щопонеділкового прогону `docs-freshness.yml` (зберігається 30 днів).

### Чому дашборд не комітиться (2026-10-01)

Рішення власника 2026-10-01. До того дашборд лежав у репо, і pre-commit-хук `bump-last-validated.mjs` перегенеровував і стейджив його на **кожному** коміті з `.md` (дати в шапках зсуваються, отже, змінюється і дашборд). Наслідок: після кожного мерджу в `main` усі відкриті PR конфліктували в цьому файлі без жодного змістовного перетину. 2026-10-01 так двічі за день зачепило по 6-7 PR одночасно; за два дні до рішення дашборд змінювали 35 із 72 комітів, що торкались `.md`.

Розглянуті варіанти й чому їх відкинуто:

- **Перегенеровувати на `main` після мерджу ботом.** Пуш у `main` через `GITHUB_TOKEN` блокує branch protection (обовʼязкові статус-чеки для не-адмінів). Обхід адмінським токеном лишає в секретах Actions токен, що обходить гейти. До того ж будь-який бот-коміт у `main` ламає автодеплой бекенду: `deploy-api.yml` пропускає деплой, якщо `main` пішов далі за коміт прогону ([ADR-0102](../adr/0102-github-actions-ci-and-autodeploy.md)), а коміт із `[skip ci]` власного CI не запускає.
- **Бот-PR, як у `docs-daily-brief.yml`.** PR, відкритий через `GITHUB_TOKEN`, не запускає `pull_request`-воркфлоу, тож обовʼязкові чеки не приходять і auto-merge висить. Кожен такий PR довелося б мерджити вручну.
- **Не комітити (обрано).** GitHub однаково показує закомічений `.html` як сирець, а не сторінку, і жоден скрипт файл не читав. Нуль ботів, нуль секретів, нуль впливу на деплой.

Що змінилось разом із рішенням: файл у `.gitignore`; регенерацію і `git add` прибрано з `bump-last-validated.mjs`, звірку з `pre-commit-derived-artifacts.mjs`, крок `--check` з `docs-automation.yml`, дашборд з `docs:gen-daily` і `REFRESH_PATHS` у `docs-daily-brief.yml`; режим `--check` і скрипт `docs:check-freshness-dashboard` видалено; `docs-freshness.yml` пише в `OUTPUT=dist/freshness-dashboard.html`, тож артефакт більше не порожній (доти генератор писав в одне місце, а крок вивантаження шукав файл в іншому).

**Не повертай дашборд у репо** без нового рішення власника. Ті самі конфлікти дає `docs/open-work.md`, але рідше, і він Markdown, тож GitHub його рендерить; його це рішення не зачіпає.

## Локальний запуск

```bash
# Dry-run (issue не створюються) — показує overdue-статус кожного відстежуваного файлу
DRY_RUN=1 node scripts/docs/check-freshness.mjs

# Coverage-gate — фейлиться, якщо є .md без freshness-заголовка
node scripts/docs/check-freshness.mjs --check-coverage

# Реальний запуск (потрібен GITHUB_TOKEN з issues:write)
GITHUB_TOKEN=ghp_... node scripts/docs/check-freshness.mjs

# HTML-дашборд із усіма відстежуваними файлами (gitignored, не комітити)
pnpm docs:freshness-dashboard
open docs/governance/governance/freshness-dashboard.html
# або в інше місце:
OUTPUT=dist/freshness-dashboard.html pnpm docs:freshness-dashboard
```
