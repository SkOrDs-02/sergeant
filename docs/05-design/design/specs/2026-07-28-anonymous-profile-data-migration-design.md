# Міграція анонімних даних у профіль

> **Last touched:** 2026-07-28 by @dimastahov16012003. **Next review:** 2026-10-26.
> **Status:** Shipped — implementation pending PR.

## Мета

Під час першого авторизованого boot перенести локальні записи всіх чотирьох
модулів із синтетичного користувача `local-anon` у SQLite-партицію реального
Better Auth `userId`, а потім підтвердити їх збереження через Sync V2. До
підтвердження модульний UI заблокований, а вихідні дані не видаляються.

## Контракт

1. Координатор відкриває анонімну партицію, проганяє клієнтські міграції та
   створює або відновлює durable batch у `anonymous_profile_migrations`.
2. Рядки синхронізованих таблиць знімаються у snapshot. Службові таблиці,
   outbox, курсори, ledger-и та відновлювані Mono-кеші не переносяться.
3. У профільній партиції спочатку виконується pull. Snapshot застосовується
   наявним LWW-механізмом за `client_ts`; ручного діалогу конфліктів немає.
4. Для кожного рядка ставиться операція у звичайний Sync V2 outbox із ключем
   `anonv1_<sha256>`, детермінованим від batch, користувача, таблиці, PK,
   timestamp і виду операції. Повторний запуск не створює серверних дублів.
5. Джерело видаляється транзакційно лише коли операції зникли з outbox після
   `applied`/`duplicate` або мають очікуваний `lww_conflict`. Будь-яка інша
   помилка залишає source і batch для кнопки «Повторити».

## UX

- Під час перевірки й перенесення показується блокувальний нейтральний екран.
- Помилка прямо каже, що дані лишилися на пристрої та ще не захищені sync.
- Після ненульового перенесення показується один success-toast.
- Якщо анонімних рядків немає, відкриття профілю відбувається без toast.

## Перевірки

- StrictMode запускає один in-flight batch.
- Міграція 008 ідемпотентна й створює checkpoint-таблицю.
- Невдалий push не відкриває модулі; retry повторює той самий batch.
- Server-newer конфлікт приймається як авторитетний LWW-результат.
