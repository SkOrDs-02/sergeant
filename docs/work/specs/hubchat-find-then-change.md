# SPEC: Чат «знайди, потім зміни ту» і квиток раунду

> **Last touched:** 2026-11-18 by @claude. **Next review:** 2027-02-18.
> **Status:** Active

## Проблема

Чат робить один раунд інструментів на повідомлення, а історію шле серверу
лише текстом реплік. Модель за правилом промпту переказує результат «без id»
(`toolDefs/systemPrompt.ts`), тож id операції, знайденої на попередньому
ході, до моделі на наступному не доїжджав. «Знайди покупку в Сільпо», потім
«перенеси її в Кафе» закінчувалось повторним пошуком без запису або
вигаданим id (С-2 розбору
[`2026-11-17-modules-teardown-vs-leaders.md` § 11.5](../research/2026-11-17-modules-teardown-vs-leaders.md)).

Поруч два дефекти того самого шляху. (1) Веб ніколи не повертав
`round_trip_ticket` у запиті синтезу, хоча сервер його видає з квітня
(AI-5): хід з інструментом списував дві одиниці тижневої AI-квоти замість
однієї, а трейс ходу в PostHog розпадався на два. (2) Картки результатів
пошуку операцій і тексти відмов показували людині технічні id (`m_1:
2026-… · 120 грн`, «Звичку h1 не знайдено.»), хоча фікс першої хвилі
(`core/lib/chatDisplayText.ts`) прибрав їх з решти показу.

## Мета

Друге повідомлення «зміни ту» після пошуку виконує запис з id, знайденим на
попередньому ході, без повторного пошуку і без вигаданого id. Хід з
інструментом коштує одну одиницю AI-квоти, і перший тур та синтез ділять
один трейс. Людина в чаті не бачить технічних id ні в картці пошуку, ні в
тексті відмови; модель свій id отримує як і раніше.

## Рішення дизайну

- **С-2 варіант (а), а не (б).** Id знайдених записів зберігаються в
  історії, другий раунд інструментів не додається. Джерело: § 11.5 (рекомендація
  «(а), потім (б)») і § 11.7 (founder ухвалив рекомендовані варіанти).
- **Памʼятаємо лише останню відповідь.** Записи бере тільки остання репліка
  асистента; репліка без записів між пошуком і проханням обриває ланцюжок.
  Джерело: дефолт § 11.8 («чат памʼятає id лише з останньої відповіді»), § 11.9
  (дефолти чинні).
- **Куди кладемо записи: у блок ДАНІ (`context`), а не в текст реплік.**
  Промпт уже велить брати id для запису лише з блоку ДАНІ
  (`NO_INVENTED_ARGS_RULE`, `toolDefs/systemPrompt.ts`), тож системний промпт і
  описи інструментів не змінюються, кеш префікса (ADR-0039) не інвалідовується.
  Сервер маскує `context` тим самим класом А + Б, що й результати інструментів
  (`lib/llmRedaction.ts`), тобто нова категорія даних за периметр не йде.
  Відкинуто: дописувати id у текст репліки асистента (модель вважала б, що сама
  їх сказала, і почала б повторювати їх людині) і повторювати `tool_use` блоки
  в історії (змінює контракт `ChatRequestSchema`).
- **Формат блоку.** Заголовок `[Записи з попередньої відповіді]` (у стилі
  розділів знімка `[Категорії]`), далі рядок `- <інструмент>: <результат>` на
  кожен результат із технічним id, як модель його вже бачила. Стеля 8000
  символів: стеля одного `tool_result` у контракті (`ToolResult.content`
  `max(8000)`, `packages/shared/src/schemas/api.ts`); понад неї відкидаються
  цілі рядки.
- **Які результати потрапляють у блок.** Лише успішні, не відмови
  (`isFailureResult`), лише з технічним id (`hasTechnicalIds`) і лише модулів
  Фінік і Рутина. Фізрук, Харчування й памʼять виключені: серверний гейт
  здоровʼя (`healthGate.ts::stripHealthContext`) розпізнає health лише за
  відомими рядками знімка, тож без згоди такі результати проскочили б до моделі
  через довільний блок. Джерело: рішення 2026-09-29 у `hub-coach.md` § Журнал
  рішень («новий шлях дані → LLM без `resolveHealthConsent` — дірка»).
- **Квиток раунду.** Клієнт повертає `round_trip_ticket` першого туру в запиті
  синтезу, якщо сервер його видав; без квитка поле відсутнє, а не порожнє.
  Сервер і тип `ChatRequestPayload.round_trip_ticket` уже існували
  (`aiQuota.ts::tryConsumeRoundTripTicket`, `chat.ts::attachRoundTripTicket`),
  тож контракт не змінюється: додано лише контрактний тест трійки (Hard Rule
  #3). Джерело: рішення AI-5 «хід з дією коштує один запит»
  (`docs/work/specs/audits/2026-09-01-product-audit/findings.md`).
- **Технічні id на показі.** `stripTechnicalIds` розпізнає третю форму,
  елемент списку операцій `<id>: <дата або «без дати»> · …`: id Monobank
  довільний рядок, тож тримаємось форми елемента, а не id. Картка
  `query_transactions` показує рядок як «дата · опис · категорія» і суму
  праворуч; масштаб смуги береться із суми, а не з року в даті.
- **Тексти відмов.** Виконавці пишуть id у формі `(id:…)`, яку вирізає показ:
  «Звичку не знайдено (id:h1).» → людині «Звичку не знайдено.». Де сутність
  відома, текст несе людський підпис (`finykTransactionLabel`): «Операцію
  «Кава» на 120 грн не видалено: …». Тренування підпису не має: дата старту в
  ISO UTC, а день-ключ за годинником пристрою (ADR-0078), тож чесний підпис
  потребує окремого форматера.
- **Tool-eval (П-19 (А)).** Пара кейсів у `toolSelectionCases/followUp.ts`:
  однакова розмова, різниця лише в блоці записів (`dataExtra`). Перший міряє
  фікс (очікуваний `change_category` з `tx_id: tx_7c40`), другий контроль без
  блоку (правильно шукати знову, будь-який id у записі = вигаданий). Кейси поза
  `ALL_CASES`, бо касета вимагає запису кожного кейса звідти; запуск
  `pnpm eval:tools --follow-up`, касету не пише. Джерело: відповідь founder-а
  П-19 (А) у § 11.9 і бриф «касети без потреби не перезаписуй».

## Верифікація (обовʼязково)

1. `pnpm --filter @sergeant/web exec vitest run src/core/hub/chat src/core/lib`:
   нові тести `turnRefs.test.ts`, «запамʼятовує id знайденої операції…»,
   «наступне повідомлення несе id…», «повертає round_trip_ticket…»,
   `chatDisplayText.test.ts`, `DataResultCard.test.tsx` зелені.
2. `pnpm --filter @sergeant/server test:tool-eval`: касета й базова лінія без
   змін, `replay.test.ts` доводить, що id з блоку записів не вигаданий, а без
   блоку вигаданий.
3. Платний прогін (П-19 (А)):
   `OPENROUTER_API_KEY=proxy-injected pnpm --filter @sergeant/server eval:tools --follow-up --repeat=5`.
   Очікування: кейс «id з попередньої відповіді» правильний у більшості
   повторів, `Invented ids` 0; контроль показує, що без блоку модель шукає
   знову або вигадує id.
4. Браузер: «знайди мою каву вчора» → картка без `m_…`; наступним
   повідомленням «перенеси її в Кафе» → картка «Категорію змінено», без
   повторного пошуку. Лічильник AI-запитів після ходу з інструментом
   зменшився на 1, а не на 2.

## Ризики та відкриті питання

- **Модулі здоровʼя в блоці записів.** Зараз «знайди тренування, потім
  заверши його» наступним повідомленням не працює. Варіанти: (А) лишити
  Фізрук, Харчування й памʼять поза блоком, як зараз: приватність без змін,
  ланцюжок працює лише для Фініка й Рутини; (Б) сервер розпізнає блок
  записів і без згоди на дані здоровʼя вирізає з нього рядки
  health-інструментів (`HEALTH_ONLY_TOOL_NAMES`): ланцюжок працює для всіх
  модулів, ціна — нова гілка в `healthGate.ts` з тестом. Питання founder-у.
- Блок записів зберігається в історії чату на пристрої (поле `toolRefs` репліки),
  тобто там само, де вже лежать картки з тими самими даними.
- Підробити блок записів може лише сам клієнт, а `context` і так клієнтський:
  модель трактує його як ДАНІ під огорожею `<user_data>`.
