# SPEC: Єдиний каталог категорій Фініка

> **Last touched:** 2026-09-09 by Codex. **Next review:** 2026-12-09.
> **Status:** Implemented

## Проблема

Ручні й банківські операції мали різні набори категорій та різні ID для однакових надходжень. Власні категорії працювали тільки для витрат.

## Мета

Дати обом джерелам один детальний каталог витрат, окремий каталог надходжень і власні категорії, розділені за типом.

## Рішення дизайну

- Каталоги спільні для ручного й банківського джерела; витрати та надходження не змішуються. Джерело: власник, 2026-09-09.
- «Техніка» є окремим кошиком. Чинні ліміти «Покупки» зберігають охоплення як «Покупки + Техніка»; нові ліміти точні. Джерело: власник, 2026-09-09.
- Старі власні категорії без `kind` є витратами; legacy ID надходжень резолвляться в єдині ID.

## Поверхня змін

- `packages/finyk-domain` — каталоги, legacy-резолв і версія ліміту.
- `apps/web/src/modules/finyk` — ручні й банківські пікери та storage.
- `apps/web/src/core/settings/FinykSection.tsx` — створення власної категорії відповідного типу.
- Owner: `sergeant-module-finyk` + `sergeant-web-ui`.

## Поза скоупом v1

- Дерево підкатегорій і ретроактивне перекласифікування операцій.
- Нові mobile-екрани.

## Верифікація (обовʼязково)

1. Domain-тести перевіряють розділення типів, legacy ID, окрему «Техніку» та спадкове охоплення лімітів.
2. Web-тести перевіряють обидва пікери, ручні операції, банківські деталі, бюджети й налаштування.
3. `pnpm check` виконується локально або повною матрицею GitHub CI.

## Ризики та відкриті питання

- Старий клієнт не показує нові income custom categories, але зберігає їх у JSON; read fallback не змішує їх із витратами.
