# SPEC: `PR body validator` червоніє на PR, створених через API

> **Last touched:** 2026-09-13 by @claude. **Next review:** 2026-12-13.
> **Status:** Active

## Проблема

Гейт `PR body validator` ([`scripts/ci/validate-pr-body.mjs`](../../../scripts/ci/validate-pr-body.mjs))
падає на PR, створених через GitHub API з повністю заповненим описом, і друкує
помилки, яких в описі немає:

```
• Section `## Docs and Governance` has no ticked checkboxes.
• Section `## Hard Rule #15` has 3 unticked checkbox(es); all 3 must be ticked.
• Section `## Summary` is empty.
```

Спостережено на [#1148](https://github.com/SkOrDs-02/sergeant/pull/1148) 2026-09-13:
опис був повний із першої секунди, усі галочки стояли.

**Механізм.** Валідатор читає `github.event.pull_request.body` з вебхука. Захист
від гонки «вебхук випереджає сховище» там уже є — фолбек на REST API, — але
вмикається він **лише коли тіло порожнє**:

```js
return process.env.PR_BODY || ""; // фолбек спрацює тільки на ""
```

А в репо з `PULL_REQUEST_TEMPLATE.md` тіло на момент `opened` порожнім не буває:
GitHub підставляє шаблон. Шаблон має всі обовʼязкові секції, порожній Summary і
незняті галочки — тобто дає **рівно той** набір помилок, який гейт і друкує.
Захист накриває один із двох станів гонки, а репо з шаблоном завжди дає другий.

Це та сама форма, що й інші знахідки цього дня: механізм прикрито на одному
шляху, сусідній про нього не знає — і мовчить так само, як зелений.

## Мета

PR, створений через API з валідним описом, дає зелений `PR body validator` з
першого прогону — без ручного редагування опису.

## Рішення дизайну

- **Розширити умову фолбеку, а не прибрати кеш вебхука.** Читати з API завжди —
  зайвий запит на кожен PR; читати ніколи — повернути гонку. Умова має бути
  «тіло порожнє **або** дорівнює шаблону».
- **Порівнювати з шаблоном нормалізовано**, а не байт-у-байт: GitHub може
  нормалізувати переводи рядків. Достатньо звірити з вмістом
  `.github/PULL_REQUEST_TEMPLATE.md` після `trim()` і згортання `\r\n` → `\n`.
- **Не чіпати тригер `edited`.** Він уже є у воркфлоу і несе коментар, чому
  «Re-run failed jobs» не рятує (відтворює старий payload). Після фікса він
  лишається шляхом для випадку «автор справді забув заповнити й дозаповнив».

## Поверхня змін

- `scripts/ci/validate-pr-body.mjs` — `loadBody()` і умова виклику
  `fetchBodyFromApi()`
- `scripts/docs/__tests__/` або сусідній тест-файл валідатора — кейс «тіло
  дорівнює шаблону → береться версія з API»
- Owner-скіл за routing-таблицею AGENTS.md: `sergeant-tech-debt`

## Поза скоупом

- Зміна складу обовʼязкових секцій або правил галочок — гейт по суті правильний,
  ламається лише джерело даних.
- Виняток для авторів-ботів — він уже є (`isAutomatedAuthor`) і до цієї гонки
  стосунку не має.

## Верифікація

1. **Відтворити до фікса.** Прогнати валідатор локально, підклавши тіло шаблону:
   `PR_BODY="$(cat .github/PULL_REQUEST_TEMPLATE.md)" node scripts/ci/validate-pr-body.mjs`
   → ті самі три помилки, що в логу #1148.
2. **Після фікса** той самий виклик без `GITHUB_TOKEN` має лишитись червоним
   (фолбек недоступний, тіло справді шаблонне), а з доступним API — зеленим,
   бо підтягнеться справжній опис.
3. **Юніт:** тіло = шаблон → `fetchBodyFromApi()` викликано; тіло = валідний
   опис → **не** викликано (інакше фікс перетворює гейт на запит на кожен PR).
4. **Наживо:** створити PR через API з повним описом → гейт зелений з першого
   прогону, без редагування.

## Ризики та відкриті питання

- Якщо API недоступний (нема токена, 403), поведінка лишається як зараз —
  червоно на шаблонному тілі. Це прийнятно: воно ж і є істинним станом, коли
  опису справді немає.
- Шаблон читається з чекауту гілки PR. Якщо PR **змінює** сам шаблон, порівняння
  треба робити з версією шаблону, а не з новою — інакше фікс не спрацює саме на
  тому PR, що править шаблон. Кейс рідкісний; закрити тестом або свідомо
  лишити як відомий виняток.
