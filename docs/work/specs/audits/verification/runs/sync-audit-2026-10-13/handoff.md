# Перевірка черги sync та переносу localStorage → OPFS

> **Status:** Closed — `incomplete` за повними картками каталогу; цільові перевірки фіксу пройшли. 2026-10-14.

## Висновок і межі

Скрін користувача показував 24 944 pending-операції у встановленому iPhone PWA. Лічильник зменшувався, але старий writer брав по 100 за тік з інтервалом ≈30 с і не запускав наступний тік одразу після повної порції. Навіть без затримок API це ≈125 хв відкритого застосунку. `Онлайн` — стан браузерної мережі, `Помилки: Немає` — відсутність `dead_letter`, а не підтвердження сервером; `Файлове сховище у фоні: Доступний` — наявність браузерної можливості, не гарантія доставки після закриття iOS PWA.

У гілці `codex/sync-backlog-drain` writer починає drain на старті, шле до 200 ops (чинна серверна межа), продовжує повну підтверджену порцію через 2 с, ріже тіло до 5 MiB UTF-8 перед серверною межею 6 MiB, а підтверджені receipt-и видаляє одним SQLite-запитом на порцію. Retry/missing receipt залишають рядки локально й припиняють швидкий догін до наступного звичайного тіку. Після кінця черги reader робить pull, включно з випадком точно кратної 200 кількості. Форма API, серверний код і LWW не змінювались.

Це перевірка ізольованого локального API/PostgreSQL і Chromium з viewport 390×844; доступу до акаунта та OPFS конкретного iPhone немає. Тому немає підстав стверджувати, що **саме його** 24 944 записи вже є у хмарі. До receipt-а сервера pending-запис зберігається в OPFS пристрою; після закриття iOS PWA передача не гарантована, а після повторного відкриття writer відновлює чергу. Видалення PWA або очищення браузерних даних до доставки може видалити локальну копію.

## Вимірювання

| Перевірка                                          | Результат                                                                                                                                                                                                                                                                                                       |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Реальний legacy kvvfs → OPFS із чинними міграціями | У кожному з `routine_habits`, `finyk_manual_expenses`, `nutrition_meals`, `fizruk_workouts` збережено 200 записів власника й 1000 pending ops; 40 чужих записів/модуль та 40 чужих ops відсічено. Інша партиція зберегла свої 20 записів/модуль. Повторний import та hard reload не перезаписали новіші записи. |
| Черга 24 944 у реальній OPFS-базі                  | Старий алгоритм: 24 944 → 24 844 → 24 744 двома тиками по 100. Новий: 24 744 → 23 744 за 8 589 мс, 5×200, 1000 унікальних ключів. Hard reload зберіг решту 23 744. HTTP-ack у цьому замірі тестовий.                                                                                                            |
| Справжній локальний API                            | Одним POST передано 200 ops: HTTP 200, 200 applied, 0 rejected, рівно 200 SQL-рядків; 1 948 мс.                                                                                                                                                                                                                 |
| Анонім → акаунт → інший чистий контекст            | Витрата після reload, входу й pull у свіжому контексті видима рівно раз. Офлайн витрата пережила reload і з’явилась на сервері та другому пристрої після reconnect. Два push отримали HTTP 200 / applied 1 / rejected 0.                                                                                        |

За цими локальними замірами 24 944 ops потребують приблизно 125 порцій; із 2 с паузою й ~2 с локального API на порцію це порядок **8–10 хв** активного PWA. Це оцінка, а не гарантія швидкості iPhone чи прод-сервера. Якщо користувач закриє PWA, локальна решта дочекається повторного відкриття.

Повні картки `SYNC-offline-conflict-isolation` та `DATA-durability-live` позначені `not-run`: тут окремо не повторювались LWW, IDOR, logout purge, stale session та P1–P9 усіх модулів. Історичний повний прогін: `durability-2026-10-08`; він не підміняє поточні докази фіксу. Одноразові браузерні харнеси запускались окремо, їхні результати збережено вище; у продуктовий web bundle вони не входять.

## Наступний крок

Після merge/deploy на iPhone відкрити PWA, залишити на передньому плані, подивитись, чи `У черзі` швидко падає й доходить до нуля; після закриття/відкриття перевірити продовження з попереднього значення. Якщо лічильник зупиниться, перевірити API 429/503 і `Retry-After`, а також `Не прийнято сервером` та локальні retry. Не очищувати дані PWA до нуля в черзі.
