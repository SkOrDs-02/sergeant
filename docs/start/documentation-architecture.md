# Архітектура документації Sergeant

> **Last touched:** 2026-09-11 by @claude. **Next review:** 2026-12-15.
> **Status:** Active

Цей документ задає чинну архітектуру документації: призначення жанрів, джерело
істини та фізичне дерево. Міграція зі старих нумерованих каталогів завершена;
історичні посилання ведуть на immutable Git permalink. Новий документ не
повинен створювати паралельний каталог.

## Цільове дерево

| Цільовий розділ     | Дім знання                                          | Приклади жанрів                     |
| ------------------- | --------------------------------------------------- | ----------------------------------- |
| `docs/start/`       | Як орієнтуватися в репо та виконувати типові задачі | онбординг, маршрути, інструкції     |
| `docs/product/`     | Що будуємо і для кого                               | продукт, модулі, launch, copy       |
| `docs/engineering/` | Як спільно працює система                           | архітектура, API, дані, тестування  |
| `docs/operations/`  | Як підтримуємо систему після релізу                 | deploy, SLO, incident, recovery     |
| `docs/design/`      | Як виглядає та звучить продукт                      | tokens, UI-патерни, i18n            |
| `docs/governance/`  | Які правила й рішення є чинними                     | ADR, hard rules, security, ledger   |
| `docs/work/`        | Що зараз змінюємо                                   | спеки, блокери, докази, дослідження |

Модульна документація живе у `docs/product/modules/<module>.md` і містить лише
продуктовий канон та посилання на спільні engineering-контракти. Дані, API й
операційні процедури не копіюються в кожен модуль.

## Правило вибору місця

1. Якщо текст пояснює сталу поведінку або термін — це довідник у відповідному
   цільовому розділі.
2. Якщо текст фіксує майбутню зміну з критеріями приймання — це спека в
   `docs/work/specs/`.
3. Якщо текст пояснює, чому прийнято рішення, яке переживе одну фічу — це ADR
   у `docs/governance/adr/`.
4. Якщо текст дає повторювані кроки — це інструкція в `docs/start/` або
   `docs/operations/` залежно від того, чи потрібен конкретний runtime.
5. Якщо матеріал більше не є активним, його прибирають з checkout і залишають
   перевірене посилання на Git-історію або ADR. Локальні archive-дерева для
   `work/{audits,initiatives,planning}` не відновлюються (ADR-0081).

## Власність і стиль

- Один факт має одне канонічне джерело; індекси містять навігацію, а не копію
  правила.
- Внутрішні документи пишуться українською, коротко й предметно: призначення,
  чинна поведінка, причина обмежень, дії або перевірка.
- Шапка кожного документа має `Status`, `Last validated` і `Next review`, якщо
  документ має cadence. Дата валідації змінюється тільки після перевірки змісту.
- Автоматично згенеровані файли починаються з `<!-- AUTO-GENERATED -->` і
  редагуються через генератор.
- Посилання на поточні шляхи перевіряються `pnpm docs:check-links`; генератори
  не повинні тихо створювати дублікати одного реєстру.

## Виконана міграція

1. Інвентаризація `docs/` зафіксувала жанр, канонічне джерело, споживачів і
   дію `keep`, `merge`, `move` або `remove` для кожного baseline-файла.
2. Нумеровані top-level каталоги перенесені до семантичних домівок без
   compatibility redirects.
3. Активні `initiatives`, `planning`, `audits`, `tech-debt`, launch і
   `superpowers` зведені під один lifecycle-root `docs/work/specs/`.
4. Playbook і runtime runbook зведені в `docs/start/instructions/` з явним
   полем `Runtime-specific: yes|no`.
5. Модульний канон живе в `docs/product/modules/`; локальні archive-дерева
   видалені після переведення inbound-посилань на Git permalink.
6. Генератори та gates переведені на нові шляхи; повторний check-mode не
   створює diff.

Машинний baseline для першого кроку —
[`documentation-inventory.json`](../work/specs/data/documentation-inventory.json).
Оновлюй його через `pnpm docs:gen-inventory`; ручні правки до JSON не
приймаються.

## Критерій завершення

Новий агент із нульовим контекстом за головним індексом знаходить модульний
канон, чинне правило, операційну інструкцію та активну спеку не більш ніж за
два переходи. Повторна генерація індексів не створює diff, а кожен вилучений
документ має запис у міграційній матриці.

## Умови майбутнього структурного перенесення

Фізичний move групи дозволений лише коли всі чотири умови виконані для цієї
групи:

1. У `documentation-inventory.json` є запис для кожного файла групи з дією,
   цільовим шляхом і `inbound_count`.
2. Для кожного `remove` немає inbound-посилань або всі вони вже переведені на
   перевірений permalink/канон.
3. Для кожного `move` немає невирішеного `target_collisions`; merge-пари
   спершу об’єднані вручну.
4. Після хвилі проходять `pnpm docs:check-inventory`,
   `pnpm docs:check-links`, `pnpm lint:specs` і відповідні генератори.

Поточний рефактор завершений: фізичне перенесення виконане, merge-колізій немає,
активні спеки живуть у `docs/work/specs/`, а локальних archive-дерев немає.
Ці чотири умови застосовуються до будь-якого нового структурного move.
