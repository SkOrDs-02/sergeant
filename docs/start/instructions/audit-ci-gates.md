# Playbook: Аудит CI-гейтів — чи кожен гейт реально виконався

> **Last touched:** 2026-09-19 by @claude. **Next review:** 2026-12-24.
> **Status:** Active
> **Runtime-specific:** no

**Trigger:** борг накопичився під зеленим CI · додаєш новий гейт у `.github/workflows/**` · «чому цей лінт не спрацював, він же в пайплайні» · періодична ревізія пайплайна перед релізом.

## Проблема, яку лікує цей playbook

Дзеркало [`fix-failing-ci.md`](./fix-failing-ci.md): той лікує «CI червоний», цей — **«CI зелений, але нічого не перевірено»**.

Канонічне формулювання репо:

> **Гейт, що стоїть у кроках після потенційно червоного кроку, не є гейтом.**

GitHub Actions пропускає всі наступні кроки джоби, щойно один упав. У логах пропущений гейт виглядає **не як «бюджет перевищено», а як тиша** — рівно так само невинно, як зелений. Двічі в історії репо це коштувало тижнів прихованого боргу:

- **2026-08-18.** `size-limit` був кроком у джобі `check` після «Format, lint, test, build». Кілька мержів поспіль пішли в `main` із червоним `format:check` — гейт не виконався, борг ріс мовчки.
- **2026-09-11.** Те саме, але вже з ДВОМА ратчетними гейтами разом (`size-limit` + `coverage-ratchet`) — тобто рівно тими, чия робота ловити повільне сповзання. Плюс третій ефект: **гейт ховав гейт** — `size-limit` падав, і eager, що стояв кроком нижче, ставав `skipped`, тож критичний шлях не міряли жодного разу.

Ту саму хворобу має і `needs:` на рівні джоб: залежна джоба не стартує ані коли `check` червоний, ані коли `check` скасовано новим пушем — і **обидва випадки у звіті тривалостей виглядають як `0s`**, так само невинно, як пропущений крок. Саме тому з `a11y`, `critical-flow`, `mobile-ui-audit` і `landing-quality` `needs: check` прибрано.

## Steps

### 1. Витягнути карту кроків

```bash
grep -n "^  [a-z0-9-]*:$\|name:\|run:\|if:\|continue-on-error:" .github/workflows/ci.yml | less
```

Для кожної джоби випиши кроки по порядку і познач три речі: **(а) чи крок може падати**, **(б) чи це гейт** (може завалити білд змістовно), **(в) чи має `if: always()`**.

### 2. Знайти три патерни поломки

| Патерн                               | Як виглядає                                           | Чому небезпечний                                                     |
| ------------------------------------ | ----------------------------------------------------- | -------------------------------------------------------------------- |
| **Гейт після дорогого кроку**        | гейт стоїть нижче за тести/лінт/білд                  | найчастіший; тиша замість вердикту                                   |
| **Гейт ховає гейт**                  | два гейти підряд, верхній без `always()`              | нижній не міряли жодного разу, і в логах це не видно                 |
| **Серіальний ланцюг дешевих гейтів** | 10+ незалежних статичних лінтів підряд без `always()` | перший червоний глушить решту → ping-pong «одне порушення за прогін» |

Плюс два, які легко пропустити:

- **`always()` на рівні джоби не рятує кроки всередині неї** — джоба стартує, але перший червоний крок так само глушить наступні.
- **Fail-open**: `continue-on-error: true`, `|| true`, `|| exit 0`, `if: false`. Гейт є, вердикту немає.

### 3. Обрати правильний фікс — вони не взаємозамінні

| Ситуація                                             | Фікс                                                                                               |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Гейт **не потребує** артефактів попереднього кроку   | `if: always()` на кроці                                                                            |
| Гейт **потребує білда**, який робить попередній крок | **окрема джоба з власним білдом** — як `bundle-budgets`. `always()` тут не допоможе                |
| Верхній гейт може ховати нижній                      | `if: always() && steps.<id>.conclusion != 'skipped'` — вердикт незалежний, але skip не маскується  |
| Крок-продюсер може впасти й забрати гейт             | **produce → gate**: продюсер під `set +e` кладе exit-code в output, гейт читає його окремим кроком |
| Джоба глушиться через `needs:`                       | зняти `needs:`, дати джобі власний setup                                                           |

Приклади в репо, на які можна дивитись як на зразок: eager-гейт (`always()` + `conclusion != 'skipped'`), Lighthouse-бюджети в `landing-quality` (справжній гейт під `always()`, щоб падіння axe не ховало число), nightly-аудит (`produce → gate`).

### 4. Закріпити форму механічним тестом

Найцінніше, що є в цьому репо проти цього класу поломки — **shape-regression тести YAML**. Вони парсять workflow і падають, якщо конструкцію зламали:

- [`ci-bundle-budget-gates.test.mjs`](../../../scripts/__tests__/ci-bundle-budget-gates.test.mjs) — гейти живуть у власній джобі, не в `check`; eager має `always()`; жоден не fail-open.
- `ci-dedupe-gate.test.mjs`, `ci-deploy-verify-gate.test.mjs`, `ci-mobile-gate.test.mjs` — те саме для своїх гейтів.

**Додав гейт, який легко зробити мовчазним — додай поруч такий тест.** Він коштує 30 рядків і ловить регресію, якої не видно в логах. Зверни увагу: shape-тести навмисно викликаються з джоби `check`, щоб бігати на КОЖНОМУ PR, а не лише на мержі.

### 5. Перевірити, що гейт падає гучно

Мовчазний успіх гірший за відсутність кроку. Для кожного гейта:

- чи повідомлення називає, **що саме** не так (не «не вдалося прочитати статус», а який файл/яка форма);
- чи порожня/несподівана відповідь трактується як провал, а не як «ще триває»;
- чи є `AI-DANGER`-коментар там, де `continue-on-error` заборонений назавжди.

Канонічний приклад із цього репо — верифікація деплою. Webhook Coolify відповідав 2xx, Coolify тихо відкочувався («New container is not healthy, rolling back»), джоба була зелена, і на VPS тижнями стояв старий образ. Другий шар тієї ж помилки: jq-вираз, який читав **одну форму відповіді з трьох** — `.status` на масиві це помилка jq, яка валить увесь вираз ще до фолбеків, а `//` ловить лише `null`/`false`.

## Verification

- [ ] Кожен доданий/змінений гейт має вердикт незалежно від сусіднього кроку (`always()` або окрема джоба)
- [ ] Жоден гейт не fail-open: немає `continue-on-error: true`, `|| true`, `|| exit 0`, `if: false`
- [ ] Для гейта, який легко зробити мовчазним, є shape-regression тест у `scripts/__tests__/`
- [ ] `node --test scripts/__tests__/ci-*.test.mjs` — зелено
- [ ] `pnpm lint` (містить actionlint-сумісні перевірки) — зелено
- [ ] Прогнано на реальному PR: у логах видно вердикт гейта, а не його відсутність
