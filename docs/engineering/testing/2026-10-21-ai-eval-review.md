## Що виправлено

Додано **96 перевірок у пʼяти нових test-файлах**. У пʼяти
red-прогонах 31, 4, 7, 8 та 4 нових перевірок відповідно відтворили дефекти;
інші перевіряють позитивні межі та нові захисні умови.

### Tool arguments

Суддя раніше пропускав невідомий tool, не-object `input`, типи елементів
масиву та вкладені обовʼязкові поля. `2026-02-29`, `2026-04-31` і `24:00`
проходили перевірку форми рядка. Тепер перевіряються реальний календар,
24-годинний час, рекурсивні `items`/`properties`/`required`, null замість
оголошеного типу та скінченність чисел. Безіменний `tool_use` лишається видимим у виборі
інструментів і отримує schema violation: це не коректна відмова без виклику. Prototype key не вважається полем
схеми. Схеми беруться з того самого `TOOLS`, який отримує модель.

Це підтримуваний суддею subset JSON Schema, а не повний JSON Schema validator.
Він не доводить узгодженість суми частин транзакції з її загальною сумою.

### Opaque ID

`h1` у контексті `h10` або `H1` у контексті `h1` раніше вважалися відомим ID.
Тепер збіг чутливий до регістру й меж токена. Це перевірка походження тексту,
а не повна перевірка належності ID сутності: число з іншого поля контексту
саме по собі не доводить, що це ID потрібної звички.

### Цілісність касети

Читання та запис перевіряють структуру до оцінювання: SHA fingerprints,
кількість кейсів, унікальність імен, модель завантажуваного файла й перший
хід без `fedResult`. Порожній кейс дозволений лише з явною transport error.
Дублі більше не можуть мовчки перезаписуватися в `Map`. Погані аргументи
самої моделі залишаються в записі, щоб їх оцінив judge.

Маніфест досі не пінить повний текст усіх user-кейсів: наявних записів для
ретроспективного доведення такого hash немає. Потрібен окремий контроль
походження під час наступного свідомого запису; проставити поточний hash
старій касеті означало б створити недоведене свідчення.

### RAG thresholds

TypeScript `classifyRecall` відхиляє NaN, Infinity й значення поза [0,1] для
mean та обох порогів. Раніше NaN у порогах міг обійти порівняння й дати `pass`.
Чинні пороги 0,5 / 0,4 і їхні включні межі не змінено. Окремий `.mjs` CLI
вже перевіряв ці аргументи — його поведінку не змінено.

### Походження text/vision benchmark

Обидва runner-и позначають stub-результат як `executionMode: "dry-run"`.
Markdown друкує окремий **DRY RUN** з переліком підготовлених викликів і
промптів; accuracy, вартість та порівняння затримок моделей не виводяться.
Змішаний звіт dry-run/live відхиляється. Звіт живого прогону зберігає
попередній формат і окремий знаменник для transport failures.

### Категоризація

Прод-парсер навмисно fail-soft: сміття стає `{other, 0}`. Judge помилково
зараховував це як правильне `other` з низькою confidence, навіть для порожньої
відповіді. Тепер до прод-парсера перевіряється саме його JSON-фрагмент:
категорія мусить бути відомою, confidence — числом від 0 до 1. Code fences
і пояснення навколо JSON підтримуються. Прод-парсер не змінено.

## Наступні кроки за цінністю

1. Записувати fingerprint user-кейсів та походження для нових касет; окремо
   розрізняти застарілий запис і регресію оцінювача.
2. Провести живе повторне вимірювання актуальних кандидатів і Voyage з
   явним бюджетом. Лише воно покаже drift постачальника після дати запису.
3. Додати семантичні інваріанти: сума частин дорівнює транзакції, ID належить
   правильній сутності, числа синтезу підтверджені конкретними tool outputs.
4. Розширювати multi-turn/injection корпус за реальними промахами; вимірювати
   доставку атаки, послух і транспортні збої окремими знаменниками.
5. Виміряти зорові пайплайни на різних HEIC/JPEG/EXIF входах і streaming на
   обірваних/повільних відповідях; успіх JSON judge цього не доводить.
