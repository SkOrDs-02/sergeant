# Runbook: запуск приймання платежів (Plata / LiqPay)

> **Last touched:** 2026-09-02 by @Skords-01. **Next review:** 2026-12-06.
> **Status:** Active

Що має бути правдою, **перш ніж** перемкнути `PLATA_ENABLED` / `LIQPAY_ENABLED` у `true` на продакшні. Код провайдера `plata` готовий і перевірений живим прогоном ([спека](../../90-work/planning/specs/plata-recurring.md)), але сам по собі він приймати гроші не дозволяє.

Порядок кроків не довільний: крок 1 блокує решту, бо від відповіді залежить, чи потрібен ще один шматок інтеграції.

## 1. Фіскалізація — вирішити ПЕРШИМ

**Питання:** чи зобовʼязані ми видавати фіскальний чек за підписку Pro, оплачену карткою.

**Чому це блокер, а не формальність.** Приймання оплати від фізособи через інтернет-еквайринг вважається розрахунковою операцією, і клієнту має бути виданий фіскальний чек (паперовий або електронний). Штраф — 100% вартості проданого без чека за перше порушення і 150% за кожне наступне. Sergeant продає підписку фізособам карткою через monopay, тобто описує рівно цей випадок.

**Чому відповідь не очевидна.** Є виняток для послуг, які надаються **повністю дистанційно**, без фізичної присутності клієнта й особистого контакту, коли взаємодія лише в електронному форматі. Sergeant формально під цей опис схожий, але трактування винятку залежить від групи ФОП і КВЕДів.

**Дія:** запитати бухгалтера. Не трактувати самостійно і не покладатися на висновок AI-асистента — це податкове питання з грошовим штрафом за помилку.

**Наслідок для коду.** Якщо чек потрібен, у monopay є вбудований пРРО (`invoice/fiscal-checks`) — інтегрувати доведеться, але не з нуля. Це окрема робота, свідомо винесена за скоуп спеки переходу на нативні підписки.

## 2. Договір еквайрингу і бойовий токен

`PLATA_TOKEN` на проді — **не** той токен, яким тестували.

|            | Тестовий                                                                                                | Бойовий                                                                                                        |
| ---------- | ------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Де брати   | [api.monobank.ua](https://api.monobank.ua/) — особистий кабінет, вхід сканом QR у застосунку            | [web.monobank.ua](https://web.monobank.ua) — бізнес-кабінет → вкладка методу приймання оплат → **Налаштувати** |
| Передумови | жодних: тестове середовище доступне всім клієнтам банку, ні термінала, ні дозволу на еквайринг не треба | бізнес-рахунок (ФОП або юрособа) + **чинний договір еквайрингу**                                               |
| Обмеження  | картка будь-яка, аби номер проходив алгоритм Луна; Apple/Google Pay не показуються                      | —                                                                                                              |

Отже особистий токен з `api.monobank.ua` для тесту — правильний вибір, і саме ним пройдено живий прогін. Для проду потрібен окремий, з бізнес-кабінету, і він кладеться в `PLATA_TOKEN` у Coolify.

Джерело: [Як отримати API токен для онлайн еквайрингу](https://monobank.ua/en/knowledge-base/acquiring/online/website/api/token).

## 3. Перемкнути прапорець

Аж після кроків 1-2:

- `PLATA_ENABLED=true` + `PLATA_TOKEN=<бойовий>` в Coolify (реєстр прапорців — [feature-flags.md](../../02-engineering/architecture/feature-flags.md)).
- `PLATA_MODE=live`.
- `PUBLIC_WEB_BASE_URL` має вказувати на публічний прод-домен: з нього збираються `webHookUrls` для `subscription/create`. Помилка тут означає, що monobank шле вебхуки в нікуди; підписки все одно активуються звіркою, але з затримкою до 5 хвилин замість секунд.

## 4. Що перевірити після вмикання

- Перша реальна оплата: у `subscriptions` зʼявився рядок `provider='plata'`, `status='active'`, `current_period_end` дорівнює `nextChargeDate`.
- `billing_webhook_total{provider="plata",status="verified"}` росте — вебхуки доходять і підпис сходиться. Нуль тут при успішних оплатах означає, що працює лише полінг (див. `PUBLIC_WEB_BASE_URL` вище).
- `billing_recurring_charge_total{provider="plata",result="past_due"}` — сигнал невдалих списань.

## 5. Відкладене, що варто закрити після першого місяця

**Грейс на невдалому списанні — припущення, не факт.** Ми даємо 3 дні доступу після провалу, але політика ретраїв monobank (скільки разів і з яким кроком банк добиває списання) не задокументована й живцем не перевірена. Після першого місяця живих платежів звірити з реальністю по `summary.totalFailed` і за потреби підкрутити `GRACE_DAYS` у [`plataSync.ts`](../../../apps/server/src/modules/billing/plataSync.ts).
