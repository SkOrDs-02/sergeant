## Історичний контекст

Первісне рішення робило браузерний `Memory Bank` основним сховищем фактів
на кшталт уподобань, цілей, дієти та алергій, щоб асистент міг одразу ними
користуватись. Це було доречно до появи durable profile storage, але вже не
описує реалізовану архітектуру.

## Поточне рішення

Для автентифікованого акаунта `user_profile.payload.memoryBank` — durable
джерело істини фактів профілю. Сховище пристрою лишається кешем і робочою
копією редактора: воно write-through у `PUT /api/me/profile` і гідратується
з сервера звичайним шляхом профілю.

Векторні рядки `ai_memories` не є другим власником цих фактів. Profile mirror
обчислює diff, ставить у чергу змінені `source='profile'` записи та прибирає
застарілі індексні записи. Це best-effort retrieval support: збій дзеркала не
має валити запис профілю. `AI_MEMORY_ENABLED=false` зберігає факти профілю та
лише вимикає їхнє індексування.

У продукті один редактор цих фактів: **Профіль → Банк пам’яті**. Поверхня
налаштувань AI-пам’яті може показувати автоматично зібрану пам’ять, але не
стає конкурентним редактором фактів профілю.

## Наслідки

- Очищення browser storage більше не визначає межу durability для
  автентифікованого користувача: наступна гідратація поверне серверний профіль.
- Видалення чи редагування мусить пройти через запис профілю, щоб RAG-індекс
  зійшовся. Пряма мутація індексу — лише захисне обслуговування, не API редактора.
- Local/offline поведінка — це поведінка кешу. ADR не обіцяє анонімну
  міжпристроєву пам’ять; AI-роути вимагають сесію (ADR-0086).
- Дзеркало profile→vector асинхронне й під feature flag. Його активація в
  середовищі залежить від конфігурації та **очікує підтвердження деплою**;
  її не можна виводити лише з вихідного коду.

## Межа верифікації

`memoryBank.ts`, автентифікований profile route і
`mirrorProfileMemoryEntries()` мають узгоджувати форму запису та стабільні ID.
Дзеркало мусить лишатися ідемпотентним для незмінених записів і прибирати
відповідний `source='profile'` рядок для вилучених.
